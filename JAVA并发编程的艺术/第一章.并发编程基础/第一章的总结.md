### 一、线程的生命周期

第一个章节介绍了线程的完整生命周期，从构造到终止共经历五个核心阶段：

- **构造线程**：通过 `new Thread()` 创建线程对象，指定线程组、线程名、优先级、守护线程状态和可执行任务。`new Thread()` 只是创建 Java 对象，==真正的 OS 线程在 `start()` 时才创建==。
    
- **启动线程**：调用 `start()` 方法后，JVM 创建操作系统线程，由 OS 时间片调度决定何时执行。`start()` 只能调用一次，线程一旦启动就无法复用,因为会把线程变成可执行事件，这意味着线程已使用，而一旦使用之后，JVM会自动清除该线程。
    
- **中断线程**：`interrupt()` 通过设置中断标识符来建议线程停止，并非强制终止。线程通过 `isInterrupted()` 检查标志位自行决定是否退出。
    
- **过时方法**：`suspend()`、`resume()`、`stop()` 已被废弃，因为它们会导致死锁、数据不一致等问题。
    
- **正确终止**：使用中断机制或 `volatile boolean` 标志位实现协作式终止，让线程在安全的时机自行退出并完成清理工作。
    

### 二、线程间的通信：等待/通知机制

线程之间通过一种经典的模型——**消费者与生产者模型**——来实现通信。这个模型的核心是等待/通知机制：

- **消费者**：获取对象的锁 → 检查条件 → 条件不满足则调用 `wait()` 释放锁并进入等待状态 → 被 `notify()`/`notifyAll()` 唤醒后重新获取锁 → 条件满足则执行消费逻辑。
    
- **生产者**：获取对象的锁 → 改变条件 → 调用 `notifyAll()` 通知所有等待线程 → 释放锁。
    

关键设计原则：消费者使用 `while` 循环检查条件防止虚假唤醒，生产者使用 `notifyAll()` 确保信号不会丢失，双方使用**同一个锁对象**进行通信。

基于这个机制，还介绍了**超时等待模式**——在 `wait(long timeout)` 的基础上，每次被唤醒后重新计算剩余超时时间（`remaining = future - now`），确保即使被虚假唤醒或提前唤醒，也能准确判断是否真正超时。这种模式在数据库连接池中得到了实际应用——客户端通过 `fetchConnection(timeout)` 获取连接，超时返回 `null` 而不是无限等待，这是系统自我保护机制的核心体现。

### 三、两个关键字：`volatile` 与 `synchronized`

**`volatile`**

`volatile` 关键字用于修饰字段，它确保了变量的**可见性**——当某个线程修改了被 `volatile` 修饰的变量时，新值会被立即刷新回共享内存，让其他线程能够看到最新的值。

`volatile` **不保证原子性与有序性**。例如 `count++` 这种复合操作（读取-修改-写入），即使 `count` 被 `volatile` 修饰，多个线程同时执行仍然会出现数据不一致。这是因为 `volatile` 只能保证每次读取和写入都走共享内存，但不能阻止另一个线程在这三条指令之间插入操作。

`volatile` 最经典的用法是作为**状态开关变量**（如 `private volatile boolean running = true`），一个线程修改开关，其他线程只读取。

**`synchronized`**

`synchronized` 通过**一次只允许一个线程执行方法或同步块**来确保原子性与有序性。它的底层依赖于 Java 对象的 Monitor：

- 每个 Java 对象都关联一个 Monitor，线程进入同步块时执行 `monitorenter` 指令获取 Monitor，退出时执行 `monitorexit` 释放 Monitor。
    
- 未获取到 Monitor 的线程会进入 BLOCKED 状态，在同步队列中等待。
    
- `wait()` 会释放锁并进入 WAITING 状态，`notify()/notifyAll()` 将等待线程从等待队列移到同步队列。
    

**两者对比**

| 维度      | `volatile` | `synchronized`  |
| ------- | ---------- | --------------- |
| 保证可见性   | ✅          | ✅               |
| 保证原子性   | ❌          | ✅               |
| 性能开销    | 低（无锁，无阻塞）  | 较高（涉及锁的获取与释放）   |
| 适用场景    | 一写多读、状态标志位 | 复合操作、需要对代码块整体加锁 |
| 是否会阻塞线程 | 否          | 是               |
