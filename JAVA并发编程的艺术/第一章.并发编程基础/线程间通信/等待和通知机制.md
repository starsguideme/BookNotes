### 一、什么是等待/通知机制

等待/通知机制是指，线程 A 调用了对象 O 的 `wait()` 方法进入等待状态，而另一个线程 B 调用了对象 O 的 `notify()` 或 `notifyAll()` 方法，线程 A 收到通知后从对象 O 的 `wait()` 方法返回，进而执行后续操作。上述两个线程通过对象 O 来完成交互，对象 O 上的 `wait()` 和 `notify()/notifyAll()` 就像开关一样，用来完成双方之间的通信。

这种模式本质上就是**生产者-消费者模型**：一个线程负责生产数据（修改对象的值），另一个线程负责消费数据（感知到变化后进行相应操作）。整个过程开始于一个线程，而最终执行又是另一个线程，这种模式隔离了"做什么"与"怎么做"。

### 二、为什么不直接用循环检查？

最简单的方法是让消费者线程一直循环检查变量是否符合预期（忙等待）。但这种方式有两个严重缺点：

- **难以确保及时性**：如果检查间隔太长，可能错过变化；如果间隔太短，会浪费 CPU 资源。
    
- **开销大**：线程一直空转，占用 CPU 却没有任何实际产出。
    

等待/通知机制解决了这两个问题：消费者在发现条件不满足时进入等待状态，**不消耗 CPU**；生产者改变条件后主动通知消费者，消费者**立即响应**。

### 三、五个相关方法

| 方法                                      | 说明                                    |
| --------------------------------------- | ------------------------------------- |
| **==`wait()`==**                        | **调用该方法的线程进入等待状态，直到被其他线程通知或中断才会继续执行** |
| **==`wait(long timeout)`==**            | **超时等待一段时间，参数是毫秒，如果没有通知则超时自动返回**      |
| **==`wait(long timeout, int nanos)`==** | **更细致的时间控制，可精确到纳秒级**                  |
| **==`notify()`==**                      | **通知一个在该对象上等待的线程（随机选择其中一个）**          |
| **==`notifyAll()`==**                   | **通知所有等待在该对象上的线程**                    |
|                                         |                                       |

==**重要前提**：这五个方法都必须在 `synchronized` 同步块或同步方法中调用，否则会抛出 `IllegalMonitorStateException`。因为调用这些方法的前提是当前线程必须先持有该对象的 Monitor。==

### 四、等待/通知的执行流程

**① 线程 A 获取到对象 O 的锁，检查条件不满足**
    **↓**
**② 线程 A 调用 O.wait()，释放锁并进入等待状态（WAITING）**
    **↓**
**③ 线程 B 获取到对象 O 的锁，修改条件**
    **↓**
**④ 线程 B 调用 O.notify() 或 O.notifyAll()**
    **↓**
**⑤ 线程 A 收到通知，从 WAITING 变为 RUNNABLE**
    **↓**
**⑥ 线程 B 释放锁后，线程 A 重新获取锁**
    **↓**
**⑦ 线程 A 从 wait() 方法返回，继续执行后续操作**

### 五、面试追问应对

**Q：`wait()` 和 `sleep()` 的区别？**

| **维度**    | **`wait()`**                        | **`sleep()`**      |
| --------- | ----------------------------------- | ------------------ |
| **所属类**   | **`Object` 的方法**                    | **`Thread` 的静态方法** |
| **是否释放锁** | **==释放锁==**                         | **==不释放锁==**       |
| **调用要求**  | **必须在 `synchronized` 块中**           | **可以在任何地方调用**      |
| **唤醒方式**  | **需要 `notify()`/`notifyAll()` 或超时** | **时间到自动苏醒**        |

**Q：为什么 `wait()` 必须在 `synchronized` 中调用？**

线程在调用 `wait()` 之前，必须先持有该对象的锁（通过 `synchronized` 获取），这样 JVM 才知道它正在这个对象上等待。如果不用 `synchronized` 直接调用，线程没有持有锁就去等待，JVM 无法保证当前条件判断是原子性的，可能导致在"条件判断"和"调用 `wait()`"之间被其他线程修改了条件，而此时线程已经错过了 `notify()` 信号，导致线程**永久等待**。

**Q：调用 `notify()` 后，等待线程会立刻执行吗？**

不会。`notify()` 只是将等待线程从等待队列移到同步队列，状态从 `WAITING` 变为 `BLOCKED`。被通知的线程必须等到调用 `notify()` 的线程释放锁之后，重新竞争到锁，才能从 `wait()` 方法返回继续执行。

**Q：为什么推荐使用 `notifyAll()` 而不是 `notify()`？**

`notify()` 只随机唤醒一个等待线程，在某些场景下如果被唤醒的不是正确的线程，而条件又不满足，该线程可能继续等待，而真正应该被唤醒的线程却永远等不到通知，造成**信号丢失**。`notifyAll()` 唤醒所有等待线程，让它们都去重新检查条件，即使有部分线程条件不满足继续等待，条件满足的线程也能继续执行。在多个生产者和多个消费者的场景下，`notifyAll()` 是更安全的选择。
