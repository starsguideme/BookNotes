等待/通知机制最经典的应用就是**生产者-消费者模式**。这个范式可以提炼为两套对称的操作流程：

---

### 一、消费者（等待方）范式

消费者需要检查条件，条件不满足时等待，条件满足时执行逻辑。
synchronized (lock) {
    // 1. 获取对象的锁
    while (条件不满足) {
        // 2. 如果条件不满足，调用 wait() 进入等待
        lock.wait();
    }
    // 3. 条件满足则执行对应的逻辑
    // 消费数据...
}

**消费者范式的四个关键点**：

|步骤|操作|说明|
|---|---|---|
|==**1**==|获取对象的锁|通过 `synchronized` 获取 `lock` 对象的锁|
|==**2**==|循环检查条件|如果条件不满足，调用 `lock.wait()` 释放锁并进入等待状态，被通知后重新获取锁并从 `wait()` 返回|
|==**3**==|执行消费逻辑|条件满足后，执行实际的数据处理操作|
|==**4**==|释放锁|退出 `synchronized` 块时自动释放锁|

**面试追问：为什么用 `while` 而不是 `if`？**

当线程从 `wait()` 被唤醒时，条件可能已经被其他线程改变。使用 `if` 只会检查一次条件，如果条件不满足，线程会继续执行后面的逻辑导致错误。使用 `while` 会让线程在被唤醒后重新检查条件，条件不满足则再次进入等待状态。这是防止 **虚假唤醒** 的标准做法。

---

### 二、生产者（通知方）范式

生产者负责改变条件，然后通知等待的消费者线程。

synchronized (lock) {
    // 1. 获得对象的锁
    // 2. 改变条件
    // 例如：向缓冲区添加数据
    // 3. 通知所有等待在对象上的线程
    lock.notifyAll();
}

**生产者范式的四个关键点**：

| 步骤        | 操作     | 说明                                         |
| --------- | ------ | ------------------------------------------ |
| ==1== | 获取对象的锁 | 通过 `synchronized` 获取 `lock` 对象的锁           |
| ==2== | 改变条件   | 执行修改操作，使得消费者等待的条件得以满足                      |
| ==3== | 通知等待线程 | 调用 `lock.notifyAll()` 唤醒所有等待线程             |
| ==4== | 释放锁    | 退出 `synchronized` 块时自动释放锁，被唤醒的线程此时才能重新竞争到锁 |

**面试追问：为什么推荐 `notifyAll()` 而不是 `notify()`？**

`notify()` 只随机唤醒一个等待线程。在多消费者场景下，如果被唤醒的线程检查后发现条件仍不满足（比如数据被其他消费者抢先拿走了），就会再次等待。但此时可能还有其他消费者满足条件，却永远等不到通知，造成 **信号丢失**。`notifyAll()` 唤醒所有等待线程，让它们都重新检查条件，哪个满足哪个执行，不满足的继续等待，能有效避免这个问题。

---
