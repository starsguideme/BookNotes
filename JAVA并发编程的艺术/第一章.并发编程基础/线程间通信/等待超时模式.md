### 一、什么是超时等待

当调用一个方法时等待一段时间（通常是一个给定的时间段），如果该方法能够在给定的时间段内得到结果，那么立即将结果返回；如果超过时间段仍未得到结果，则不再继续等待，直接返回默认结果或抛出超时异常。

这种机制的核心思想是：**给等待操作加上时间上限，避免线程无限期阻塞。**

### 二、经典范式的局限性

前面在[[等待和通知的经典范式]]中讲述了消费者与生产者的模型，其核心流程分为三个步骤：加锁 → 条件循环 → 处理逻辑。但这种经典范式存在一个局限：消费者在条件不满足时，会调用 `wait()` **无限期等待**，直到被生产者 `notify()` 唤醒。

如果生产者因为某种原因（如异常、死锁）永远没有调用 `notifyAll()`，消费者线程就会**永久阻塞**，造成线程资源浪费甚至系统不可用。

### 三、超时等待的实现原理

实现超时等待只需要对经典范式做一个非常小的改动——**在等待循环中加入超时时间计算**：

1. 设定超时时间段为 `T`，当前时间为 `now`，则超时边界为 `now + T`。
    
2. 每次进入循环时，计算**剩余超时时间** = 超时边界 - 当前时间。
    
3. 如果剩余超时时间 ≤ 0，说明已经超时，直接退出等待循环并释放资源。
    
4. 如果剩余超时时间 > 0，则调用 `wait(剩余时间)` 等待，等待返回后重新循环检查条件。
    

**核心思想**：不是在循环开始时一次性计算超时时间，而是**每次等待返回后重新计算剩余时间**，这样即使线程被虚假唤醒，也能准确判断是否真正超时。

### 四、超时等待的标准代码模板
// 消费者：支持超时等待的范式
public synchronized Object consume(long timeout) throws InterruptedException {
    long future = System.currentTimeMillis() + timeout; // 超时边界 = 当前时间 + 超时时长
    long remaining = timeout;                            // 剩余超时时间
    while (条件不满足 && remaining > 0) {
        wait(remaining);                                 // 等待剩余时间
        remaining = future - System.currentTimeMillis(); // 重新计算剩余超时时间
    }
    // 两个退出原因：
    // 1. 条件满足 → 执行后续逻辑
    // 2. remaining <= 0 → 超时，返回默认结果或抛出异常
    if (条件满足) {
        // 执行消费逻辑
        return result;
    } else {
        return 默认值; // 或 throw new TimeoutException();
    }
}

### 五、为什么每次等待后都要重新计算剩余时间？

这是超时等待中最容易出错的细节。线程从 `wait(remaining)` 返回有两种可能：

| 返回原因                    | 说明                    |     |
| ----------------------- | --------------------- | --- |
| ==**被 `notify()` 唤醒**== | 条件可能已满足，需要重新检查        |     |
| ==**等待时间到了，自动返回**==     | 此时 `remaining` 已经消耗完毕 |     |

无论哪种原因返回，都必须用 `future - System.currentTimeMillis()` 重新计算剩余时间，而不是简单地减去一个固定值。因为：

- 如果是因为 `notify()` 提前返回，剩余时间应该反映真实的时间消耗。
    
- 如果是虚假唤醒（`wait()` 意外返回），剩余时间同样需要重新评估。
    
- 用固定值递减无法准确判断是否真的超时。
    

### 六、面试要点

**Q：`wait(long timeout)` 和 `sleep(long millis)` 在超时场景下有什么区别？**

| 维度    | `wait(long timeout)`    | `sleep(long millis)`  |
| ----- | ----------------------- | --------------------- |
| 是否释放锁 | ==**释放锁**==，其他线程可以进入同步块 | ==**不释放锁**==，其他线程无法进入 |
| 唤醒方式  | 可以被 `notify()` 提前唤醒     | 只能等时间到或 `interrupt()` |
| 适用场景  | 需要等待条件变化，且允许超时放弃        | 单纯的时间延迟，不涉及条件同步       |

**Q：如果超时时间设置为 0 会怎样？**

`wait(0)` 的行为等价于 `wait()`，即**无限期等待**，直到被 `notify()` 唤醒。这是 `Object.wait()` 方法的特殊设计：参数为 0 表示不设超时。

**Q：`future - System.currentTimeMillis()` 和直接递减一个固定值有什么区别？**

直接递减固定值假设了每次 `wait(remaining)` 都刚好消耗了 `remaining` 毫秒，但实际上线程可能被 `notify()` 提前唤醒，实际消耗时间小于 `remaining`。用固定值递减会导致超时判断不够精确。`future - now` 的写法不依赖 `wait()` 到底等了多久，只看是否已经过了超时边界，这是一种更稳健的做法，能应对任何唤醒场景。
