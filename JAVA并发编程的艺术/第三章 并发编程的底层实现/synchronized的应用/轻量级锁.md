
### 一、获取轻量级锁的流程

线程执行同步块之前，`JVM` 会在**当前线程的栈帧**中创建一个名为 **Lock Record** 的空间，用于存储锁记录。获取轻量级锁的过程如下：

**1. 复制 Mark Word**

线程将 Java 对象头中的 Mark Word 复制到自己的 Lock Record 中。这份复制被称为 **Displaced Mark Word**，它保存了对象在加锁前的原始状态。

**2. [[CAS]] 替换对象头**

线程通过 CAS 操作，尝试将对象头中的 Mark Word 替换为一个指针，指向自己栈帧中的 Lock Record。

**3. 判断结果**

| 结果             | 含义                             | 后续操作           |
| -------------- | ------------------------------ | -------------- |
| ==**CAS 成功**== | 当前线程获取锁，Mark Word 的锁标志位变为 `00` | 线程进入同步块执行      |
| ==**CAS 失败**== | 说明其他线程也在竞争锁                    | 进入自旋等待或升级为重量级锁 |

### 二、CAS 失败后的竞争策略

当 CAS 失败时，说明有另一个线程也在尝试获取同一把锁。此时根据竞争情况有两种处理方式：

- **自旋等待**：失败线程不立刻阻塞，而是在用户态进行自旋，反复尝试 CAS。设计出发点是：大部分同步块的执行时间都很短，持有锁的线程很快就会释放，自旋等待的开销远小于线程阻塞和唤醒的上下文切换开销。
    
- **升级为重量级锁**：如果自旋超过一定次数（默认 10 次，JVM 也会根据运行情况自适应调整）仍未成功，说明锁竞争激烈。此时轻量级锁不再适合，锁会升级为重量级锁，未获取锁的线程进入 BLOCKED 状态，在 Monitor 的同步队列中等待。
    

### 三、轻量级锁的释放流程

1. 线程将 Lock Record 中保存的 Displaced Mark Word 通过 CAS 写回对象头。
    
2. 如果 CAS 成功，说明在持有锁期间没有其他线程竞争，锁恢复为无锁状态。
    
3. 如果 CAS 失败，说明在持有锁期间有其他线程尝试过竞争，此时 Mark Word 中已经是重量级锁的指针，需要唤醒在 Monitor 同步队列中等待的线程。
### 四、轻量级锁与膨胀流程图

###   第一阶段：线程1 获取轻量级锁

| 步骤  | 操作             | 详细描述                                                                           |
| --- | -------------- | ------------------------------------------------------------------------------ |
| 1   | 初始状态           | 对象处于无锁状态，Mark Word 中存储着 HashCode 和分代年龄，锁标志位为 `01`                              |
| 2   | 创建 Lock Record | JVM 在线程1 的栈帧中创建一块 **Lock Record** 空间，用于存储锁记录                                   |
| 3   | 复制 Mark Word   | 线程1 将对象头中的 Mark Word 完整复制到自己的 Lock Record 中，作为 Displaced Mark Word（保存加锁前的原始状态） |
| 4   | CAS 替换         | 线程1 通过 CAS 操作，尝试将对象头的 Mark Word 替换为指向自己栈帧中 Lock Record 的指针                     |
| 5   | CAS 成功         | Mark Word 锁标志位从 `01` 变为 `00`，线程1 获取轻量级锁，进入同步块执行代码                              |

---

###   第二阶段：线程2 竞争轻量级锁

| 步骤  | 操作             | 详细描述                                                                  |
| --- | -------------- | --------------------------------------------------------------------- |
| 6   | 线程2 进入         | 线程2 也尝试进入同一个同步块                                                       |
| 7   | 创建 Lock Record | JVM 在线程2 的栈帧中同样创建一块 Lock Record 空间                                    |
| 8   | 复制 Mark Word   | 线程2 将对象头中的 Mark Word 复制到自己的 Lock Record 中（此时 Mark Word 中是指向线程1 栈帧的指针） |
| 9   | CAS 尝试         | 线程2 通过 CAS 操作，尝试将对象头的 Mark Word 替换为指向自己栈帧的指针                          |
| 10  | CAS 失败         | 对象头中的 Mark Word 指向的是线程1 的 Lock Record，和线程2 预期的不一致，CAS 失败              |
| 11  | 开始自旋           | 线程2 不立即阻塞，在用户态反复自旋，不断重试 CAS 操作                                        |

---

###   第三阶段：锁膨胀为重量级锁

| 步骤  | 操作           | 详细描述                                                     |
| --- | ------------ | -------------------------------------------------------- |
| 12  | 自旋持续         | 线程2 反复执行 CAS，但线程1 仍在执行同步块，CAS 始终失败                       |
| 13  | 自旋超阈值        | **线程2 自旋次数超过 JVM 设定的阈值（默认 10 次，JVM 会自适应调整），JVM 判断锁竞争激烈** |
| 14  | 开始膨胀         | 线程2 主动将轻量级锁升级为重量级锁                                       |
| 15  | 创建 Monitor   | JVM 为该对象创建或获取关联的 Monitor 对象                              |
| 16  | 修改 Mark Word | 对象头中的 Mark Word 被修改为指向 Monitor 对象的指针，锁标志位变为 `10`         |
| 17  | 线程2 阻塞       | 线程2 将自己放入 Monitor 的同步队列，进入 BLOCKED 状态，放弃自旋，让出 CPU        |

---

###   第四阶段：线程1 释放锁

| 步骤  | 操作       | 详细描述                                                                |
| --- | -------- | ------------------------------------------------------------------- |
| 18  | 线程1 执行完毕 | 线程1 执行完同步块，准备退出                                                     |
| 19  | CAS 尝试恢复 | 线程1 将 Lock Record 中的 Displaced Mark Word 通过 CAS 写回对象头               |
| 20  | CAS 失败   | Mark Word 已经被线程2 修改为指向 Monitor 的指针，和 Displaced Mark Word 不一致，CAS 失败 |
| 21  | 检测到膨胀    | 线程1 意识到：在我持有锁期间，有其他线程来竞争过，锁已经被膨胀为重量级锁                               |
| 22  | 走重量级释放   | 线程1 不再尝试 CAS，改为通过 Monitor 走重量级锁的释放流程                                |
| 23  | 唤醒等待线程   | 线程1 释放 Monitor，Monitor 从同步队列中取出等待的线程2，将其唤醒                          |
| 24  | 线程2 获取锁  | 线程2 从 BLOCKED 状态变为 RUNNABLE，重新竞争锁，获取成功后进入同步块执行                      |

---

###   各阶段 Mark Word 状态变化

| 阶段      | 步骤    | Mark Word 内容              | 锁标志位 | 锁状态  |
| ------- | ----- | ------------------------- | ---- | ---- |
| 初始      | 1     | HashCode + 分代年龄           | `01` | 无锁   |
| 线程1 获取锁 | 5     | 指向线程1 Lock Record 的指针     | `00` | 轻量级锁 |
| 线程2 竞争  | 10-11 | 指向线程1 Lock Record 的指针（不变） | `00` | 轻量级锁 |
| 锁膨胀     | 16    | 指向 Monitor 的指针            | `10` | 重量级锁 |
| 线程1 释放  | 19-22 | 指向 Monitor 的指针（不变）        | `10` | 重量级锁 |
| 线程2 被唤醒 | 23-24 | Monitor 管理锁的获取与释放         | `10` | 重量级锁 |
### 五、面试要点

**Q：轻量级锁适用于什么场景？**

适用于**两个线程交替执行**同步块的场景。因为两个线程不会同时在临界区内，通过 CAS 自旋就可以获取锁，避免了线程阻塞和唤醒的开销。但如果多个线程同时竞争，自旋消耗 CPU 时间过长，就需要升级为重量级锁。

**Q：轻量级锁和偏向锁有什么区别？**

偏向锁解决的是"一个线程反复获取"的场景，获取锁几乎零开销。轻量级锁解决的是"两个线程交替执行"的场景，通过 CAS 自旋获取锁。偏向锁在有第二个线程竞争时就会撤销并升级为轻量级锁。

**Q：Displaced Mark Word 的作用是什么？**
·把 Displaced Mark Word 写回对象头，恢复对象在加锁前的原始状态。如果没有这个备份，释放锁后就无法还原对象的 HashCode 和分代年龄等信息。
