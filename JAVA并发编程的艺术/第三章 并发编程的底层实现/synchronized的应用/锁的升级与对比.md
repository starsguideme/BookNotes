### 一、锁的四种状态与升级方向

在 Java 中，锁有四种状态，按照竞争程度从低到高依次为：

**无锁 → [[偏向锁]] → [[轻量级锁]] → [[重量级锁]]**

这几个状态会随着线程之间的竞争情况逐渐升级。==**锁可以升级但不会降级**==——一旦锁从偏向锁升级到轻量级锁，即使之后竞争消失，也不会再降回偏向锁。这个设计是为了简化锁状态管理的复杂度。

**面试要点**：偏向锁撤销需要等到安全点并暂停线程，这个开销较大。在 JDK 15 之后，偏向锁被默认关闭，JDK 21 中已被彻底移除。

### 二、偏向锁的完整生命周期

**① 线程 A 第一次获取锁**
   **→ Mark Word 从未锁定变为偏向锁，记录线程 A 的 ID**
        **↓**
**② 线程 A 再次进入同步块**
   **→ 检查 Mark Word 中线程 ID 是否为自己 → 是，直接进入（无 CAS）**
        **↓**
**③ 线程 B 尝试竞争该锁**
   **→ 发现偏向锁已被线程 A 持有，需要撤销偏向锁**
        **↓**
**④ 撤销偏向锁**
   **→ 等待安全点，暂停线程 A**
   **→ 遍历线程 A 的栈，检查锁记录**
        **↓**
    **├── 线程 A 已不存在 → Mark Word 改为无锁状态**
    **└── 线程 A 仍存活 → Mark Word 升级为轻量级锁**
        **↓**
**⑤ 升级后的状态**
   **→ 线程 A 和线程 B 通过 CAS 自旋竞争轻量级锁**

### 五、面试要点

**Q：偏向锁为什么被废弃了？**

偏向锁适用于“一个线程反复获取同一把锁”的场景。但在现代 Java 应用中，线程池被广泛使用，锁不会被某一个线程长期独占，偏向锁的偏向往往很快就要被撤销，而撤销操作的开销（等待安全点、暂停线程、遍历栈）本身就很大，得不偿失。因此 JDK 15 默认关闭偏向锁，JDK 21 彻底移除。

**Q：锁升级是不可逆的，为什么这样设计？**

如果允许锁降级，需要在每次锁释放后判断当前竞争情况并决定是否降级，这需要额外的 CPU 开销和复杂的同步判断。而“只能升级不能降级”的设计实现简单，且在实际应用中，一旦出现竞争，后续再次竞争的概率很高，频繁的升降级反而得不偿失。

**Q：偏向锁和轻量级锁的区别？**

偏向锁解决了“一个线程反复获取”的问题，获取锁几乎零开销，但撤销成本高。轻量级锁解决了“两个线程交替执行”的问题，通过 CAS 自旋来获取锁，避免线程阻塞，但如果多个线程同时竞争，自旋空耗 CPU，就需要升级为重量级锁。
