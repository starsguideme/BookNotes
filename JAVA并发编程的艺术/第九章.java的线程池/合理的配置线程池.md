
### 一、从四个性质来思考

要想更好地配置线程池，可以从以下四个性质来思考：

| 性质 | 分类 | 说明 |
|------|------|------|
| ==**任务的性质**== | CPU 密集型、I/O 密集型、混合型 | 不同性质的任务需要的线程数不同 |
| ==**任务的优先级**== | 高、中、低 | 使用优先级队列可以根据优先级来处理任务 |
| ==**任务的执行时间**== | 长、中、短 | 执行时间长的任务可能会阻塞线程池中的线程 |
| ==**任务的依赖性**== | 是否依赖其他系统资源 | 如数据库连接、网络 I/O 等 |

### 二、根据任务性质配置线程数

| 任务类型 | 配置策略 | 原因 |
|---------|---------|------|
| ==**CPU 密集型**== | 尽可能**小的线程数**，推荐 `CPU 核心数 + 1` | CPU 密集型任务会长时间占用 CPU，线程过多会导致频繁的上下文切换，反而降低效率 |
| ==**I/O 密集型**== | 尽可能**大的线程数**，推荐 `CPU 核心数 × 2` | I/O 密集型任务线程并不是一直在执行任务，大部分时间在等待 I/O 完成，因此需要更多的线程来充分利用 CPU |
| ==**混合型**== | 将其拆分为 CPU 密集型和 I/O 密集型两部分，分别配置 | 两者的结合，可以分开处理以获得更好的性能 |

这些任务都可以在**优先级任务队列**（如 `PriorityBlockingQueue`）中使用，它可以根据任务的优先级来处理任务，让高优先级的任务优先执行。

### 三、依赖数据库连接的场景

对于依赖数据库 Druid 的任务来说，因为线程提交 SQL 后需要等待数据库返回结果，因此**等待的时间越长**会导致 CPU 的**空闲时间越长**。因此线程池理应设置得**大一点**，以充分利用 CPU 资源。

### 四、有界队列的优势

为了解决大规模线程池但又不想使用无上限的线程池，可以采用**有界队列**的功能。因为有界队列可以增加系统的**稳定性**和**预警能力**，可以根据需求设置大小。当然，既然是用于线程池，因此超出界限的线程也会陷入**长时间的线程等待**，但这比让使用无界队列的系统因资源耗尽而崩溃要好得多。

### 五、线程数计算公式

| 任务类型 | 推荐线程数 | 公式 |
|---------|----------|------|
| ==**CPU 密集型**== | `N + 1` | `N = CPU 核心数` |
| ==**I/O 密集型**== | `N × 2` | `N = CPU 核心数` |

**补充公式**：对于 I/O 密集型任务，也可以使用以下更精确的公式：

```
最佳线程数 = CPU 核心数 × (1 + 平均等待时间 / 平均工作时间)
```

### 六、面试要点

| 问题                  | 回答                                          |
| ------------------- | ------------------------------------------- |
| **CPU 密集型任务如何配置线程数**    | ==**`CPU 核心数 + 1`**==，避免频繁上下文切换             |
| **I/O 密集型任务如何配置线程数**    | ==**`CPU 核心数 × 2`**==，充分利用 CPU 等待 I/O 的空闲时间 |
| **依赖数据库的任务线程池应该设置大还是小** | ==**设置大一点**==，因为等待数据库返回期间 CPU 处于空闲状态        |
| **为什么推荐使用有界队列**         | 增加系统的**稳定性和预警能力**，避免资源耗尽                    |
