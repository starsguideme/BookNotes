### 一、什么是上下文切换

由于每次在线程之间进行切换时，系统需要保存当前线程的状态（包括程序计数器、寄存器、栈指针等），然后查找并恢复下一个线程的状态，这个过程会产生额外的开销。这个开销就是**上下文切换**。

### 二、上下文切换的具体过程

多线程编程中，线程数量往往大于 CPU 核心数，CPU 需要通过时间片轮转来调度线程。每次切换分为两步：

1. **保存现场**：CPU 暂停当前线程的执行，把它的程序计数器、寄存器、栈指针等状态保存到内存中。
    
2. **恢复现场**：CPU 从内存中读取下一个线程的保存状态，恢复到寄存器中，然后开始执行该线程。
    

这两步操作本身不产生任何业务价值，纯粹是**调度开销**。单次上下文切换的耗时通常在**微秒级别**，但高并发场景下每秒可能发生成千上万次切换，累积开销会显著影响系统吞吐量。

### 三、如何减少上下文切换的开销？

| 策略              | 原理                      | 实际应用                                  |
| --------------- | ----------------------- | ------------------------------------- |
| ==**无锁并发编程**==  | 避免使用锁，减少线程阻塞和唤醒         | `ConcurrentHashMap` 使用 CAS 分段操作       |
| ==**CAS 算法**==  | 使用硬件层面的原子操作，不阻塞线程       | `AtomicInteger` 的 `incrementAndGet()` |
| ==**合理设置线程数**== | 线程数接近 CPU 核心数时切换最少      | CPU 密集型任务：核心数 + 1                     |
| ==**使用协程**==    | 协程在用户态切换，不涉及内核态，开销远小于线程 | Go 的 goroutine、Java 的虚拟线程             |

### 四、面试要点

**Q：线程数越多越好吗？**

不是。当线程数远大于 CPU 核心数时，大量 CPU 时间被浪费在上下文切换上，实际处理业务的时间反而减少，系统吞吐量下降。

**Q：上下文切换的开销有多大？**

单次上下文切换通常耗时**几微秒到几十微秒**。如果每秒发生 10 万次切换，累积开销可能达到**数百毫秒甚至秒级**，对高并发系统来说影响显著。

**Q：CAS 为什么能减少上下文切换？**

`synchronized` 获取锁失败时线程会进入 BLOCKED 状态，涉及**两次上下文切换**（阻塞一次，唤醒一次）。CAS 在硬件层面原子完成"比较-交换"操作，线程不会被阻塞，也就避免了上下文切换的开销
