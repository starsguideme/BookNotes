### 一、为什么大量等待线程会增加上下文切换？
当线程池中有大量线程处于等待状态时，虽然它们不消耗 CPU，但它们仍然存活在系统中。操作系统调度器会周期性地检查所有存活线程的状态，线程数量越多，调度器每次需要扫描的线程就越多，调度开销也就越大。此外，当这些等待线程被 `notifyAll()` 唤醒时，大量线程同时竞争锁，会导致激烈的锁竞争和频繁的上下文切换。
 
### 二、缩减线程的策略

线程池可以通过定期检查工作者线程的状态来动态调整线程数量。如果发现大量线程处于等待状态（即工作队列为空，多个工作者线程都在 `wait()`），说明当前线程数量超出了实际需要的处理能力，此时可以将线程池中的最大线程数进行缩减，关闭一部分空闲线程。这样可以有效减少线程总数，从而降低上下文切换的频率和调度开销。

### 三、具体实现方式

在之前实现的 `SimpleThreadPool` 中，`removeWorker` 方法就实现了这一逻辑。可以在 `serverCron` 式的周期性检查任务中调用该方法，当检测到空闲线程过多时自动缩减：
// 周期性执行的检查逻辑（简化示例）
public void trimIdleWorkers() {
    synchronized (jobs) {
        // 当工作队列为空，且工作者线程数超过核心线程数时
        if (jobs.isEmpty() && workers.size() > corePoolSize) {
            int idleCount = workers.size() - corePoolSize;
            removeWorker(idleCount); // 缩减空闲线程
        }
    }
}

**设计原则**：缩减操作不是立即关闭线程，而是调用 `worker.shutdown()` 设置 `running = false` 并调用 `notifyAll()` 唤醒等待中的线程，让它们检查到标志位后自行退出循环。这是标准的**协作式终止**方式，避免强制终止带来的资源释放问题。

### 四、面试要点

**Q：为什么等待状态的线程也会导致性能问题？**

等待状态的线程虽然不占用 CPU，但操作系统调度器仍然需要管理它们。当线程数量过多时，调度器的负担会增大。更关键的是，当任务到来时调用 `notifyAll()`，大量等待线程被同时唤醒并竞争锁，产生**惊群效应**——大部分线程抢不到锁又回到等待状态，这个反复唤醒-竞争-等待的过程就是不必要的上下文切换开销。

**Q：线程池的核心线程数和最大线程数有什么区别？**

核心线程数是在任何情况下都保留的线程数量，即使它们处于空闲状态也不会被回收。最大线程数是线程池允许创建的最大线程数量，当工作队列满且线程数小于最大线程数时，线程池会创建新线程来处理任务。当任务量下降、空闲线程过多时，超过核心线程数的部分可以被回收，这就是动态缩减的策略。
