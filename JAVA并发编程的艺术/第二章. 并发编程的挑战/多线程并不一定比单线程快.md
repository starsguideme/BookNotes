### 一、多线程的额外开销

每次创建一个新的线程并进行上下文切换时，都需要一定的额外开销，这会导致每次都要花费时间去处理这些与业务逻辑无关的任务。具体开销包括：

|开销类型|说明|
|---|---|
|==**线程创建与销毁**==|每个线程的创建都需要系统调用和内存分配，执行时间很短的任务时，创建线程的开销可能比任务本身还大|
|==**上下文切换**==|线程数量超过 CPU 核心数时，CPU 需要频繁保存和恢复线程状态，单次切换耗时几微秒到几十微秒，高并发下累积开销显著|
|==**内存占用**==|每个线程默认占用约 1MB 的栈内存，线程数过多会消耗大量内存资源|

### 二、为什么单线程有时反而更快？

单线程没有线程创建、销毁和上下文切换的责任与开销，CPU 可以全神贯注于业务逻辑的执行。当任务本身是纯 CPU 计算且耗时极短时，多线程带来的额外开销可能超过了并行执行的收益，此时单线程反而更快。

这和硬件特性也有关系——比如 Redis 的内存操作速度远远快于磁盘 I/O。在高并发场景下，如果每个命令都在微秒级完成，主线程同步处理百万级别的命令也不会产生严重的延迟，这种耗时极短的 CPU 操作就属于单线程处理的合理范畴。

### 三、判断标准

|场景|单线程|多线程|
|---|---|---|
|==**纯 CPU 计算 + 耗时极短**==|✅ 更优（无切换开销）|❌ 上下文切换开销可能大于任务本身|
|==**包含 I/O 等待**==（磁盘、网络、数据库）|❌ 等待期间 CPU 空转|✅ 其他线程可利用等待时间执行|
|==**需要并行处理大量数据**==|❌ 单线程吞吐量有限|✅ 多核并行提升吞吐量|

### 四、面试要点

**Q：单线程一定比多线程慢吗？**

不一定。在任务执行时间极短、无 I/O 等待的场景下，单线程可能更快，因为它免去了线程创建和上下文切换的开销。Redis 就是典型的例子——它的命令都在内存中完成，执行速度极快，单线程避免了锁竞争和上下文切换，反而获得了极高的吞吐量。

**Q：什么时候应该用多线程？**

当任务包含 I/O 阻塞操作（磁盘读写、网络请求、数据库查询）或需要利用多核 CPU 并行处理大量数据时，多线程的优势才真正体现出来。I/O 等待期间线程会被阻塞，如果只有一个线程，CPU 就完全空闲；多线程可以让其他线程在等待期间继续执行，提高整体吞吐量。

**Q：I/O 密集型任务为什么适合多线程？**

当线程执行 I/O 操作时，磁盘或网络的响应速度远慢于 CPU 的处理速度。如果只有一个线程，CPU 只能空转等待 I/O 完成。使用多线程时，当一个线程阻塞等待 I/O，其他线程可以立刻被调度执行，充分利用 CPU 资源。尽管多线程会带来上下文切换开销，但在 I/O 密集型场景中，这些开销相对于 I/O 等待时间来说可以忽略不计。
