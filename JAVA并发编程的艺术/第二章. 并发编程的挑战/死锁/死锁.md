### 一、锁的困境

锁是一个非常有用的工具，运用场景非常多，使用起来简单且易于理解。但它也会带来一些困扰——如果在锁中嵌套锁，或者因异常没有合理释放锁，就有可能引发**死锁**。一旦产生死锁，会产生大量的麻烦，包括但不限于系统功能阻塞、资源永远无法获取，甚至系统宕机。

**死锁的四个必要条件**：

|条件|说明|
|---|---|
|==**互斥**==|资源每次只能被一个线程使用|
|==**请求与保持**==|线程持有至少一个资源，同时又请求其他资源|
|==**不可剥夺**==|线程已获得的资源在未使用完之前不能被强制剥夺|
|==**循环等待**==|多个线程之间形成一种头尾相接的循环等待关系|

四个条件同时满足，死锁就必然发生。

### 二、解决方案

**1. 避免一个线程同时获取多个锁**

尽可能保证每个线程只持有一个锁。如果必须获取多个锁，统一所有线程的加锁顺序——比如规定必须先获取锁 A 再获取锁 B，避免了"线程1持有A等B，线程2持有B等A"的循环等待。

**2. 避免一个线程在锁内同时占用多个资源**

尽量保证每个锁都只占用一个资源，缩小锁的粒度。如果必须访问多个资源，可以先把所有资源准备好，然后在最小范围内加锁更新。

**3. 尝试使用定时锁**

使用 `Lock.tryLock(timeout)` 来代替永不超时的 `synchronized` 或 `lock.lock()`。如果在指定时间内获取不到锁，就放弃并释放已持有的资源，避免无限等待。这破坏了"请求与保持"条件。
Lock lock = new ReentrantLock();
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try {
        // 处理业务逻辑
    } finally {
        lock.unlock();
    }
} else {
    // 获取锁超时，放弃执行，避免死锁
}

**4. 对于数据库来说**

加锁和解锁必须处于同一个数据库连接中，否则会出现解锁失败的问题。这与 Java 中的锁释放必须在 `finally` 块中执行的原理一致——确保在任何情况下锁都能被正确释放。

### 三、其他检测与避免手段

- **使用 `jstack` 工具**：将 `jstack` 打印的线程快照中重点关注 `BLOCKED` 状态并查看它们等待的锁资源，如果多个线程等待的锁形成了闭环，说明发生了死锁。
    
- **使用 `Lock.lockInterruptibly()`**：支持中断方式获取锁，当检测到死锁时可以中断等待线程。
    
- **使用显式锁对象**：不同的资源用不同的锁保护，而不是所有资源共用一把大锁，这样能从根本上降低锁的交叉依赖概率。
    

### 四、面试要点

**Q：`synchronized` 发生死锁时能自动解锁吗？**

不能。`synchronized` 没有超时机制，获取不到锁时会一直阻塞。如果发生死锁，线程永远无法自行恢复，只能通过重启 JVM 来解决。使用 `ReentrantLock.tryLock(timeout)` 或 `lockInterruptibly()` 可以避免这种无限等待。

**Q：如何排查线上死锁问题？**

使用 `jstack <pid>` 命令打印线程堆栈，在输出末尾会显示 JVM 检测到的死锁信息，包括死锁线程名称和它们各自持有的锁与等待的锁。如果没有自动检测结果，则需要人工分析线程栈中处于 `BLOCKED` 状态的线程，检查它们等待的锁资源是否形成闭环。

**Q：死锁的四个必要条件中，破坏哪个最容易？**

==**破坏"循环等待"条件最容易做到**==。通过统一所有线程的加锁顺序（按固定顺序获取锁），可以彻底消除循环等待。其他三个条件中，互斥通常无法破坏（资源本身就是互斥的），不可剥夺性在 Java 中难以实现，请求与保持可以通过一次性申请所有资源来破坏，但实现复杂度较高。
