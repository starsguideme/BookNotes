### 一、多线程未必比单线程快

在并发编程中，多线程并非总是优于单线程。多线程带来了额外的开销——线程创建与销毁、上下文切换、锁竞争和资源等待。当这些额外开销的总和超过了并行执行带来的收益时，多线程的实际性能会低于单线程。这也是为什么在并发编程中需要关注以下三大核心问题。

### 二、三大挑战与解决方案

#### 1. 上下文切换

当线程数量超过 CPU 核心数时，CPU 需要在线程之间来回切换。每次切换都要保存当前线程的执行状态并恢复下一个线程的状态，这个开销不产生任何业务价值。当上下文切换频繁发生时，大量 CPU 时间被浪费在调度上，实际吞吐量反而下降。

**解决方案**：

|策略|原理|
|---|---|
|==**无锁并发编程**==|避免使用锁，减少线程阻塞和唤醒的次数|
|==**CAS 算法**==|使用硬件层面的原子操作，线程不会被阻塞，也就没有切换开销|
|==**合理设置线程数**==|线程数接近 CPU 核心数时切换最少|
|==**使用协程**==|协程在用户态切换，不涉及内核态，开销远小于线程|

#### 2. 死锁

锁是一个非常有用的工具，但如果使用不当——比如在锁中嵌套锁，或者因异常没有合理释放锁——就有可能引发死锁。一旦产生死锁，轻则系统功能阻塞，重则资源永远无法获取甚至系统宕机。

**解决方案**：

|策略|原理|
|---|---|
|==**避免一个线程同时获取多个锁**==|如果必须获取多个锁，统一所有线程的加锁顺序|
|==**避免一个线程在锁内同时占用多个资源**==|尽量保证每个锁只占用一个资源，缩小锁的粒度|
|==**使用定时锁代替内部锁**==|`Lock.tryLock(timeout)` 设置超时时间，超时放弃避免无限等待|
|==**加锁和解锁在同一个连接中**==|对于数据库锁，加锁和解锁必须在同一个数据库连接中完成|

#### 3. 资源限制的挑战

程序的执行受限于硬件资源（CPU 核心数、内存大小、磁盘 I/O 带宽）或软件资源（数据库连接数、Socket 连接数）。当资源有限时，创建过多线程不仅无法提升性能，反而会因为资源竞争导致线程饥饿、退化为串行执行、无效开销放大，最终吞吐量反而下降。

**解决方案**：

|策略|原理|
|---|---|
|==**使用线程池限制线程数**==|线程数匹配资源瓶颈，多余请求排队等待而非无限创建线程|
|==**使用协程/虚拟线程**==|轻量级用户态线程，资源开销远小于 OS 线程，适合 I/O 密集型高并发|
|==**异步非阻塞 I/O**==|一个线程同时处理多个 I/O 请求，不用阻塞等待每个请求完成|
|==**资源隔离**==|不同业务使用不同的资源池，避免核心业务与非核心业务互相影响|
|==**限流与降级**==|当请求超过资源承载能力时，拒绝多余请求或返回默认值，保护系统|

### 三、三大挑战知识体系总览
并发编程的三大挑战
├── [[上下文切换]]
│   ├── 成因：线程数超过 CPU 核心数，频繁保存/恢复线程状态
│   └── 解决：无锁并发、CAS、合理线程数、协程
│
├── [[死锁]]
│   ├── 成因：锁中嵌套锁、异常未释放锁
│   └── 解决：避免多锁、避免多资源、定时锁、统一加锁顺序
│
└── [[资源限制]]
    ├── 成因：硬件或软件资源有限，多线程抢占导致饥饿
    └── 解决：线程池、协程、异步I/O、资源隔离、限流降级

### 四、面试要点

**Q：多线程一定比单线程快吗？**

不一定。多线程的额外开销包括线程创建与销毁、上下文切换、锁竞争和资源等待。当这些开销的总和超过了并行执行带来的收益时，多线程反而更慢。任务执行时间极短、锁竞争激烈或资源受限时，单线程可能更优。

**Q：资源受限时应该怎么办？**

核心原则是：**与其让大量线程抢占资源导致全部瘫痪，不如让请求排队等待或快速失败**。具体策略包括使用线程池限制并发数量、使用协程减少线程开销、使用异步非阻塞 I/O 提高资源利用率、对不同业务做资源隔离，以及在负载过高时进行限流和降级。

**Q：上下文切换、死锁和资源限制这三者有关联吗？**

有。死锁会加剧上下文切换——线程在死锁状态下反复被唤醒、检查锁、再次阻塞，造成大量无效切换。资源限制会导致线程饥饿和频繁争抢，也会引发更多的上下文切换。三者的核心根源都是**对共享资源的无序竞争**，解决方案的共同思路都是**控制并发度、减少竞争**。
