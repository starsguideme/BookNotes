### 一、问题的本质

多线程并行的前提是有足够的硬件资源（CPU 核心、内存、I/O 带宽）和软件资源（数据库连接、文件句柄、锁）。当资源受限时：

- **CPU 核心数有限**：如果只有 4 核 CPU，100 个线程同时运行，同一时刻最多只有 4 个线程在真正并行，其余 96 个线程都在排队等待时间片。这 96 个线程的创建、切换、销毁开销都是白白浪费的。
    
- **外部资源有限**：比如数据库连接池只有 10 个连接，100 个线程同时请求数据库，90 个线程只能阻塞等待。多线程的并行效果被外部资源瓶颈完全抵消。
    
- **单线程比多线程更快的情况**：当每个任务执行时间极短且资源竞争激烈时，单线程按顺序执行 100 个任务的总耗时，可能少于多线程的创建、调度、上下文切换和资源等待的额外耗时之和。
    

### 二、表现形式

当资源受限时，多线程会出现以下问题：

| 表现             | 说明                                                |
| -------------- | ------------------------------------------------- |
| ==**线程饥饿**==   | 大量线程因无法获取资源而一直处于等待状态，始终得不到执行                      |
| ==**退化为串行**==  | 同一时刻只有一个线程能拿到资源，其他线程全部阻塞等待                        |
| ==**无效开销放大**== | 创建了 100 个线程，但同一时刻只有 1 个在工作，其余 99 个的创建和上下文切换开销全部浪费 |
| ==**吞吐量下降**==  | 操作系统花费大量 CPU 时间在调度和切换上，实际业务处理时间反而减少               |

### 三、解决方案

| 策略                 | 原理                          | 应用场景               |
| ------------------ | --------------------------- | ------------------ |
| ==**使用线程池限制线程数**== | 线程数匹配资源瓶颈，多余的请求排队等待         | 数据库连接池、Web 服务器线程池  |
| ==**使用协程/虚拟线程**==  | 轻量级用户态线程，不受 OS 线程数限制，资源开销更小 | 高并发 I/O 密集型任务      |
| ==**异步非阻塞 I/O**==  | 一个线程可以同时处理多个 I/O 请求，不用阻塞等待  | Netty、Redis 的事件循环  |
| ==**资源隔离**==       | 不同业务使用不同的资源池，互相不影响          | 核心业务与非核心业务使用不同的连接池 |
| ==**限流与降级**==      | 当请求超过资源承载能力时，拒绝多余请求或返回默认值   | 高并发系统的自我保护         |

**面试要点**：资源受限场景下的设计原则是——**与其创建大量线程抢占资源导致全部瘫痪，不如让请求排队等待或快速失败**。线程池的拒绝策略、`tryLock(timeout)` 的超时放弃、连接池的等待超时，都是这一原则的具体体现。
