

**独占式同步状态的获取与释放**

### 一、自旋等待：`acquireQueued` 方法

当节点成功地进入同步队列之后，就会陷入**自旋**的状态。每个线程或每个节点都在以自旋的方式等待获取同步状态的结果，一旦获取则会退出自旋，否则会一直自旋且会阻塞节点中的线程。

在 `acquireQueued` 中，当前线程虽然一直处于自旋状态，但仍然会尝试获取共享内存中的同步状态。但由于队列的特性，每次操作只能由**首节点**开始。只有首节点完成了获取与释放并唤醒了下一个节点，才能进行下一个节点的获取与释放。

这么做的原因大致有两个：

| 原因 | 说明 |
|------|------|
| ==**首节点完成获取与释放后，后继节点判断自己是否成为首节点**== | 如果是，则重复获取同步状态 |
| ==**满足队列的先进先出原则**== | 保证等待最久的线程优先获取锁 |

### 二、自旋等待的核心逻辑

```text
acquireQueued(node, arg) 的执行流程：
    ↓
① 获取当前节点的前驱节点 p
    ↓
② 如果 p 是头节点，尝试 tryAcquire(arg) 获取锁
    ↓
    ├── 成功 → 将当前节点设为新的头节点，原头节点出队，返回
    │
    └── 失败 → 执行 shouldParkAfterFailedAcquire(p, node)
              ↓
        ③ 检查前驱节点的 waitStatus
              ↓
              ├── SIGNAL → 执行 parkAndCheckInterrupt，阻塞当前线程
              │
              └── CANCELLED → 跳过取消的前驱节点，重新自旋
              │
              └── 其他状态 → CAS 将前驱节点设为 SIGNAL
```

### 三、队列的先进先出机制

```text
同步队列的 FIFO 工作流程：

初始状态：
head → Node1(持有锁) → Node2(等待) → Node3(等待) → null(tail)

Node1 释放锁，唤醒 Node2：
head → Node2(持有锁) → Node3(等待) → null(tail)

Node2 释放锁，唤醒 Node3：
head → Node3(持有锁) → null(tail)
```

由上图可得以下两点：

-   **队列中的节点与节点之间相互并不共享数据**，只做是否是首节点的判断。每个节点只关心自己的前驱节点是否是头节点，如果是则尝试获取锁。
-   **由于队列的特性，可以对过早的唤醒进行无效化处理**。当一个节点被唤醒时，它会检查自己的前驱节点是否是头节点。如果不是，说明它被过早唤醒了，它会继续自旋或阻塞，直到真正轮到自己。

### 四、独占式同步状态的获取与释放完整流程

```text
获取同步状态（acquire）：
    ↓
① tryAcquire(arg) —— 尝试获取锁
    ├── 成功 → 线程持有锁，返回
    │
    └── 失败 → addWaiter(Node.EXCLUSIVE)
              ↓
        ② 以互斥模式构建节点，CAS 加入队尾
              ↓
        ③ acquireQueued(node, arg)
              ↓
        ④ 自旋等待，前驱节点是头节点时尝试获取锁
              ↓
        ⑤ 获取失败 → 阻塞线程
              ↓
        ⑥ 被唤醒 → 继续自旋，直到成功获取锁


释放同步状态（release）：
    ↓
① tryRelease(arg) —— 尝试释放锁（由子类实现）
    ├── 失败 → 返回 false
    │
    └── 成功 → unparkSuccessor(head)
              ↓
        ② LockSupport.unpark() 唤醒后继节点中的线程
              ↓
        ③ 被唤醒的线程在 acquireQueued 中继续自旋，尝试获取锁
```

### 五、总结

由[[独占式同步状态的获取与释放]]与该文可以总结出以下观点：

-   **独占式同步状态中获取同步状态主要是在 AQS 这个队列上进行的**。当队列中的节点不是首节点的情况下会一直处于长期自旋的状态中。
-   **当首节点释放锁之后，会向后发起唤醒请求**，并结合队列的特性，让下一个节点判断自己是不是首节点。如果不是则无视该唤醒并依旧执行自旋的操作，否则重复首节点的操作。
-   **当线程释放锁的时候使用 `release` 方法**，在该方法中有个后续方法是 `unparkSuccessor`，而在该方法中会使用 `LockSupport` 方法来唤醒处于等待的线程。

### 六、面试要点

| 问题                    | 回答                                                         |
| --------------------- | ---------------------------------------------------------- |
| **`acquireQueued` 方法的作用** | 让节点以**自旋**方式等待获取锁，获取失败则阻塞线程                                |
| **为什么只能由首节点获取锁**          | ==**满足 FIFO 原则**==，保证等待最久的线程优先获取                           |
| **节点被唤醒后如何判断是否轮到自己**      | 检查前驱节点是否是**头节点**，不是则继续等待                                   |
| **释放锁时如何唤醒后继节点**          | `release()` → `unparkSuccessor()` → `LockSupport.unpark()` |
| **入队操作如何保证线程安全**          | 通过 ==**自旋 CAS**== 设置尾节点                                    |
