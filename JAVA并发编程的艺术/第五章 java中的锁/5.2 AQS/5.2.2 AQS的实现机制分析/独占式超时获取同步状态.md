


### 一、超时获取同步状态的方法

通过调用同步器的 `doAcquireNanos` 方法可以**超时获取同步状态**，即可以自定义时间去获取同步状态。此时如果获取到了同步状态会返回 `true`，否则返回 `false`。由于这种方法是在 [[Lock接口]] 下的，所以 `synchronized` 是无法进行这种精细化操作的。

### 二、中断处理的历史演进

要想知道为什么可以自定义去获取同步状态，首先得理解线程正在执行同步状态的获取时被中断后的情况：

**JDK 5 之前**：当一个线程因为获取不到锁而处于同步方法之外的时候，对这个线程进行中断操作时，该线程中的中断标识符会被修改。虽然被修改了，却依然无法进入同步状态，同时一直在尝试获取锁。

**JDK 5 之后**：为了解决这个问题，同步器提供了确保中断的方法，这个方法交给 JVM 自行处理。如果这个方法在等待获取同步状态时却被意外中断，会立刻返回并抛出中断异常。

而现在的超时获取同步状态在同步器的确保中断方法上进行了**升级**，不仅可以保留原有效果，还拥有了**超时获取**的特性。

### 三、超时时间的计算

超时操作需要手动操作，因此就需要对计算时间做出正确的判断。超时时间的计算方法为：

```text
timeout = now - lastTime
```

其中 `now` 为当前唤醒的时间，`lastTime` 为上次唤醒的时间。如果 `timeout` 大于 0 表示时间并未超时，会进入睡眠状态；否则会被唤醒。

### 四、`doAcquireNanos` 的执行流程

该方法在自旋过程中，当节点的前驱节点为头节点时会尝试获取同步状态，一旦获取成功则从该方法返回。这个过程与独占式和共享式的获取同步状态的成功方式类似，但在获取失败时却有所不同。

一旦获取失败，会进行以下判断：

| 情况 | 处理方式 |
|------|---------|
| ==**没有超时**== | 重新计算超时间隔，并让当前线程进入等待状态 |
| ==**已经超时或小于特定时间**== | 线程不会进入超时等待，而是进入**更高频率的自旋** |

**为什么超时或时间极短时进入高频自旋？**

因为在极短时间内的超时等待的结果并不精确。如果此时再次进入超时等待，会让超时等待从整体上表现得**很不精确**。为了解决这个问题，AQS 会让节点进入无条件的**更高频率自旋**，避免因等待粒度不精确导致超时判断失真。

### 五、`doAcquireNanos` 完整流程图

```text
doAcquireNanos(arg, nanosTimeout) 的执行流程：
    ↓
① 构建节点，CAS 加入队尾
    ↓
② 进入自旋
    ↓
③ 前驱节点是头节点时，尝试 tryAcquire(arg)
    ↓
    ├── 成功 → 将当前节点设为头节点，返回 true
    │
    └── 失败 → 计算剩余超时时间 nanosTimeout
              ↓
        ④ nanosTimeout ≤ 0？
              ↓
              ├── 是 → 超时，返回 false
              │
              └── 否 → nanosTimeout > spinForTimeoutThreshold(1000ns)？
                        ↓
                        ├── 是 → 进入睡眠等待（LockSupport.parkNanos）
                        │         ↓
                        │    被唤醒或超时后重新自旋
                        │
                        └── 否 → 进入高频自旋（不睡眠，继续循环尝试）
```

### 六、面试要点

| 问题                     | 回答                                       |
| ---------------------- | ---------------------------------------- |
| **超时获取同步状态的方法**            | ==**`doAcquireNanos`**==，可以自定义超时时间       |
| **超时时间如何计算**               | ==**`timeout = now - lastTime`**==，超时则唤醒 |
| **为什么超时或时间极短时进入高频自旋**      | 避免因等待粒度不精确导致超时判断失真                       |
| **`synchronized` 能超时获取锁吗** | ==**不能**==，这是 Lock 接口独有的精细化操作            |
| **JDK 5 前后中断处理的区别**        | JDK 5 之前中断后仍无法获取锁；JDK 5 之后中断会立刻返回并抛出异常   |
