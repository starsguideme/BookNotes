
### 一、读写锁的同步状态

由于读写锁同样依赖自定义同步器实现同步功能，所以读写锁的读写状态就是其同步器的同步状态。而且读写锁是 `ReentrantReadWriteLock` 接口下的一个锁，所以其同步状态会表示锁会被一个线程重复获取的同时，因此读写锁的自定义同步器就需要在同步状态上维护**多个读和一个写操作的同步状态**，这就是读写状态设计的重要性。

### 二、读写状态的位分割设计

由于需要在同一个整型变量上维护多种同步状态，就需要按存储空间将读写锁的变量分割成几份。在 32 位 JVM 上，一个完整的 32 位会被切割成一个**高 16 位**，一个**低 16 位**。

| 位段 | 含义 | 说明 |
|------|------|------|
| ==**高 16 位**== | 读锁状态 | 表示锁目前有多少个读操作（读锁被获取的次数） |
| ==**低 16 位**== | 写锁状态 | 表示写锁被获取的次数（写锁重入次数） |

```text
32 位 state 的位分割：

高 16 位（读锁状态）        低 16 位（写锁状态）
┌─────────────────────┬─────────────────────┐
│  读锁被获取的次数      │  写锁被获取的次数      │
│  (多个线程同时持有)     │  (写锁重入次数)       │
└─────────────────────┴─────────────────────┘
```

### 三、为什么要这样设计？

-   **读锁状态（高 16 位）**：需要记录**所有线程**获取读锁的总次数，因为在多个线程同时持有读锁时，每个线程都可以多次获取读锁（可重入）。释放时也需要根据这个计数来判断是否完全释放。
-   **写锁状态（低 16 位）**：只需要记录写锁被**当前持有者**重入的次数，因为同一时刻只有一个线程能持有写锁。

这种设计让读写锁可以通过**位运算**快速判断当前是否有读锁或写锁被持有，以及获取读锁或写锁的具体次数。

### 四、面试要点

| 问题             | 回答                                                  |
| -------------- | --------------------------------------------------- |
| **读写锁的同步状态如何设计**   | ==**高 16 位存读锁状态**==，==**低 16 位存写锁状态**==             |
| **为什么读锁状态用高 16 位** | 需要记录**所有线程**获取读锁的总次数                                |
| **为什么写锁状态用低 16 位** | 只需要记录**当前线程**对写锁的重入次数                               |
| **如何通过位运算判断锁状态**   | 通过 `state >>> 16` 获取读锁次数，通过 `state & 0xFFFF` 获取写锁次数 |
