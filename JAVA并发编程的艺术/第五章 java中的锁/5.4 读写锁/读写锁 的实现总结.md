### 一、核心知识体系
在理解 ReentrantReadWriteLock 的实现之前，就得知道[[读写状态的设计]]。该设计方案提供了将一个 32 位的 `state` 变量分成高 16 位和低 16 位，这样做的好处是方便计算读写锁中的读锁和写锁的数量，并以此进行下一步的判断。详细的 API 操作参考[[读写锁的接口与示例]]。

```text
ReentrantReadWriteLock 的实现体系：

读写状态的设计（state 高16位 + 低16位）
    ↓
├── 写锁（低16位）：互斥锁，同一时刻只有一个线程持有
│   └── [[写锁的释放与获取]]
│
├── 读锁（高16位）：共享锁，多个线程可以同时持有
│   └── [[读锁的获取与释放]]
│
└── 锁降级：写锁 → 读锁的不可逆转换
    └── [[锁降级]]
```

### 二、读写状态的设计

在该设计方案中，将一个 32 位的 `state` 变量分成高 16 位和低 16 位：

| 位段 | 含义 | 说明 |
|------|------|------|
| ==**高 16 位**== | 读锁状态 | 表示所有线程获取读锁的总次数 |
| ==**低 16 位**== | 写锁状态 | 表示写锁被获取的次数（写锁重入次数） |

### 三、写锁

写锁是一个**一般意义上的互斥锁**，详细参考[[写锁的释放与获取]]。该文章讲述了关于为什么写锁会阻塞其他线程获取锁的原因——**可见性问题**。写锁在持有期间，所有读线程和其他写线程都会被阻塞。

### 四、读锁

读锁是一个**支持重进入的非互斥锁**，详细参考[[读锁的获取与释放]]。读锁的生成前提是**写锁对其具有完全的可见性**。每个线程通过本地线程中的计数器来确认自己的读状态，但读锁的读状态的完整性是交给所有线程的读状态的总和来决定的。

**可一旦遇到了写锁并非是本地线程所持有的，且写锁却依然存在时，读锁是无法被获取到的**——这正是因为写锁是一个互斥锁，在读锁和写锁之间存在可见性依赖关系。

### 五、锁降级

为了解决读写之间的可见性问题，引申出一个关于读锁和写锁之间的关系机制——[[锁降级]]。锁降级的核心关键就是保证了线程之间的可见性，但锁降级是**不可逆**的，且只能由写锁变成读锁。

```text
锁降级的执行顺序：
① 获取写锁 → ② 获取读锁（在写锁持有期间） → ③ 释放写锁
```

### 六、面试要点

| 问题         | 回答                                      |
| ---------- | --------------------------------------- |
| **读写锁的状态如何设计** | ==**高 16 位存读锁状态**==，==**低 16 位存写锁状态**== |
| **读锁获取的前提条件**  | ==**写锁不存在**==，或写锁是当前线程持有（锁降级）           |
| **写锁为什么阻塞读操作** | ==**写锁必须对读锁可见**==                       |
| **锁降级的执行顺序**   | ==**获取写锁 → 获取读锁 → 释放写锁**==              |
| **锁降级为什么不可逆**  | 因为锁升级（读锁 → 写锁）会导致**死锁**                 |
