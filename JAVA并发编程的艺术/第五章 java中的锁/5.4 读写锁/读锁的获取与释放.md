
### 一、读锁的核心特性

读锁是可以支持**重进入**的共享锁，它能够被多个线程同时获取。在没有写锁的情况下，读锁一般都会成功获取，而获取读锁也只是**增加读状态**（高 16 位加 1）。

但如果当前线程在获取读锁之前就已经存在写锁，则读锁不会生效且会进入等待状态。这是因为读写锁的设计原则是**写锁必须对读锁可见**，所以在写锁持有期间，所有读线程都必须阻塞等待，直到写锁释放。

### 二、读锁状态的存储机制

读锁的读状态是根据**所有线程获得的读锁次数的总和**来判断的（存储在 `state` 的高 16 位）。但每个线程的读锁状态均由其**本地线程**来保存（通过 `ThreadLocal` 存储各自的重入次数）。

这样设计的原因是：读锁可以被多个线程同时持有，如果只靠高 16 位记录总次数，无法区分每个线程各自重入了多少次。因此需要 `ThreadLocal` 来记录每个线程自己的读锁重入次数，而高 16 位只记录全局总次数。

### 三、读锁的获取流程

```text
tryAcquireShared(arg) 获取读锁的流程：
    ↓
① 判断写锁是否存在（writeCount != 0）
    ↓
    ├── 写锁存在且不是当前线程持有 → 进入等待状态（写锁必须对读锁可见）
    │
    └── 写锁不存在 或 写锁是当前线程持有（锁降级）
              ↓
        ② CAS 增加读状态（高 16 位加 1），获取成功
              ↓
        ③ 通过 ThreadLocal 记录当前线程的读锁重入次数
```

### 四、读锁的释放

在释放的过程中，均会按照**线程安全的方式**减少读状态（高 16 位减 1）。由于可能有多个读锁一起释放，因此需要通过 **CAS** 来保证状态修改的原子性。

每个线程在释放读锁时，会先从 `ThreadLocal` 中获取自己的重入次数，减 1 后更新回 `ThreadLocal`，同时通过 CAS 将全局读状态（高 16 位）减 1。

### 五、面试要点

| 问题                | 回答                                                   |
| ----------------- | ---------------------------------------------------- |
| **读锁的核心特性**           | ==**可重入的共享锁**==，多个线程可以同时持有                           |
| **获取读锁时为什么要判断写锁是否存在** | ==**写锁必须对读锁可见**==，写锁存在时读线程必须等待                       |
| **读锁状态如何存储**          | 高 16 位存储**全局读锁总次数**，每个线程通过 **ThreadLocal** 存储各自的重入次数 |
| **读锁释放为什么需要 CAS**     | 可能有**多个读锁一起释放**，必须保证原子性                              |
| **锁降级时读锁能获取吗**        | ==**能**==，当写锁是当前线程持有时，允许同时获取读锁（锁降级）                  |
