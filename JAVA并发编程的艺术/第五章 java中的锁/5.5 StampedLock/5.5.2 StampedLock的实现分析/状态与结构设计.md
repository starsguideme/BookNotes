


### 一、为什么 StampedLock 没有使用 AQS？

快照锁没有选择使用 AQS 来实现，主要原因在于 AQS 无法满足快照锁对**状态**和**同步队列**的需求。

**从状态来看**：快照锁需要能够体现出**版本**概念的同步器。随着写锁的获取与释放，状态会随操作数一直自增，而通过自增的状态可以获取到锁的历史状态。如果状态能够像数据库表中的主 Key 一样提供唯一的约束，那么这个状态就可以以快照的方式给予获取锁的使用者。这个快照可以被用来和当前锁状态进行对比，以此来判断数据是否发生了更新。

但由于 AQS 这个同步器反映的是任意时刻锁的使用情况，不具备任意版本的概念，因此快照锁的状态需要使用新的同步组件。

**从同步队列来看**：AQS 对同步队列中的节点出队和入队以及运作方式都进行了极大的抽象。这种使用模板方法的好处是扩展成本低，但缺点是扩展后性能依然不高。在大多数情况下，程序虽然运行在多处理器环境下，但并发冲突并不是常态，所以不必要的资源浪费和上下文切换是 AQS 不适合快照锁的另一个原因。

### 二、StampedLock 的状态设计

因此 StampedLock 使用了名为 `state` 的 `long` 类型成员变量来维护锁的状态，其中**低 7 位**表示读，**第 8 位**表示写，其他更高位表示**版本号**。

```text
64 位 state 的位划分：

┌──────────────────────┬───────┬──────────────────────────┐
│      高 56 位         │ 第8位  │        低 7 位             │
│      (版本号)         │(写锁)  │       (读锁计数)           │
│  每次写操作 +1         │ 0/1    │   最多 127 个读线程        │
└──────────────────────┴───────┴──────────────────────────┘
```

**各字段的含义**：

| 字段 | 说明 |
|------|------|
| ==**低 7 位**== | 读锁计数，最多表示 127 个读线程 |
| ==**第 8 位**== | 写锁标志位，1 表示写锁被获取，0 表示不存在写锁 |
| ==**高 56 位**== | 版本号，每次写锁的获取与释放都会让版本号 +1 |

### 三、读锁计数的溢出处理

由于 2^7 最多只能容纳 128 个读线程，在高并发下会导致并发溢出。因此一旦超出了低 7 位的表示范围，StampedLock 会使用一个名为 `readerOverflow` 的 `int` 类型成员变量来保存溢出的读状态。

### 四、写锁的不支持重进入

因快照锁仅使用一位来表示写状态，所以不能像 AQS 实现读写锁那样，用一个 16 位数来表示写锁共获取了多少次。从这里就可以看出该锁**不支持重进入**的原因。

如果写锁被获取，第 8 位会被设置为 1。但写锁的释放不是简单地将第 8 位取反，而是让 `state` 加上 `WBITS`。这样不仅可以将第 8 位设置为 0，还可以**产生进位**，这会影响到高 56 位的值。也就是说**每次写锁的释放与获取都会让版本号 +1**，这也就是为什么快照锁可以判断当前锁状态的原因。

由此可以反推出：如果不同线程看到的版本号是一样的，那么在线程本地中被锁住的资源理应也是一样的。所以这就是**乐观锁运行的基础**。

### 五、StampedLock 的同步队列

状态能够表示锁的读写状态，但等待获取锁的读写请求如何排队，就需要同步队列来表示了。StampedLock 自定义了同步队列，该队列由自定义的 `WNode` 节点组成。该节点比 AQS 中的节点更复杂一点，它的属性与描述如下：

| 属性 | 说明 |
|------|------|
| ==**`prev`**== | 前驱节点指针 |
| ==**`next`**== | 后继节点指针 |
| ==**`cowait`**== | 将正在等待获取锁的读请求以**栈**方式分组排队 |
| ==**`thread`**== | 当前节点所代表的线程对象 |
| ==**`status`**== | 节点状态标志位 |
| ==**`mode`**== | 节点的模式（读/写） |

`WNode` 通过 `prev` 和 `next` 组成双向链表，而 `cowait` 会将正在等待获取锁的读请求以**栈**的形式进行分组排队。

StampedLock 通过 `whead` 和 `wtail` 分别指向同步队列的头节点和尾节点。头节点是由第一个未获取到锁而被阻塞的线程所创建的。

### 六、面试要点

| 问题                     | 回答                                       |
| ---------------------- | ---------------------------------------- |
| **为什么 StampedLock 不用 AQS** | AQS 不具备**版本号**概念，无法实现快照对比                |
| **StampedLock 的状态如何设计**    | 低 7 位读锁计数，第 8 位写锁标志，高 56 位**版本号**        |
| **为什么 StampedLock 不支持重进入** | 写锁只占 1 位，只能表示是否存在，无法记录重入次数               |
| **版本号如何自增**                | 每次写锁的获取与释放通过加上 `WBITS` 进位，使高 56 位 **+1** |
| **读锁溢出如何处理**               | 超出低 7 位范围时，使用 `readerOverflow` 变量保存溢出计数  |
| **`cowait` 的作用**           | 将等待获取读锁的请求以**栈**方式分组排队                   |
