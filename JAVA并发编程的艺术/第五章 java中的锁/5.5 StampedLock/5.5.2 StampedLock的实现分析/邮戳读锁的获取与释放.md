
### 一、读锁获取的核心机制

邮戳读锁和写锁的获取方式类似，可实现起来却要复杂得多。其主要限制于 **`cowait` 读栈**的存在，使得新加入队列中的读类型节点会根据尾节点的类型来实现不同的操作。

### 二、读类型节点入队逻辑

当存在节点 `node` 想要加入同步队列时，会先判断当前尾节点的类型：

| 尾节点类型 | 处理方式 |
|-----------|---------|
| ==**尾节点是读类型**== | 选择加入栈尾节点的 `cowait`（读栈） |
| ==**尾节点是写类型或其他**== | 将当前节点设置为同步队列的**尾节点** |

**进入读栈的节点**会成为栈顶节点的附属，它的状态随着栈顶节点的变化而变化。

**进入横向主队列的节点**会尝试自旋获取读锁。如果此时的前驱节点是头节点时，如果锁的状态仅存在读，则会设置为读状态。但如果此时的设置已经超出 `state` 低 7 位的上限，就需要让 **`readerOverflow`** 自增来保存溢出的读计数。

### 三、读锁释放的复杂性

邮戳锁中的读锁使用了 `state` 和 `readerOverflow` 两个变量来记录读状态，因此读锁的释放相比写锁要来得更复杂。

写锁由于其互斥性，可以导致其释放完之后就可以将锁交给另外的线程。但读锁在释放完之后必须进行判断，直到线程的读状态完全为 0（也就是 `state` 为 0 且 `readerOverflow` 也为 0）时，读锁才可以唤醒后继节点。

**释放读锁的流程**：

```text
① 判断当前状态的快照与先前传入的快照版本是否一致
    ↓
    ├── 不相同 → 说明有写操作发生，直接返回
    │
    └── 相同 → 执行自减操作
              ↓
        ② 判断是否是最后一个读锁
              ↓
              ├── 不是最后一个 → 继续自减，直到读状态变成 0
              │
              └── 是最后一个 → 释放锁，唤醒后继节点对应的线程
```

被唤醒的线程会执行其本身的逻辑，并尝试在队列中采用**自旋**的方式获取锁。

### 四、数据一致性的保证

邮戳锁为了防止状态和同步队列的头尾指针出现数据不一致的情况，在实现锁的获取与释放时，都会将相关数据拷贝到 **`ThreadLocal`** 中。

### 五、面试要点

| **问题**              | 回答                                         |
| --------------- | ------------------------------------------ |
| **读类型节点入队时如何判断**    | 根据尾节点类型：尾节点是读类型则加入 `cowait` 读栈，否则设为新的尾节点   |
| **读锁释放为什么比写锁复杂**    | 读锁需要判断所有读线程是否都已释放，直到 `state == 0` 才能唤醒后继节点 |
| **读锁计数溢出怎么处理**      | 超出低 7 位范围时，使用 `readerOverflow` 变量保存溢出计数    |
| **如何保证数据一致性**       | 在获取与释放锁时，将相关数据拷贝到 **`ThreadLocal`** 中      |
| **读栈节点和主队列节点有什么区别** | 读栈节点随栈顶节点状态变化；主队列节点通过自旋获取读锁                |
