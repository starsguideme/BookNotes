

**Condition 的等待机制**

### 一、`await()` 方法的核心流程

使用 `Condition` 的 `await` 为开头的方法时，会使当前线程进入等待队列并释放锁，同时线程状态变为**等待状态（WAITING）**。当从 `await()` 方法返回时，当前线程一定获取了与 `Condition` 相关联的锁。

### 二、从队列角度看等待过程

**从队列的角度来看**：当使用 `await()` 方法时，这就相当于在同步队列中的首节点（由于 FIFO 特性，首节点一定是获取了锁的节点）**移动**到 `Condition` 的等待队列中。

### 三、`await()` 的执行过程

使用该方法的线程如果成功地获取到了锁（通常情况下，这个线程一般都是同步队列的首节点），`await()` 方法会将当前线程构造成新的节点并加入到等待队列中，然后释放同步状态，尝试唤醒同步队列中的后继节点，最后使自己进入等待状态。

**如果后继节点被唤醒**：被唤醒的节点会尝试获取同步状态。但此时如果发现不是后继节点使用 `Condition.signal()` 来唤醒，而是**中断**了首节点的等待状态，则会抛出中断异常（`InterruptedException`）。

### 四、`await()` 的完整流程图

```text
await() 的执行流程：

① 当前线程已持有锁（是同步队列的首节点）
    ↓
② 调用 condition.await()
    ↓
③ 通过 addConditionWaiter() 将当前线程构造成新的节点
    ↓
④ 将新节点加入到 Condition 等待队列的尾部
    ↓
⑤ 释放同步状态（释放锁）
    ↓
⑥ 唤醒同步队列中的后继节点
    ↓
⑦ 当前线程进入等待状态（WAITING），等待被唤醒
    ↓
⑧ 被 signal() 唤醒 或 被中断
    ↓
    ├── 被 signal() 唤醒 → 重新竞争锁 → 获取锁后从 await() 返回
    │
    └── 被中断 → 抛出 InterruptedException
```

### 五、同步队列首节点不会直接加入等待队列

从队列的角度看，在当前线程加入到 `Condition` 的等待队列的过程中，同步队列的首节点并**不会直接加入**等待队列，而是通过 `addConditionWaiter()` 方法把当前线程构造成一个新的节点后，再将这个新节点加入到等待队列中。

**关键点**：同步队列中的节点和等待队列中的节点是**不同的节点实例**，只是它们都使用了 AQS 中同一个静态内部类 `Node`。`await()` 方法会构造一个新的节点，而不是将同步队列中的原节点移动到等待队列。

### 六、面试要点

| 问题                   | 回答                                                  |
| -------------------- | --------------------------------------------------- |
| **`await()` 方法执行后会发生什么** | 当前线程**释放锁**，构造成新节点加入等待队列，进入 **WAITING** 状态          |
| **从 `await()` 返回的前提是什么** | 必须被 `signal()` 唤醒并**重新获取锁**                         |
| **同步队列首节点会直接加入等待队列吗**    | ==**不会**==，通过 `addConditionWaiter()` 构造**新的节点**后再加入 |
| **被中断唤醒时会怎样**            | 抛出 **`InterruptedException`**                       |
| **`await()` 释放锁后会做什么**   | 唤醒同步队列中的**后继节点**                                    |
