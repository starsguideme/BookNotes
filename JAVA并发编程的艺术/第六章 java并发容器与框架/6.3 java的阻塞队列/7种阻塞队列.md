

**阻塞队列**

### 一、核心概念

阻塞队列是一个支持两个附加操作的队列，这两个附加操作支持**阻塞的插入和移除方法**。

| 附加操作 | 说明 |
|---------|------|
| ==**支持阻塞的插入方法**== | 当队列已满时，队列会阻塞插入元素的线程，直到队列不满 |
| ==**支持阻塞的移除方法**== | 当队列为空时，获取元素的线程会等待队列变为非空 |

阻塞队列常用于**生产者与消费者**的场景。生产者是向队列里添加元素的写线程，消费者是从队列取元素的读线程。因此生产者用来存放元素，消费者用来获取元素，队列就是它们之间的容器。

### 二、四种处理方式

| 处理方式 | 插入方法 | 移除方法 | 检查方法 |
|---------|---------|---------|---------|
| ==**抛出异常**== | `add(e)` | `remove()` | `element()` |
| ==**返回特殊值**== | `offer(e)` 返回 `true/false` | `poll()` 返回元素或 `null` | `peek()` 返回元素或 `null` |
| ==**一直阻塞**== | `put(e)` | `take()` | 不可用 |
| ==**超时退出**== | `offer(e, time, unit)` | `poll(time, unit)` | 不可用 |

### 三、JDK 7 常用阻塞队列

| 队列 | 数据结构 | 有界/无界 | 核心特点 | 适用场景 |
|------|---------|----------|---------|---------|
| ==**ArrayBlockingQueue**== | 数组 | 有界 | FIFO，公平性可配置，默认非公平 | 需要固定容量、防止内存溢出的场景 |
| ==**LinkedBlockingQueue**== | 链表 | 有界（默认 `Integer.MAX_VALUE`） | FIFO，吞吐量较高 | 容量需求大但不需要严格控制上限的场景 |
| ==**PriorityBlockingQueue**== | 数组（堆） | 无界 | 按优先级排序，支持自定义排序规则 | 需要按优先级处理任务的场景，如 VIP 任务队列 |
| ==**DelayQueue**== | `PriorityQueue` | 无界 | 元素需实现 `Delayed` 接口，支持延时获取 | 缓存超时清理、定时任务调度 |
| ==**SynchronousQueue**== | 无内部结构 | 无容量 | 每个 `put` 必须等一个 `take`，线程间直接传递数据 | 线程间快速传递任务，如 Netty EventLoop |
| ==**LinkedTransferQueue**== | 链表 | 无界 | 支持 `transfer` 和 `tryTransfer` 方法 | 需要即时传递数据或等待消费者的场景 |
| ==**LinkedBlockingDeque**== | 链表 | 双向 | 支持双端插入和移除，减少多线程竞争 | 需要双端操作的场景，如工作窃取 |

### 四、各队列详解

**1. ArrayBlockingQueue**

一个由数组结构组成的有界阻塞队列，严格按照 FIFO 的原则对队列中的元素进行排序。默认情况下，该队列不保证线程进行**公平**的访问队列。

所谓**公平访问队列**指的是阻塞的线程可以按照阻塞的先后顺序访问队列，即谁排在前面就是谁先访问线程。**非公平性**指的是对先等待的线程是非公平的，当队列可用时，阻塞的线程都可以争夺访问队列的资格，可能先阻塞的线程最后访问队列。为了保证公平性，一般情况下会降低吞吐量。

**综上所述，这个队列中的锁应该就是公平锁**——当 `fair=true` 时使用公平锁，保证先等待的线程先获取资源。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**需要固定容量的场景**== | 防止队列无限增长导致内存溢出 |
| ==**需要公平调度的场景**== | 设置为公平模式，保证先等待的线程先获取资源 |
| ==**生产与消费速率匹配的场景**== | 队列满了就阻塞生产者，避免资源浪费 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**容量需求不确定的场景**== | 固定容量可能成为瓶颈，此时应使用 `LinkedBlockingQueue` |
| ==**需要极高吞吐量的场景**== | 一把锁的设计导致吞吐量低于 `LinkedBlockingQueue` |

**2. LinkedBlockingQueue**

一个由链表结构组成的有界阻塞队列，此队列的默认最大长度是 `Integer.MAX_VALUE`（即 2^31 - 1），并按照 FIFO 的原则对元素进行排序。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**吞吐量要求高的场景**== | 使用两把锁（`putLock` 和 `takeLock`），生产和消费可同时进行 |
| ==**容量需求大但不严格限制的场景**== | 默认 `Integer.MAX_VALUE`，适合大多数缓存队列场景 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**需要严格容量限制的场景**== | 可能撑满内存，此时应使用 `ArrayBlockingQueue` |
| ==**需要公平调度的场景**== | 不支持公平性配置 |

**3. PriorityBlockingQueue**

一个支持优先级排序的无界阻塞队列。默认情况下元素会使用**自然顺序**进行升序排序，也可以自定义 `compareTo()` 方法来指定元素排序规则，也可以在初始化 `PriorityBlockingQueue` 时，指定修改参数 `Comparator` 来对元素进行自定义排序。

**但这不可以适用于同优先级的元素**——对于同优先级的元素，系统可能按照线程优先级或其他策略来处理。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**需要按优先级处理任务的场景**== | 如 VIP 用户请求优先处理，紧急任务优先执行 |
| ==**需要自定义排序规则的场景**== | 通过 `Comparator` 灵活定义排序策略 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**需要严格容量控制的场景**== | 无界队列可能导致内存溢出 |
| ==**对 FIFO 有严格要求的场景**== | 优先级队列不保证 FIFO 顺序 |

**4. DelayQueue**

是一个支持延时元素的无界阻塞队列。队列可以使用 `PriorityQueue` 来实现，但队列中的元素必须实现 `Delayed` 接口。在创建元素时需要指定超时时间后才能从队列中获取当前元素，而且**只有在延迟期满时**才可以从队列中提取元素。

**常用使用场景**：

| 场景 | 说明 |
|------|------|
| ==**缓存系统的设计**== | 用 `DelayQueue` 保存缓存元素的有效期。当尝试使用一个线程来循环查询 `DelayQueue` 时，一旦能获取到数据，则说明缓存时间已经到期，需要进行缓存失效处理 |
| ==**定时任务调度**== | 使用 `DelayQueue` 保存当天将会保存执行的任务和执行时间，一旦从 `DelayQueue` 中获取到的任务就开始执行。`TimerQueue` 的底层就是由 `DelayQueue` 来实现的 |

**实现 DelayQueue 接口的步骤**：

| 步骤 | 说明 |
|------|------|
| ==**第一步**== | 在初始化数据元素时，通过设定时间来规定当前对象大致在什么时候进行初始化。使用 `Delayed` 中的 `sequenceNumber` 来标识元素在队列中的先后顺序 |
| ==**第二步**== | 实现 `getDelay` 方法，返回当前元素还需要延时多久，单位是**纳秒**。如果 `time` 小于当前真实时间，`getDelay` 返回**负数** |
| ==**第三步**== | 实现 `compareTo` 方法来指定元素的顺序 |

**如何实现延时阻塞队列**：当消费者从队列获取元素时，如果元素没有达到延时时间，就会阻塞当前线程。

**关于"缓存失效时获取数据"的疑问**：`DelayQueue` 中的元素在到达延时时间后会**自动失效**，此时消费者可以通过 `take()` 或 `poll()` 获取到已失效的元素。所以**缓存到期后能获取到数据是正常的**——获取到的就是那个已经到期、需要进行清理或更新的缓存元素。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**缓存超时清理**== | 将缓存元素放入 `DelayQueue`，超时后自动清理 |
| ==**定时任务调度**== | 如 `TimerQueue` 的底层实现 |
| ==**订单超时取消**== | 将订单放入队列，超时后自动取消 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**需要高精度定时的场景**== | `DelayQueue` 基于 `PriorityQueue`，定时精度受限于纳秒级 |
| ==**需要严格容量控制的场景**== | 无界队列可能导致内存溢出 |

**5. SynchronousQueue**

一个**不存储元素**的阻塞队列。每一个 `put` 操作之前必须等待一个 `take` 操作，否则不能增加元素。它支持公平访问队列，默认情况下线程会使用**非公平性策略**访问队列。使用构造方法 `new SynchronousQueue(true)` 可以创建公平访问的 `SynchronousQueue`，等待的线程会采用**先进先出**的顺序访问队列。

`SynchronousQueue` 的作用是将生产者线程产生的数据**直接传递**给消费者线程，但队列本身是**无法存储任何元素**的。因为这个特性，它一般是用于**线程之间的快速数据传递**。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**线程间快速传递任务**== | 如 Netty EventLoop 内部的任务传递 |
| ==**高性能 RPC 框架的内部通信**== | 需要低延迟的线程间数据交换 |
| ==**需要严格同步的场景**== | 生产者必须等待消费者消费后才能继续 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**需要消息持久化的场景**== | 队列不存储元素，一旦宕机数据全部丢失 |
| ==**生产者与消费者速率不匹配的场景**== | 速率不匹配会导致生产者一直被阻塞 |

**6. LinkedTransferQueue**

一个由链表结构组成的无界阻塞队列。相对于其他阻塞队列，`LinkedTransferQueue` 多了 `transfer` 和 `tryTransfer` 方法。

| 方法 | 说明 |
|------|------|
| ==**`transfer(E e)`**== | 如果当前有消费者正在等待获取元素，`transfer` 方法会把生产者生产的数据**直接转发**给消费者。如果此时没有消费者在等待接收元素时，`transfer` 方法会将元素存放在队列的 `tail` 节点后，等待被消费者消耗掉，并返回该数据 |
| ==**`tryTransfer(E e)`**== | 用于判断生产者传入的元素能否**直接传递给**消费者。如果没有消费者正在等待接收元素，则返回 `false`。和 `transfer` 的区别在于：无论消费者是否接收，`tryTransfer` 方法都会**立即返回**，而 `transfer` 方法必须等到消费者消费了才返回 |
| ==**`tryTransfer(E e, long timeout, TimeUnit unit)`**== | 带超时的尝试传递。如果过了时间依旧没有消费者损耗数据，则返回 `false`，否则返回 `true` |

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**需要即时传递数据的场景**== | 用 `tryTransfer` 判断是否有消费者等待，如果有则直接传递 |
| ==**需要等待消费者确认的场景**== | 用 `transfer` 确保数据被消费后才返回 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**对吞吐量要求极高的场景**== | `transfer` 的阻塞等待机制可能影响吞吐量 |
| ==**需要严格容量控制的场景**== | 无界队列可能导致内存溢出 |

**7. LinkedBlockingDeque**

一个由链表结构组成的**双向阻塞队列**。所谓的双向队列是指可以从队列的**双端插入和移除元素**。因为多了一个操作队列的入口，所以在多线程下如果数据同时入队，因此也就**减少了一半的竞争**。相比于其他的线程阻塞队列，`LinkedBlockingDeque` 多了 `addFirst`、`addLast`、`offerFirst`、`offerLast` 等各种双端操作方法。

**适用范围**：

| 适用场景 | 说明 |
|---------|------|
| ==**需要双端操作的场景**== | 如工作窃取算法，可以从队列两端分别操作 |
| ==**需要减少竞争的场景**== | 双端设计使得生产和消费可以操作不同端，减少锁竞争 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**只需要单端操作的场景**== | 使用 `LinkedBlockingQueue` 即可，不需要双端操作的额外复杂度 |

### 五、面试要点

| 问题                                           | 回答                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------- |
| **阻塞队列的四种处理方式**                                  | ==**抛出异常、返回特殊值、一直阻塞、超时退出**==                                                          |
| **ArrayBlockingQueue 和 LinkedBlockingQueue 的区别** | ArrayBlockingQueue 基于数组，有界，一把锁；LinkedBlockingQueue 基于链表，默认有界（`Integer.MAX_VALUE`），两把锁 |
| **DelayQueue 的实现原理**                             | 基于 `PriorityQueue`，元素需实现 `Delayed` 接口，通过 `getDelay` 判断是否到期                            |
| **SynchronousQueue 的特点**                         | ==**不存储元素**==，每个 `put` 必须等一个 `take`，用于线程间直接传递数据                                       |
| **LinkedTransferQueue 的 transfer 方法**            | 有消费者直接传递，无消费者则存入队列等待，直到被消费才返回                                                         |
