

**阻塞队列的通知模式**

### 一、通知模式的核心流程

如果队列是空的，消费者会一直处于等待。当生产者添加元素时，会使用**通知模式**来实现——当生产者向**满的队列**里添加元素时会阻塞生产者，可当消费者消费了一个队列中的元素后，会通知生产者当前队列可用。

在源码中会使用 `Unsafe.park()` 这个本地方法，`park` 方法会阻塞当前线程，但遇到以下 **4 种情况**会使该方法返回：

| 情况                                     | 说明                                                                                        |
| -------------------------------------- | ----------------------------------------------------------------------------------------- |
| ==**与 `park` 对应的 `unpark` 已执行或正在执行**== | 这里"先执行 `unpark` 后执行 `park`"的情况是允许的——`unpark` 可以先于 `park` 调用，相当于提前发放了"通行证"，后续 `park` 会直接返回 |
| ==**线程被中断**==                          | 当其他线程调用了当前线程的 `interrupt()` 方法时，`park` 会响应中断并返回                                           |
| ==**等待时间超时**==                         | 如果使用了带超时的 `parkNanos` 或 `parkUntil`，时间到了会返回                                               |
| ==**虚假唤醒**==                           | 由于操作系统层面的原因，`park` 可能在没有任何原因的情况下意外返回，这就是"虚假唤醒"，所以需要在 `while` 循环中反复检查条件                    |

### 二、通知模式的完整流程图

```text
消费者等待流程：
① 消费者尝试从队列获取元素
    ↓
② 队列为空 → 调用 park() 阻塞当前线程
    ↓
③ 消费者线程处于 WAITING 状态，等待被唤醒


生产者通知流程：
① 生产者向队列添加元素
    ↓
② 添加成功后 → 调用 unpark() 唤醒等待的消费者线程
    ↓
③ 被唤醒的消费者线程从 park() 返回
    ↓
④ 消费者重新尝试获取元素
    ↓
⑤ 成功获取元素，继续执行
```

### 三、为什么要用 `while` 循环检查条件？

由于 `park()` 可能因为**虚假唤醒**而意外返回，所以被唤醒的线程不能直接认为队列一定有元素可用。必须在 `while` 循环中反复检查条件（队列是否为空），如果条件仍不满足，就再次调用 `park()` 进入等待。这和 `wait()` 必须在 `while` 循环中使用是同一个道理。

### 四、面试要点

| **问题**                       | 回答                                                  |
| ------------------------ | --------------------------------------------------- |
| **阻塞队列的通知模式是什么**             | 消费者在队列为空时 **`park` 阻塞**，生产者添加元素后 **`unpark` 唤醒**消费者 |
| **`park` 方法可能因为哪些情况返回**      | ==**unpark 已执行、线程被中断、超时、虚假唤醒**==                    |
| **为什么要用 `while` 循环检查条件**     | 防止**虚假唤醒**导致线程在条件不满足时继续执行                           |
| **`unpark` 可以先于 `park` 执行吗** | ==**可以**==，相当于提前发放"通行证"，后续 `park` 会直接返回             |
