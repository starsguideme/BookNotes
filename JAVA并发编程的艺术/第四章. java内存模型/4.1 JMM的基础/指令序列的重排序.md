### 一、什么是重排序

为了提高性能，编译器和处理器往往会对指令进行**重排序**。重排序分为三种类型：

|类型|执行者|说明|
|---|---|---|
|==**编译器优化重排序**==|编译器|在不改变**单线程**语义的前提下，调整语句的执行顺序|
|==**指令级并行重排序**==|处理器|使用指令级并行技术重叠执行多条指令，如果不存在**数据依赖性**，处理器可以改变指令的执行顺序|
|==**内存系统重排序**==|处理器|由于 CPU 使用了缓存和读/写缓冲区，使得加载和存储操作看上去可能是乱序执行|

### 二、重排序在 Java 中的执行顺序

Java 代码从编写到最终执行，会经历三种重排序：


**源代码**
    **↓**
**① 编译器优化重排序（软件层面）**
    **↓**
**② 指令级并行重排序（硬件层面）**
    **↓**
**③ 内存系统重排序（硬件层面）**
    **↓**
**最终执行的指令序列**

第①种是**软件层面**的，由编译器完成；第②和第③种是**硬件层面**的，由处理器完成。这些优化在单线程环境下不会影响程序的正确性，但在多线程环境下可能导致可见性问题——一个线程对共享变量的修改，另一个线程可能因为指令重排序而看不到。

### 三、数据依赖性

重排序的核心约束是**数据依赖性**。如果两条指令之间存在数据依赖，它们就不能被重排序：

|依赖类型|示例|说明|
|---|---|---|
|==**写后读**==|`a = 1; b = a;`|必须先写 `a`，再读 `a`|
|==**写后写**==|`a = 1; a = 2;`|两次写入的顺序决定最终结果|
|==**读后写**==|`b = a; a = 1;`|必须先读 `a` 的旧值，再写 `a`|

存在数据依赖关系的两条指令**不能被重排序**，否则单线程下的执行结果就会发生变化。

### 四、JMM 如何解决重排序问题

JMM 提供了四种**内存屏障**来禁止特定类型的重排序：

| 屏障类型                  | 作用                                       |
| --------------------- | ---------------------------------------- |
| ==**LoadLoad 屏障**==   | 确保 Load1 的数据装载先于 Load2 及后续所有装载指令         |
| ==**StoreStore 屏障**== | 确保 Store1 的数据对其他处理器可见，先于 Store2 及后续存储指令  |
| ==**LoadStore 屏障**==  | 确保 Load1 的数据装载先于 Store2 及后续所有存储指令        |
| ==**StoreLoad 屏障**==  | 确保 Store1 的数据对其他处理器可见，先于 Load2 及后续所有装载指令 |

`volatile` 变量就是通过插入这些内存屏障来实现可见性和禁止指令重排的。不仅内存屏障可以分为这四类，其中并发模型也可以分为以下几类:[[并发编程的模型]]
### 五、as-if-serial 语义

**as-if-serial** 语义规定：不管怎么重排序，单线程程序的执行结果不能被改变。编译器、处理器和运行时都必须遵守这个语义。也就是说，单线程环境下重排序对程序行为不会有任何影响，因此程序员察觉不到重排序的存在。

但在多线程环境下，as-if-serial 语义只在单个线程内成立，跨线程的可见性问题只能通过同步机制（`volatile`、`synchronized`、`Lock` 等）来解决。

### 六、面试要点

| 问题                 | 回答                                           |
| ------------------ | -------------------------------------------- |
| 重排序有哪三种类型          | 编译器优化重排序、指令级并行重排序、内存系统重排序                    |
| 重排序会导致什么问题         | 多线程环境下的可见性问题——一个线程修改了共享变量，另一个线程因为重排序看不到最新值   |
| 如何禁止重排序            | 使用 `volatile`（插入内存屏障）或 `synchronized`（锁内存语义） |
| as-if-serial 语义的含义 | 不管怎么重排序，单线程程序的执行结果不能被改变                      |
