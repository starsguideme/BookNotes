

**Java内存模型总结**

### 一、核心框架

本章主要讲述了Java内存模型（JMM）的核心知识，包括但不限于核心规则——**先行发生原则**（happens-before），重排序规则，以及各关键字中的内存屏障机制。这些关键字包括但不限于 `volatile`、`synchronized`、`final` 等，每个关键字都有其只属于自己的特殊含义。

整个JMM的体系结构可以概括为：

```text
先行发生原则（happens-before）
    ↓ 提供理论基础
内存屏障（LoadLoad、StoreStore、LoadStore、StoreLoad）
    ↓ 提供底层实现
volatile / synchronized / final
    ↓ 面向开发者
线程安全的并发程序
```

先行发生原则是JMM的**理论基础**，内存屏障是JMM的**底层实现机制**，而 `volatile`、`synchronized`、`final` 等关键字则是JMM面向开发者提供的**具体工具**。

### 二、volatile

`volatile` 有读、读-写、写-读等特殊的内存语义，其主要功能是解决**可见性**问题。`volatile` 的写操作与锁的释放具有相同的内存语义，`volatile` 的读操作与锁的获取具有相同的内存语义。

`volatile` 结合先行发生原则中的**volatile变量规则**（volatile写 happens-before volatile读），以及**传递性规则**，建立起跨线程的可见性保证。同时，`volatile` 通过**内存屏障**（特别是写操作后的StoreLoad屏障）来禁止指令重排序，以此完成**有序性**。

具体参考：[[volatile的实现原则]]与[[volatile内存语义的实现]]

### 三、synchronized

`synchronized` 是一种同步机制，通过向处理器发送一条Lock前缀的指令，以此完成**互斥锁**的机制。它将多线程操作变为单线程串行执行，以此实现**原子性**。

同时，`synchronized` 的释放锁和获取锁在内存语义上等价于 `volatile` 的写和读——释放锁时将工作内存中的修改刷新到主内存，获取锁时从主内存重新读取最新值。因此 `synchronized` 也可以完成**可见性**。此外，`synchronized` 通过先行发生原则中的**监视器锁规则**（释放锁 happens-before 获取锁），保证**有序性**。

`synchronized` 的特性主要参考：[[Synchronized总结]]

### 四、final

`final` 也有其特殊的功能，主要用于在完成类的初始化时一次性确定该类/对象是否可以被访问。`final` 域的重排序规则保证了：只要对象正确构造完成（没有this逃逸），其他线程就能看到 `final` 域在构造函数中被正确初始化的值，不需要额外的同步机制。

具体实现上，`final` 的写操作通过**StoreStore屏障**禁止重排序到构造函数之外，`final` 的读操作通过**LoadLoad屏障**禁止与读对象引用之间的重排序。

`final` 参考：[[final的具体实现]]

### 五、先行发生原则是基础

以上是关键字的作用，这些关键字的实现都依赖于**先行发生原则**。如果没有这个原则，关键字的实现就无从谈起：

| 关键字                  | 依赖的happens-before规则                      |
| -------------------- | ---------------------------------------- |
| ==**volatile**==     | volatile写 happens-before volatile读 + 传递性 |
| ==**synchronized**== | 释放锁 happens-before 获取锁                   |
| ==**final**==        | 构造函数完成 happens-before 对象被访问              |

要想深入理解先行发生原则，就需要参考：[[happens-before规则]]

### 六、三大关键字对比

| 维度            | volatile          | synchronized      | final                      |
| ------------- | ----------------- | ----------------- | -------------------------- |
| ==**保证可见性**== | ✅                 | ✅                 | ✅（仅构造完成后）                  |
| ==**保证原子性**== | ❌（仅单次读写）          | ✅（整个临界区）          | ❌                          |
| ==**保证有序性**== | ✅（内存屏障）           | ✅（happens-before） | ✅（StoreStore + LoadLoad屏障） |
| ==**底层机制**==  | Lock前缀指令 + MESI协议 | Monitor + 锁升级     | StoreStore + LoadLoad屏障    |
| ==**核心作用**==  | 轻量级同步，状态标志位       | 重量级互斥，保护临界区       | 初始化安全，不可变对象                |
| ==**性能开销**==  | 低（无上下文切换）         | 较高（涉及上下文切换）       | 极低（无运行时开销）                 |

### 七、面试要点

| 问题                                | 回答                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------ |
| **JMM的核心规则是什么**                       | ==**先行发生原则（happens-before）**==，所有关键字的实现都依赖于它                                   |
| **volatile、synchronized、final各自保证什么** | volatile保证可见性+有序性+单次读写原子性，synchronized保证原子性+可见性+有序性，final保证初始化安全               |
| **volatile和synchronized的底层实现区别**      | volatile依赖Lock前缀指令+内存屏障，synchronized依赖Monitor+锁升级                              |
| **final如何保证初始化安全**                    | ==**StoreStore屏障**==禁止写重排序到构造函数外，==**LoadLoad屏障**==禁止读与读引用之间的重排序               |
| **三个关键字的内存语义有何异同**                    | volatile写=synchronized释放锁，volatile读=synchronized获取锁；final只在构造完成时保证可见性，不需要运行时同步 |
