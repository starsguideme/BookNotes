### 一、volatile 的局限性

由 volatile 的特性得知，volatile 无法同时对多个 volatile 变量进行**原子操作**，也无法保证对复合操作（如 `count++`）的原子性。

### 二、volatile 的内存语义

从 JDK 5 开始，volatile 的内存语义得到了增强。对 volatile 变量的**写操作**和**读操作**可以实现线程之间的通信。

从内存语义的角度来看，被 volatile 修饰的变量在以下操作上具有与同步锁等效的内存语义：

|操作类型|内存语义|
|---|---|
|==**volatile 写**==|与释放锁（`monitorexit`）具有相同的内存语义|
|==**volatile 读**==|与获取锁（`monitorenter`）具有相同的内存语义|

这意味着：**[[volatile 写与读操作的内存语义]]与[[锁的释放-获取的内存语义]]完全等效。**

### 三、volatile 如何保证有序性和可见性

当 volatile 操作与 [[happens-before规则]]结合时：

- **volatile 写** happens-before 于后续对这个 volatile 变量的**读**。
    
- 根据 happens-before 的**传递性**，volatile 写之前的所有操作的结果，对 volatile 读之后的所有操作可见。
    

这就使得线程的执行顺序像顺序一致性内存模型一样，变得具有**有序性**。同时根据 volatile 的可见性特性，线程之间也相互可见。
**volatile 写（释放语义）**
    **↓ happens-before**
**volatile 读（获取语义）**
    **↓ 传递性**
**写之前的操作 → 对 → 读之后的操作可见**

### 四、volatile 写-读与锁的内存语义对比

| 维度        | volatile 写-读        | synchronized     |
| --------- | ------------------- | ---------------- |
| **写操作语义** | 与 `monitorexit` 等效  | 释放锁时刷回主内存        |
| **读操作语义** | 与 `monitorenter` 等效 | 获取锁时从主内存重新读取     |
| **可见性保证** | 写之前的所有操作对读之后的操作可见   | 释放锁前的所有修改对获取锁后可见 |
| **原子性保证** | 不保证复合操作的原子性         | 保证整个同步块的原子性      |
|           |                     |                  |

### 五、面试要点

| 问题                | 回答                                |
| ----------------- | --------------------------------- |
| **volatile 的内存语义是什么** | volatile 写与释放锁等效，volatile 读与获取锁等效 |
| **volatile 如何保证有序性**  | 通过 happens-before 规则禁止指令重排，保证执行顺序 |
| **volatile 能替代锁吗**    | 不能，volatile 不能保证复合操作的原子性          |
