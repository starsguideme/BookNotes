### 一、AQS 的核心机制

锁的具体实现依赖于 **AQS（AbstractQueuedSynchronizer，抽象队列同步器）**。在 AQS 中不仅**封装了 [[CAS]]**，还使用 volatile 修饰的 `state` 变量来维护**同步状态**。

AQS 的核心组成：

| 组件                           | 说明                              |
| ---------------------------- | ------------------------------- |
| ==**`volatile int state`**== | 同步状态，0 表示锁空闲，大于 0 表示锁被持有（可重入次数） |
| ==**CAS**==                  | 原子地修改 `state` 的值，保证只有一个线程能成功获取锁 |
| ==**CLH 同步队列**==             | 获取锁失败的线程被封装成节点，加入队列尾部并阻塞等待      |

其中 volatile 是实现锁方法的关键——`state` 的可见性通过 volatile 保证，`state` 的原子修改通过 CAS 保证。两者配合才构成了完整的锁机制。

### 二、公平锁的加锁流程

在使用公平锁进行加锁处理时：

1. 优先读取 volatile 的 `state` 变量，根据状态变量的值来判断锁是否空闲。
    
2. 如果 `state == 0`（锁空闲），先检查同步队列中是否有等待时间更长的线程（这是公平性的核心体现）。如果没有更早等待的线程，则通过 CAS 将 `state` 从 0 改为 1，修改成功后当前线程持有锁。
    
3. 如果 `state > 0`（锁已被持有），检查当前线程是否是锁的持有者。如果是，可重入地将 `state` 的值加 1（重入次数增加）。如果不是，则加锁失败，当前线程被封装成节点加入同步队列尾部，进入阻塞等待。
    

### 三、公平锁的解锁流程

在使用公平锁进行解锁处理时：

1. 每次解锁将 `state` 的值减 1（重入次数减少）。
    
2. 当 `state == 0` 时，表示锁完全释放。如果当前线程不是锁的持有者，会抛出 `IllegalMonitorStateException`。
    
3. 锁释放后，唤醒同步队列中的下一个等待线程，让它重新竞争锁。
    

### 四、CAS 的 volatile 内存语义

在 AQS 的 `compareAndSetState` 方法中，CAS 通过原子操作更新 `state` 变量。该操作同时具有 volatile 读和 volatile 写的内存语义——既能保证 `state` 的修改对其他线程立即可见，又能保证 `state` 修改前后的指令不会被重排序。

由于无法对 volatile 读与 volatile 读后面的任意内存操作进行重排序，也无法对 volatile 写与 volatile 写进行重排序，因此编译器在处理连续的 CAS 操作时，不会执行任意的指令重排序，保证了同步状态的一致性。

### 五、Lock 前缀指令的特点

程序会根据当前处理器的类型来决定是否添加 Lock 前缀。处于多线程竞争时就会有这个 Lock 前缀。以下是 Lock 前缀的特点：

1. **保证原子性**：根据处理器的不同，采用缓存锁定或总线锁定来保证指令执行的原子性，并以此降低开销。
    
2. **禁止重排序**：禁止这条指令与其之前和之后的读写指令进行重排序。
    
3. **刷新写缓冲区**：将写缓冲区中的所有数据刷新到内存中。
    

### 六、公平锁与非公平锁的重要区别

非公平锁的实现与公平锁类似，但有一个重要区别：非公平锁在调用 `lock()` 时，**先直接通过 CAS 尝试获取锁**，不检查同步队列中是否有等待时间更长的线程。如果 CAS 成功则持有锁，失败则走正常排队流程。

| 对比维度              | 公平锁            | 非公平锁            |
| ----------------- | -------------- | --------------- |
| ==**获取锁的顺序**==    | 按请求的先后顺序（FIFO） | 不保证顺序，新线程可能插队   |
| ==**首次 CAS 尝试**== | 不直接尝试，先检查队列    | 直接 CAS 尝试，不检查队列 |
| ==**性能**==        | 较低（需要维护等待队列顺序） | 较高（减少线程切换开销）    |
| ==**适用场景**==      | 需要严格公平性的场景     | 追求吞吐量，默认使用      |

**默认使用非公平锁**，因为它的吞吐量更高——一个刚释放锁的线程再次获取锁时，直接 CAS 插队成功，避免了唤醒等待线程的上下文切换开销。
