### 一、DCL 的本质与问题

由于某些时候需要降低启动线程的开销与降低类的初始化成本，需要某些方法来解决这个问题。历史上曾使用**双重检查锁定**来实现延迟初始化。这种方法虽然可以实现延迟初始化的功能，但也带来了严重的问题。

DCL 的问题根源在于 `instance = new Singleton()` 这一行代码。它在 JVM 层面分解为三步：

| 步骤  | 伪代码                         | 说明            |
| --- | --------------------------- | ------------- |
| ①   | **`memory = allocate();`**  | 分配内存空间        |
| ②   | **`ctorInstance(memory);`** | 初始化对象（执行构造函数） |
| ③   | **`instance = memory;`**    | 将引用指向分配的内存空间  |

步骤②和步骤③之间没有直接的**数据依赖**，因此在某些处理器上会被**重排序**——先执行步骤③，再执行步骤②。在单线程下，由于 intra-thread semantics（线程内语义）的保证，无论怎么重排序，单线程的执行结果不会改变。但在多线程下则完全不同。

多线程下，线程的执行是根据操作系统以**时间片轮转**的方式安排的。如果线程 A 执行到步骤③（为 instance 分配了内存空间但尚未初始化对象），此时线程 B 来做第一次检查，发现 `instance != null`，直接返回这个**尚未初始化完成的对象**，就会导致数据访问错误。

### 二、两种解决方案

| 方案          | 核心思路            | 实现方式                                                 |
| ----------- | --------------- | ---------------------------------------------------- |
| ==**方案一**== | 禁止步骤②和步骤③的重排序   | 使用 **`volatile`** 修饰 `instance`，通过 StoreLoad 屏障禁止重排序 |
| ==**方案二**== | 允许重排序，但对其他线程不可见 | 使用静态内部类，利用 JVM 类初始化锁保证初始化过程对其他线程不可见，直到完成             |

**方案一**是"禁止重排序"，通过volatile字段让所有线程都按正确的顺序看到初始化过程。

**方案二**是"允许重排序，但藏起来"，让初始化过程对其他线程完全不可见，直到彻底完成才公布引用。这个就要参考[[基于类初始化的方案]]

### 三、面试要点

| 问题        | 回答                                                  |
| --------- | --------------------------------------------------- |
| **DCL 是什么**   | 双重检查锁定，一种单例延迟初始化方案                                  |
| **DCL 的问题**   | `instance = new Singleton()` 分解为多个步骤，分配内存和初始化可能被重排序 |
| **为什么单线程没问题** | intra-thread semantics 保证重排序不影响单线程结果                |
| **为什么多线程有问题** | 一个线程可能看到尚未初始化完成的半初始化对象                              |
| **两种解决方案**    | volatile 禁止重排序，或静态内部类利用类初始化锁                        |
