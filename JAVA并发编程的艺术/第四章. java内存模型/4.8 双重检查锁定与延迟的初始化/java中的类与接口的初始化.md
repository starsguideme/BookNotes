**JVM 类初始化机制**

### 一、为什么 JVM 要给 Class 对象加初始化锁？

每个类在 JVM 内部都对应一个 `java.lang.Class` 对象。当类被首次主动使用时，JVM 必须执行类的初始化——执行静态变量的赋值和静态代码块。JVM 规范要求：**多线程同时触发同一个类的初始化时，只有一个线程能执行初始化，其他线程必须等待**。

为了满足这个规范，JVM 在 `Class` 对象上实现了一个同步机制——可以理解为在类的初始化方法上隐式加了一把 `synchronized` 锁。线程 A 执行初始化时，获取这把锁；线程 B 获取不到，只能等待或自旋。初始化完成后，线程 A 释放锁，线程 B 获取锁后检查状态，发现类已经初始化完成，直接释放锁返回。

**为什么这样实现？**

- **保证原子性**：每个类的初始化只执行一次，不会因为多线程并发而重复初始化。
    
- **保证可见性**：初始化完成后，所有静态变量的值对其他线程立即可见——这正是 `happens-before` 规则的体现。
    
- **保证有序性**：初始化过程中的操作不会被重排序到初始化完成之后。
    

**Java 是怎么制定这个规则的？**

这是 JVMS（Java 虚拟机规范）明确要求的。JVMS 规定：**类的初始化过程（即 `<clinit>` 方法）必须被 JVM 自动加锁保护**，以确保多线程环境下的安全性。

### 二、类初始化的完整流程（五个阶段）

**阶段一：获取初始化锁**

线程 A 在 `Class` 对象上获取初始化锁。这本质上是一个 JVM 层面的同步机制——线程 A 获取锁后，其他线程无法获取该 `Class` 对象的初始化锁。

**阶段二：执行类初始化**

线程 A 持有锁，执行类的静态变量赋值和静态代码块。在此期间，线程 B 在初始化锁的对应等待状态上阻塞等待。

**阶段三：释放初始化锁**

线程 A 完成初始化后，如果线程 A 中使用了 `notifyAll` 机制（这是 JVM 内部实现的，并非显式的 `notifyAll` 调用），唤醒所有等待的线程，释放初始化锁。线程 A 中类/对象/接口的初始化处理完成。

**阶段四：其他线程确认初始化完成**

线程 B 获取初始化锁，检查 `Class` 对象的状态，发现类已经初始化完成，释放初始化锁，结束自己的等待，然后开始正常访问这个类。

**为什么是线程 B 执行结束操作，而不是线程 A？**

线程 A 的"销毁"不是 GC 回收的对象销毁。线程 A 在阶段三释放了初始化锁，它的初始化任务已经完成，线程 A 本身继续执行后续代码，继续活着。而线程 B 在阶段四获取锁、确认类已初始化、释放锁，这是线程 B 自己完成自己的初始化等待流程，不是替线程 A 执行销毁任务。

**阶段五：后续线程快速通过**

线程 C 获取初始化锁，检查 `Class` 对象状态，发现类已经初始化完成，直接释放锁返回，不再执行初始化。

### 三、类初始化如何保证可见性与有序性？

根据 JMM 的先行发生原则：

- **有序性**：线程 A 在持有锁期间完成初始化操作，线程 B 在获取锁之后才能访问类。**锁的释放 happens-before 锁的获取**，因此线程 A 的初始化操作在线程 B 访问类之前完成。
    
- **可见性**：线程 A 在释放锁时，将所有静态变量的值刷新到主内存。线程 B 获取锁时，从主内存重新读取。因此**线程 A 对类初始化的结果对线程 B 可见**。
    

### 四、延迟初始化 vs 正常初始化

通过延迟初始化降低了初始化类或创建实例的开销，但增加了访问延迟初始化的字段时的开销。在大多数情况下，**正常初始化的优先级要高于延迟初始化**。

如果需要对 `final` 变量实现延迟初始化，需要配合 `volatile` 关键字来保证多线程下的可见性。这是因为 `final` 只保证构造函数完成后的初始化可见性，不保证延迟初始化这种绕过构造函数的场景下的可见性。

### 五、面试要点

| 问题                     | 回答                                             |
| ---------------------- | ---------------------------------------------- |
| **JVM 为什么给 Class 对象加初始化锁** | 保证每个类的初始化只执行一次，且多线程安全                          |
| **为什么锁是隐式的**               | JVMS 规范要求 `<clinit>` 自动加锁，JVM 在底层实现，不需要程序员手动加锁 |
| **初始化如何保证 happens-before** | 线程 A 释放锁 → 线程 B 获取锁，释放锁 happens-before 获取锁     |
| **多个线程同时触发初始化会发生什么**       | 一个线程执行初始化，其他线程等待；初始化完成后，其他线程直接返回               |
| **延迟初始化的开销权衡**             | 降低了初始化开销，但增加了每次访问字段的检查开销                       |
