**初始化的线程安全机制**

### 一、类初始化锁的本质

在初始化时，即在被 Class 加载但被线程使用之前，会执行类的初始化工作。在执行初始化的时候，JVM 会获取一把**初始化锁（LC 锁）**。这个锁由 JVM 隐式管理，确保多个线程对同一个类执行初始化时，只有一个线程能执行初始化，其他线程必须等待。

==**类初始化锁由 JVM 自动加锁，不需要程序员手动使用 volatile/synchronized/Lock。**== 这是 JVM 规范层面的保证，底层实现上将初始化过程视作一个临界区，自动为其加锁。

基于这个特性，就有以下方案来解决初始化问题——比如**静态内部类（占位类模式）**，正是利用类初始化锁来保证单例的线程安全：`InstanceHolder` 在首次被访问时才触发类初始化，JVM 自动保证初始化过程的原子性和可见性。

### 二、触发类初始化的六种情况
根据 Java 语言规范，在以下情况会直接进行初始化工作：

| 触发条件                               | 说明               | 示例                            |
| ---------------------------------- | ---------------- | ----------------------------- |
| ==**T 是一个类，且 T 类型的实例被创建**==        | 使用 `new` 关键字创建对象 | `new MyClass()`               |
| ==**T 是一个类，且 T 中声明的一个静态方法被调用**==   | 调用类的静态方法         | `MyClass.staticMethod()`      |
| ==**T 中声明的一个静态字段被赋值**==            | 对静态字段进行写操作       | `MyClass.staticField = value` |
| ==**T 中声明的一个静态字段被使用，但这个字段并不是常量**== | 读取非常量的静态字段       | `int v = MyClass.staticField` |
| ==**一个顶级类，且断言语句在 T 内部被迭代执行**==     | 断言语句在类内部执行       | JDK 1.4 引入的 `assert` 语句       |
| ==**每个类或接口 C，都有与其对应的初始化 LC 锁**==   | JVM 在初始化类时获取初始化锁 | 全程由 JVM 自主实现                  |

==**注意**==：访问类的 `static final` 常量不会触发类的初始化，因为编译期常量在编译时就会被确定，不需要类初始化也能访问。

### 三、JVM 的自主实现

每个类或接口 C，都有与其对应的初始化 LC 锁，从接口 C 到初始化 LC 锁，全程由 **JVM 自主实现**。JVM 在初始化类时获取LC锁，并且每个线程都会尝试获取这把锁，以确保类被正确地执行初始化的任务。

Java 也允许 JVM 自主实现自己的优化任务——比如延迟初始化、提前初始化等，只要不违反 JVM 规范的语义。

|类初始化锁由谁加锁|==**JVM 自动加锁**==，不需要程序员手动使用 volatile/synchronized/Lock|
