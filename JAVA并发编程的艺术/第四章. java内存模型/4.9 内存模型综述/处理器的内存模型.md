

### 一、从顺序一致性到宽松模型

顺序一致性的内存模型是一个理论模型，JMM 和处理器内存模型在实现程序时通常会参考这个理论模型。由于顺序一致性模型的要求太过苛刻，导致在严格执行下反而影响了处理器的执行效率。

为了解决这个不必要的麻烦，JMM 和处理器对其进行了放松。按照读写的要求降低划分来看，处理器内存模型可以分为如下事物：

```text
顺序一致性模型（最严格，理论模型）
    ↓ 放松写-读执行顺序
TSO（Total Store Ordering）
    ↓ 继续放松写-写顺序
PSO（Partial Store Ordering）
    ↓ 放松读-写和读-读顺序
RMO / PowerPC（最宽松）
```

注:==这些模型都是以不存在**任何数据依赖性**为前提而诞生的==。

### 二、各模型允许的重排序类型

| 模型 | 是否允许 Store-Load 重排序 | 是否允许 Store-Store 重排序 | 是否允许 Load-Load 重排序 | 是否允许 Load-Store 重排序 | 典型代表 |
|------|------------------------|------------------------|----------------------|----------------------|---------|
| ==**TSO**== | ==**是**== | 否 | 否 | 否 | X86、AMD64 |
| ==**PSO**== | 是 | ==**是**== | 否 | 否 | SPARC（部分） |
| ==**RMO/PowerPC**== | 是 | 是 | ==**是**== | ==**是**== | ARM、PowerPC |

**性能由强到弱**：**顺序一致性 > TSO > PSO > RMO > PowerPC**。越宽松的模型，允许的重排序类型越多，性能潜力越大，但编程难度也越高。

### 三、为什么所有模型都允许写-读重排序？

由表可得，所有的处理器内存模型都允许**写-读（Store-Load）操作之间的重排序**。这是因为这些模型内部都使用了**写缓冲区**。写缓冲区可能导致写-读操作之间的重排序，同时也允许线程更早地读到写-读操作之间的重排序结果——其他线程可能看到一个写操作尚未完成时的中间状态。

### 四、处理器模型与内存屏障的对应关系

正常情况来看，这些处理器模型一般都要比 Java 内存模型的性能要弱。因此 JVM 在执行初始化任务的时候会根据需求自行安排需要插入的内存屏障。以下是各处理器模型需要显式插入的内存屏障：

| 处理器模型 | 允许的重排序类型 | 需要显式插入的内存屏障 |
|-----------|----------------|---------------------|
| ==**TSO**== | 仅 Store-Load | ==**仅需 StoreLoad**==（其余三种由硬件保证） |
| ==**PSO**== | Store-Load + Store-Store | ==**StoreStore + StoreLoad**== |
| ==**RMO/PowerPC**== | 全部四种 | ==**四种全部需要**==：LoadLoad、StoreStore、LoadStore、StoreLoad |

**逐模型分析**：

**TSO 模型（X86、AMD64）**——只允许 Store-Load 重排序：

| 内存屏障 | 是否需要显式插入 | 原因 |
|---------|----------------|------|
| LoadLoad | ❌ 不需要 | 硬件已保证读-读顺序 |
| StoreStore | ❌ 不需要 | 硬件已保证写-写顺序 |
| LoadStore | ❌ 不需要 | 硬件已保证读-写顺序 |
| ==**StoreLoad**== | ✅ ==**需要**== | 只有这一种重排序是允许的，必须用屏障禁止 |

**PSO 模型**——允许 Store-Load 和 Store-Store 重排序：

| 内存屏障 | 是否需要显式插入 | 原因 |
|---------|----------------|------|
| LoadLoad | ❌ 不需要 | 硬件已保证 |
| ==**StoreStore**== | ✅ ==**需要**== | 允许写-写重排序 |
| LoadStore | ❌ 不需要 | 硬件已保证 |
| ==**StoreLoad**== | ✅ ==**需要**== | 允许写-读重排序 |

**RMO / PowerPC 模型**——允许全部四种重排序：

| 内存屏障 | 是否需要显式插入 |
|---------|----------------|
| ==**LoadLoad**== | ✅ 需要 |
| ==**StoreStore**== | ✅ 需要 |
| ==**LoadStore**== | ✅ 需要 |
| ==**StoreLoad**== | ✅ 需要 |

### 五、Java 的 volatile 在不同处理器模型下的屏障策略

| Java 机制 | 插入的内存屏障 | 在 TSO（X86）上实际插入 | 在 RMO（ARM）上实际插入 |
|---------|-------------|---------------------|---------------------|
| ==**`volatile` 写**== | 前 StoreStore，后 StoreLoad | 仅 **StoreLoad** | **StoreStore + StoreLoad** |
| ==**`volatile` 读**== | 前 LoadLoad，后 LoadStore | **无**（硬件已保证） | **LoadLoad + LoadStore** |
| ==**`synchronized` 释放锁**== | 隐式 Store 屏障 | 依赖 TSO 硬件保证 | 需显式插入 Store 屏障 |
| ==**`synchronized` 获取锁**== | 隐式 Load 屏障 | 依赖 TSO 硬件保证 | 需显式插入 Load 屏障 |

### 六、关键结论

1. ==**所有模型都需要 StoreLoad 屏障**==，因为所有模型都允许 Store-Load 重排序，而 StoreLoad 是唯一能保证写操作对其他处理器可见的屏障。
2. **X86（TSO）是最高效的**——JVM 在 X86 上只需插入 StoreLoad 屏障，其他三种屏障由硬件自动保证。
3. **ARM（RMO）是最复杂的**——JVM 在 ARM 上需要插入全部四种内存屏障。
4. **JVM 会自动适配**——JVM 会根据处理器类型自动选择需要插入的内存屏障，开发者无需手动处理。

### 七、面试要点

| 问题                              | 回答                                               |
| ------------------------------- | ------------------------------------------------ |
| **处理器内存模型有哪些**                      | ==**TSO、PSO、RMO、PowerPC**==，性能由强到弱               |
| **为什么所有模型都允许写-读重排序**                | ==**写缓冲区**==的存在导致 Store-Load 重排序                 |
| **X86 属于哪种模型**                      | ==**TSO**==，只允许 Store-Load 重排序，仅需插入 StoreLoad 屏障 |
| **ARM 属于哪种模型**                      | ==**RMO**==，允许全部四种重排序，需要插入全部四种内存屏障               |
| **Java 的 volatile 在不同处理器上屏障策略有何不同** | X86 上 volatile 写仅需 StoreLoad；ARM 上需要全部四种屏障       |
