#### 1. `synchronized` 的作用与本质

- **作用**：`synchronized` 用于保证代码块或方法的**线程安全**，它通过内置锁机制，==**原子性**==（同一时间只有一个线程执行）、==**可见性**==（一个线程对共享变量的修改，在解锁后对其他获取锁的线程立即可见）和==**有序性**==（禁止在临界区内的指令重排序到临界区外）的“三大特性”。
    
- **本质**：它的本质是一种 **JVM 内置的锁机制**，常被称为 **悲观锁、独占锁（互斥锁）或内置锁**。从1.6版本开始，JVM 对其进行了大量优化，引入了**偏向锁、轻量级锁、自适应自旋锁**等机制，所以它的实际性能并没有很多旧认知里那么低。
    

#### 2. 核心特性：可重入与自动释放

- ==**可重入锁**==：`synchronized` 是可重入锁，这意味着==**同一个线程**在已经持有一个锁的情况下，可以再次进入该锁保护的同步方法或同步块==，而不会被自己阻塞。其内部通过一个计数器实现，每次进入计数器加1，退出减1，计数器归零时释放锁。
    
- ==**自动获取与释放**==：这是它最核心的特点。线程进入同步块时**自动获取**锁；无论是正常执行完，还是中途抛出异常，JVM 都会保证锁被**自动释放**，从而避免了死锁风险，构成一个健壮的锁机制。
    

#### 3. `synchronized` 与 `Lock` 的对比

| 特性        | `synchronized` （JVM内置锁）                     | `Lock` （1.5 引入的全新设计，如 `ReentrantLock`）               |
| --------- | ------------------------------------------- | ---------------------------------------------------- |
| **实现层级**  | **JVM层面**的内置实现，是关键字                         | **API层面**的实现，是接口                                     |
| **释放机制**  | **自动获取与释放**（JVM保证）                          | ==**必须手动释放**，否则会导致死锁==，通常在 `finally` 块中调用 `unlock()` |
| **性能**    | 经过现代JVM优化（偏向锁等），**两者在大多数场景下性能已非常接近**        | 在某些高竞争场景下可能仍然略占优势，但差距很小                              |
| **功能灵活性** | **功能单一，无法灵活处理**。不支持尝试获取锁、等待可中断等特性，只能持续等待阻塞。 | ==**功能丰富强大**==，支持尝试非阻塞获取锁、可中断获取锁、公平锁等多种高级功能。         |
| **适用场景**  | 适用于大多数标准并发场景，代码简洁，不易出错。                     | 适用于需要高级锁特性解决的并发问题，如需要保证等待最久的线程优先获取资源的公平锁等。           |
