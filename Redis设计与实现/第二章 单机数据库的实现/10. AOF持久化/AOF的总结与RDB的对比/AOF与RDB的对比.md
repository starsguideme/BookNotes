## 一、RDB 持久化

### 1.1 RDB 的本质与触发方式

RDB 本质上是一种通过生成 ==**二进制快照**== 来实现持久化的策略。它会将某个时刻 Redis 中的所有键值对、数据类型编码、过期时间等数据库状态，序列化后写入一个压缩的二进制文件中。

**触发方式分为两类：**

- ==**手动触发**==：
    
    - `SAVE`：由主线程直接执行，在主线程中遍历并写入，==**期间 Redis 完全阻塞，无法响应任何客户端请求**==。
        
    - `BGSAVE`：由主线程执行，然后通过 `fork` 创建子进程来异步执行，执行完后自动退出，==**主进程继续处理请求，不阻塞**==。
        
- ==**自动触发**==：
    
    - 配置文件中设置 `save <seconds> <changes>`，例如 `save 900 1` 表示 900 秒内如果有至少 1 次修改，就自动触发 `BGSAVE`。
        
    - 底层原理：`serverCron` 定时函数每 100ms 检查一次 `dirty` 计数器（记录自上次保存后的修改次数）和 `lastsave` 时间戳，满足条件则触发。
        

### 1.2 RDB 文件的内部结构（完整版）

RDB 文件是一个经过 **LZF 算法压缩** 的二进制文件，其完整结构如下：

| REDIS(5字节) | RDB版本号(4字节) | 数据库选择器 | 键值对数据(含类型/编码/过期时间) | EOF标记 | 校验和(8字节) |

各部分详解：

- ==REDIS==（5字节）：文件头，存储 "REDIS" 这五个字符的 ASCII 码，==**用于快速校验该文件是否为合法的 RDB 文件**==。
    
- ==**RDB 版本号**==（4字节，如 "0009"）：不同版本的 Redis 使用不同的 RDB 格式，用于兼容性检查，确保不会用高版本文件覆盖低版本数据。
    
- ==**数据库选择器**==：标记接下来的键值对属于哪个数据库，此后的数据隶属于该数据库，直到下一个数据库选择器出现。
    
- ==**键值对数据**==：这是 RDB 文件的核心部分，存储键值、数据类型编码、过期时间等信息。
    
- **数据类型编码**：包含 key 和 value 两部分，value 部分会记录该值使用的内部编码（如 `intset`、`ziplist`、`skiplist` 等）。
    
- **内存淘汰相关的逻辑时钟**：**LRU 和 LFU 信息** 会被一起存入 RDB 文件，用于恢复时维护内存淘汰策略的状态，避免恢复后所有键的访问时间都重置为当前时间。
    
- ==**空闲时间（idletime）**==：记录每个键的空闲时长，方便恢复到真实的内存访问状态。
    
- **EOF 标记**（常量的指定明文）：标识数据部分的结束，碰到 EOF 说明核心数据读取完毕，防止越界读取。
    
- ==**校验和**==（8字节，CRC64）：用于 **完整性校验**，Redis 加载 RDB 文件时会计算校验和并与文件中记录的校验和对比，不匹配则拒绝加载以保证数据安全。
    

### 1.3 RDB 加载时机与优先级

- **启动加载**：Redis 启动时，==**优先检查 AOF 文件是否存在**==。如果 AOF 开启，则使用 AOF 文件恢复数据，忽略 RDB 文件，==**原因：AOF 的数据完整性优于 RDB，通常更新更及时**==。
    
- **主从全量同步**：主从复制时，主节点执行 `BGSAVE` 生成 RDB 文件发送给从节点，从节点加载 RDB 文件完成数据初始化。
    

### 1.4 RDB 的优缺点及适用场景

- ==**优点**==：
    
    - 文件紧凑，体积小，适合做 **冷备份甚至异地备份方案**。
        
    - 恢复速度极快，直接加载二进制数据，无需逐条执行命令。
        
    - 对主进程性能影响小，`fork` 子进程异步生成。
        
- ==**缺点**==：
    
    - 存在数据丢失窗口，大概率丢失最后一次备份后的所有数据。
        
    - `fork` 子进程在数据集较大时可能耗时较长，且需要足够的内存（写时复制会复制页表）。
        
- ==**适用场景**==：对数据完整性和安全性要求不高，但对恢复速度要求较高的场景，如菜品信息、书籍目录等相对静态的配置数据。

## 二、AOF 持久化

### 2.1 AOF 的本质与写入流程

AOF 本质上是一种通过 ==**记录所有写入命令**== 来持久化数据库状态的方式。与 RDB 不同，==**AOF 保存的是 Redis 协议格式的文本内容**==，而不是二进制数据。

**写入流程：**

- ==命令追加==：服务器每执行一条写命令，就将该命令以协议格式追加到服务器全局的 `aof_buf` 缓冲区末尾，本质上就是追加进入了一个内存中的字符串对象末端。
    
- ==**文件写入与同步**==：在每次 `beforeSleep` 事件循环调用之前，Redis 都会调用 `flushAppendOnlyFile` 函数，根据 `appendfsync` 策略将缓冲区内容写入并同步到磁盘。
    

**关键区分点**：

- **写入（write）**：将 `aof_buf` 中的数据拷贝到 OS 内核缓冲区（页缓存），速度快但数据可能还没到磁盘。
    
- **同步（fsync/fdatasync）**：强制将内核缓冲区中的数据刷入磁盘，速度慢但能保证持久化。
    

### 2.2 appendfsync 三种策略对比（高频面试题）

| 策略               | 写入行为      | fsync 行为      | 性能  | 安全性 | 丢失窗口       |
| ---------------- | --------- | ------------- | --- | --- | ---------- |
| **always**       | 每次事件循环都写入 | 每次事件循环都同步     | 最差  | 最高  | 只丢当前未完成的命令 |
| **everysec**（默认） | 每次事件循环都写入 | 后台线程每 1 秒同步   | 中等  | 较高  | 最多丢失 1 秒数据 |
| **no**           | 每次事件循环都写入 | 不主动同步，由 OS 决定 | 最好  | 最差  | 可能丢失大量数据   |

==**面试话术**==：

- 所以你可以这样简单记，三个选项：always、everysec、no，对应每次、每秒、操作系统自己决定。
    
- **always**：每次写入都同步，**效率最差但安全性最高**，就算停机最多也只丢当前一条命令，适合对数据要求极高的场景。
    
- **everysec**：每次事件循环都写入内核缓冲区，但同步操作由后台线程每秒执行一次。==**兼顾了性能和数据安全，是 Redis 的默认策略**==。如果发生故障，最多只丢失 1 秒内的数据，适合绝大多数业务场景。
    
- **no**：只写入内核缓冲区，不调用 `fsync`。系统会在刷新周期到来时自动写入，**写入速度最快，但发生停机可能会丢掉大量写命令**，适合对数据安全性要求极低的场景。
    

### 2.3 AOF 的加载与数据还原

Redis 启动时，如果开启了 AOF，会通过以下步骤恢复数据：

- ==创建一个不带网络连接的伪客户端==，因为 Redis 命令只能在客户端上下文中执行。
    
- 从 AOF 文件中逐条分析并读取出写命令。
    
- 使用伪客户端逐条执行这些命令。
    
- **由于 Redis 是单线程的**，所以整个执行过程严格顺序进行，必须等到所有命令执行完毕后，Redis 才可以对外提供服务。
    

### 2.4 AOF 重写的本质与目的

**为什么需要重写？**

- 如果不对 AOF 文件加以控制，**AOF 文件会越来越大**，过大的文件会占用大量磁盘空间，且还原时因要执行全部命令导致恢复时间越来越长，甚至影响宿主机性能。
    

**重写的本质：**

- AOF 重写虽然叫"重写"，但 ==**完全不读取旧 AOF 文件**==，**而是直接读取==当前==数据库状态**，为每个键生成一条等同效果的创建/设置命令。
    
- 新文件等价于旧文件所保存的数据库状态，但用最精简的命令表达，==**不会包含任何冗余操作**==。
    
- **示例**：旧 AOF 记录了 5 次 `LPUSH` 命令，重写后只记录一条包含最终 5 个元素的 `RPUSH` 命令。
    

**重写的触发方式：**

- 手动触发，通过执行 `BGREWRITEAOF` 命令。
    
- 自动触发，由配置参数控制，通常检查当前 AOF 文件大小相对上次重写后的增长百分比及最小尺寸。
    

### 2.5 BGREWRITEAOF 的实现原理（高频面试追问）

**为什么需要子进程？**

- AOF 重写会进行大量磁盘写入，如果由主线程执行（如同 `SAVE` 命令），==**Redis 可能会无法响应客户端请求，遇到高并发场景时则必定造成长时间的服务不可用，进而可能引发严重业务中断与生产事故**==。
    
- 因此，==**Redis 通过 fork 创建子进程执行重写**==，主进程在此期间继续处理客户端请求。
    

**为什么用子进程而不用线程？**

- ==**为了在不使用锁的情况下保证数据安全性**==。子进程拥有父进程的内存副本（写时复制），天然避免数据竞争，无需加锁。
    

**如何解决数据不一致问题？**

- 这是个核心的面试细节，子进程重写期间，父进程仍在处理新命令，导致子进程生成的 AOF 文件可能落后于当前数据库状态。
    
- 解决方案：引入 ==**AOF 重写缓冲区**==。
    
    - 重写期间，父进程的所有写命令同时追加到两个地方：`aof_buf`（保证旧 AOF 正常写入）和 ==**AOF 重写缓冲区**==（`aof_rewrite_buf_blocks`，记录重写期间的增量命令）。
        
    - 子进程完成后，父进程将 ==**AOF 重写缓冲区**== 的内容追加到新 AOF 文件末尾。
        
    - 最后，==**原子替换**==：将新 AOF 文件原子性地重命名为旧文件名，保证替换过程不会出现中间状态。
        

### 2.6 AOF 重写的具体流程

**通用步骤：**

- 遍历所有数据库（`SELECT` 切换）。
    
- 每个数据库中遍历所有键。
    
- 忽略已过期的键。
    
- 根据键的类型，用对应的全量获取命令读取值，再用创建命令写入新文件。
    
- 如果键有 TTL，直接用 `PEXPIREAT` 写入绝对过期时间戳。
    
- 最后关闭文件。
    

**不同类型键的处理方式（必须背下来）：**

|键类型|获取值命令|重写命令|
|---|---|---|
|String|`GET`|`SET`|
|List|`LRANGE 0 -1`|`RPUSH`|
|Hash|`HGETALL`|`HMSET`（或多次 `HSET`）|
|Set|`SMEMBERS`|`SADD`|
|Sorted Set|`ZRANGE 0 -1 WITHSCORES`|`ZADD`|

### 2.7 防止缓冲区溢出机制

- 对于包含多元素的键（List/Hash/Set/ZSet），如果元素数量超过 ==**`REDIS_AOF_REWRITE_ITEMS_PER_CMD`（默认值 64）**==，重写程序会拆分为多条命令。
    
- 例如：一个包含 200 个元素的集合会被拆分为 4 条 `SADD` 命令（64+64+64+8）。
    
- 目的：防止单条命令过大导致 ==**客户端输出缓冲区溢出**==。

## 三、RDB 与 AOF 对比与混合持久化（面试总结必考）

### 3.1 核心区别对比表

|维度|RDB|AOF|
|---|---|---|
|持久化方式|二进制快照|记录写命令|
|文件体积|小|大|
|恢复速度|快|慢|
|数据安全性|可能丢失大量数据|最多丢 1 秒（everysec）|
|对性能影响|fork 瞬间阻塞|取决于 fsync 策略|
|运维便捷性|备份方便|可手动修复数据|

### 3.2 Redis 是混合持久化模式的说明

- 在实际生产环境中，RDB 和 AOF ==**通常会同时开启**==。
    
- RDB 用于 **冷备份恢复和部署**，AOF 用于 **保证数据安全性**。
    
- Redis 启动时优先加载 AOF，因为它的数据更完整。
    

### 3.3 面试加分项：混合持久化（Redis 4.0+）

- Redis 4.0 引入了 ==**混合持久化模式**==：AOF 重写时，先以 RDB 格式将当前快照写入新 AOF 文件开头，后续的增量命令以 AOF 文本格式追加。
    
- **优点**：兼顾 RDB 的快速恢复和 AOF 的数据安全性，是生产环境的最佳实践。
    
- **判断方式**：通过 `aof-use-rdb-preamble yes` 开启。

## 四、面试常见追问及回答话术

**Q1：RDB 的 fork 会不会阻塞主线程？**

- fork 操作本身会瞬间阻塞主线程，阻塞时间与内存页表大小成正比。内存越大，阻塞时间越长（通常几毫秒到几百毫秒）。
    

**Q2：如果 RDB 文件损坏了怎么办？**

- Redis 提供了 `redis-check-rdb` 工具检测和修复，同时优先使用 AOF 恢复可以避免这个问题。
    

**Q3：AOF 如果文件出现异常损坏呢？怎么恢复？**

- Redis 提供了 `redis-check-aof --fix` 工具，可以修复 AOF 文件中的语法错误，文件末尾截断不完整的命令，保证至少能恢复大部分数据。
    

**Q4：为什么 Redis 重写 AOF 时不共享已存在的 AOF 内容，而是重新生成？**

- 重新生成能最大程度精简和节省最终空间，老文件的冗余内容必须依赖新生成的数据结构和当前程序本身的解析，直接复用旧片段反而实现复杂且容易因历史格式变更产生兼容性问题。
    

**Q5：线上出现 BGSAVE 失败，你会怎么排查？**

- 检查是否有足够磁盘空间、`dir` 目录是否有写入权限、`fork` 是否能分配足够内存和进程等系统资源、Redis 本身的日志报错信息，以及操作系统的内存策略（OOM 设置等）。具体排查按：先看日志 → 查磁盘（`df -h`）→ 查权限 → 查内存（`free -h`）→ 查系统限制（`ulimit -a`）→ 复制测试 → 如果都没问题则考虑定时突发大量写入导致的瞬时 I/O 瓶颈，需要结合业务流量特征分析。
    

**Q6：为什么选择 fork 而不是线程？**

- 避免锁竞争：Redis 是单线程模型，使用多线程访问共享数据结构需要引入复杂的锁机制，而 `fork` 利用操作系统的写时复制机制，天然避免数据竞争，实现简单且安全。
