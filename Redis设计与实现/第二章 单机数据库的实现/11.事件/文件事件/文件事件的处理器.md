**文件事件处理器**

Redis 为文件事件编写了多个处理器，分别用于实现不同的网络通信需求。==这些处理器是 Redis 事件循环机制的核心组件==，各自承担特定的职责：

---

### 1. [[连接应答处理器]]

- **关联对象**：监听套接字
    
- **触发时机**：当有新的客户端连接请求到达时
    
- **核心职责**：==对连接服务器的各个客户端进行应答==，接受客户端的连接，并为新的客户端套接字绑定后续的处理器
    

**面试补充**：监听套接字只负责接受连接，一旦连接建立，就会创建一个客户端套接字，后续的读写操作都在客户端套接字上进行，监听套接字不再参与。

---

### 2. [[命令请求处理器]]

- **关联对象**：客户端套接字
    
- **触发时机**：当客户端发送命令请求数据到达时
    
- **核心职责**：==读取客户端发送的命令数据==，将其传递给命令执行器
    

**面试补充**：命令请求处理器负责从套接字中读取命令内容，但不会执行命令。读取完成后，命令会被传递给命令执行器进行解析和执行。==这种设计遵循了单一职责原则==。

---

### 3. [[命令回复处理器]]

- **关联对象**：客户端套接字
    
- **触发时机**：当命令执行完毕，有回复数据需要发送给客户端时
    
- **核心职责**：==将命令的执行结果返回给客户端==
    

**面试补充**：命令执行完毕后，回复数据会被写入客户端的输出缓冲区。命令回复处理器会监听套接字的可写事件，当套接字变为可写状态时，将缓冲区中的数据发送给客户端。==这是典型的异步写入机制==，避免主线程因网络慢而阻塞。

---

### 4. [[复制处理器]]

- **关联对象**：主从服务器的专用套接字
    
- **触发时机**：当主从服务器进行复制操作时
    
- **核心职责**：==处理主从复制过程中的数据传输和同步==
    
**5. 以下是前三种处理器的优劣势与应用场景**

| **维度**     | **连接应答处理器**            | **命令请求处理器**               | **命令回复处理器**             |
| ---------- | ---------------------- | ------------------------- | ----------------------- |
| **函数**     | **`acceptTcpHandler`** | **`readQueryFromClient`** | **`sendReplyToClient`** |
| **关联套接字**  | **监听套接字**              | **客户端套接字**                | **客户端套接字**              |
| **事件类型**   | **`AE_READABLE`**      | **`AE_READABLE`**         | **`AE_WRITABLE`**       |
| **底层系统调用** | **`accept()`**         | **`read()`**              | **`write()`**           |
| **触发时机**   | **新连接到达时**             | **客户端发送命令时**              | **回复数据准备好且套接字可写时**      |
# ** 6. 以下是钱三种处理器的核心工作流程**
**① 客户端发起连接**
         **↓**
**② 监听套接字 AE_READABLE → `acceptTcpHandler``**
         **↓**
**③ 创建客户端套接字**
         **↓**
**④ 客户端套接字关联 AE_READABLE →`readQueryFromClient`**
         **↓**
**⑤ 客户端发送命令 → `readQueryFromClient` 读取**
         **↓**
**⑥ 命令执行，结果写入输出缓冲区**
         **↓**
**⑦ 客户端套接字关联 AE_WRITABLE → `sendReplyToClient`**
         **↓**
**⑧ `sendReplyToClient` 将结果发送给客户端**
         **↓**
**⑨ 取消 AE_WRITABLE 监听，等待下一次命令**
**面试补充**：复制处理器是为复制功能专门编写的，在 RDB 全量同步和命令增量传播阶段都会被使用，是整个 Redis 高可用架构的底层支撑。
