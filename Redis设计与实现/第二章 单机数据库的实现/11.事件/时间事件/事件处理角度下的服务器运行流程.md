## 一、服务器的执行流程

Redis 服务器启动后，会进入一个无限循环的事件处理流程，直到服务器关闭为止。

### 完整执行流程
① 启动服务器（初始化配置、加载数据、创建事件循环）
         ↓
② 判断是否关闭服务器
         ↓
    ├── 是 → 关闭服务器，退出事件循环
    │
    └── 否 → 进入事件循环的一次迭代
              ↓
        ③ 在 `beforeSleep()` 中执行准备工作（AOF 刷盘等）
              ↓
        ④ 调用 `aeApiPoll()` 阻塞等待文件事件的产生
              ↓
        ⑤ 处理所有已产生的文件事件
           （连接应答、命令请求、命令回复等）
              ↓
        ⑥ 处理所有已到达的时间事件
           （`serverCron` 的定期任务、过期键清理等）
              ↓
        ⑦ 开始新的事件循环迭代（回到步骤②）

## 二、事件的调度与执行规则

### 1. `aeApiPoll` 阻塞时间的决定机制

`aeApiPoll` 函数的最大阻塞时间 ==**由到达时间最近的时间事件决定**==。通过计算最近时间事件的到达时间与当前时间的差值来确定阻塞时长。

这样做有两个好处：

- ==**避免频繁轮询**==：如果没有文件事件产生，`aeApiPoll` 可以安心阻塞等待，不会空转消耗 CPU。
    
- ==**避免阻塞时间过长**==：阻塞时间上限由最近的时间事件决定，确保不会因为等待文件事件而让时间事件延迟过久。
    

### 2. 事件逐渐逼近时间事件到达时间的过程

因为文件事件是随机产生的，如果等待并处理完一次文件事件之后，仍然没有任何时间事件到达，那么服务器会再次等待并处理文件事件。==随着文件事件的不断执行，时间会逐渐向最近时间事件的到达时间逼近，直到最终处理已到达的时间事件。==

这个过程保证了服务器在繁忙时优先响应客户端请求，在空闲时及时处理定时任务。

### 3. 执行的有序性与原子性

服务器对文件事件和时间事件的处理是 ==**同步、有序且原子性的**==。

- **同步**：一个事件处理完毕后才处理下一个，不会并行执行。
    
- **有序**：==**文件事件先处理，时间事件后处理**==，顺序固定不变。
    
- **原子性**：单个事件处理器的执行不会被其他事件打断，直到处理器返回。
    

==**与 Java 并发的类比修正**==：Java 并发中的"原子性、有序性、可见性"是描述**多线程**环境下对共享变量的操作特性。而 Redis 之所以能处理并发请求，本质是因为 ==**单线程模型避免了竞态条件**==，不需要锁就能保证数据一致性，这与 Java 的 `synchronized` 加锁机制有本质区别。二者虽然都涉及"原子性、有序性"，但一个靠**无锁单线程**实现，一个靠**锁机制**实现，不可混为一谈。

### 4. 时间事件的实际执行时间偏差

因为时间事件在文件事件之后执行，并且事件之间不会出现抢占，所以 ==**时间事件的实际处理时间，通常会比设定的到达时间稍晚一些**==。

**产生偏差的原因**：

- `aeApiPoll` 返回时，可能刚好有新文件事件到达，需要先处理文件事件。
    
- 如果文件事件处理耗时较长，时间事件的执行会被进一步推迟。
    
- Redis 能保证时间事件**大致在设定时间附近**执行，但无法做到精确的实时触发。
    

**面试中关于偏差的追问**：这个偏差通常可以忽略不计，原因在于 Redis 的**单线程处理极快**，文件事件的处理时间往往在微秒级别。只有在命令执行耗时过长（比如 `KEYS *` 扫描大数据库）的情况下，才会明显影响时间事件的准时性，这也解释了**为什么 Redis 要避免使用耗时命令**。

## 三、面试话术（标准回答）

> Redis 的事件循环在每次迭代时，会先以最近时间事件的到达时间为上限，阻塞等待文件事件。这样可以避免空转，也保证时间事件不会延迟太久。当 `aeApiPoll` 返回后，先处理所有已触发的文件事件，再处理所有已到达的时间事件。由于文件事件在前、时间事件在后，且单线程不会抢占，所以时间事件的实际执行时间通常会比设定时间稍晚一些，但微秒级别的偏差在绝大多数场景下可以忽略不计。
