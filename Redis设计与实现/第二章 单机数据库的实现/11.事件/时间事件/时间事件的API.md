**时间事件的创建与调度**

### 1. 创建时间事件：`aeCreateTimeEvent`

`ae.c/aeCreateTimeEvent` 函数接受两个参数：

- **milliseconds**（毫秒数）：指定事件在多长时间后到达。
    
- **proc**（时间事件处理器）：事件到达时被调用的回调函数。
    

==该函数会创建一个新的时间事件，并将其添加到服务器的时间事件链表中。新事件将在当前时间的 `milliseconds` 毫秒之后到达。==

**计算方式**：`when = 当前时间戳 + milliseconds`

---

### 2. 时间事件的调度执行流程

当 `aeApiPoll` 阻塞等待文件事件返回或超时后，事件循环会调用 `processTimeEvents` 函数来处理所有已到达的时间事件。==时间事件的调度本质上是对无序链表的遍历与过滤==。

**完整执行流程**：

`processTimeEvents`() 被调用
         ↓
① 遍历整个时间事件链表
         ↓
② 检查每个事件的 when 属性是否 ≤ 当前时间
         ↓
    ├── 未到达 → 跳过，继续遍历下一个
    │
    └── 已到达 → 执行事件处理器 proc()
                  ↓
              ③ 获取处理器的返回值
                  ↓
              ├── 返回 AE_NOMORE（-1）→ 定时事件
              │         ↓
              │    ④ 从链表中删除该事件
              │
              └── 返回其他整数值（如 100）→ 周期性事件
                        ↓
                   ⑤ 更新 when 属性 = 当前时间 + 返回值
                      让事件在指定毫秒后再次到达
         ↓
⑥ 继续遍历下一个事件，直到链表末尾

---

### 3. 定时事件与周期性事件的处理对比

|维度|定时事件|周期性事件|
|---|---|---|
|返回值|`AE_NOMORE`（-1）|其他正整数值（如 100）|
|执行后操作|==**从链表中删除**==|==**更新 when 属性**==|
|后续是否触发|不再触发|持续触发，直到返回 `AE_NOMORE`|

---

### 4. 示例：`serverCron` 的周期性调度

以 Redis 最核心的周期性事件 `serverCron` 为例：

- 调用 `aeCreateTimeEvent(server.el, 1, serverCron, NULL, NULL)` 创建事件。
    
- 1 毫秒后首次到达，执行 `serverCron` 函数。
    
- `serverCron` 执行完毕后返回 `100`（即 `server.hz` 的倒数，默认 `100ms`）。
    
- 调度器更新该事件的 `when = 当前时间 + 100ms`。
    
- 100 毫秒后事件再次到达并执行，如此循环往复。
### 5. `serverCron` 的主要职责

`serverCron` 是 Redis 中最重要的周期性事件，负责执行服务器运行期间的各项定期维护任务。==它每隔 `100ms`（默认）执行一次，持续运行直到服务器关闭为止。==

其主要职责可分为以下几类：

**一、系统状态与统计信息更新**

- 更新服务器的各类统计信息，例如：
    
    - ==**时间戳**==：更新 `unixtime` 和 `mstime` 缓存，避免频繁系统调用。
        
    - ==**内存占用**==：更新 `used_memory` 等内存相关统计。
        
    - ==**数据库键数量**==：更新每个数据库的键数量统计。
        
    - 更新命令执行次数（如 `total_commands_processed`）、网络流量等指标。
        

**二、过期键清理与资源回收**

- ==**清理数据库中已过期的键值对**==（定期删除策略的触发点）。
    
    - 随机抽取一部分设置了过期时间的键，检查并删除其中已过期的键。
        
    - 通过限制每次清理的执行时长，避免阻塞主线程。
        
- 在从节点上，还会处理主节点发送的 `DEL` 命令来同步删除操作。
    
- 回收无效的客户端输出缓冲区、关闭空闲客户端等资源释放工作。
    

**三、客户端连接管理**

- ==**关闭和清理连接失败的客户端**==。
    
- 检查客户端的超时情况，释放超时客户端的资源。
    
- 收缩客户端查询缓冲区、输出缓冲区的大小，防止内存浪费。
    

**四、持久化操作触发**

- ==**尝试进行 AOF 或 RDB 持久化操作**==：
    
    - 检查 `BGSAVE` 或 `BGREWRITEAOF` 是否被延迟执行，如果条件满足则触发。
        
    - 检查 RDB 自动保存条件（`save <seconds> <changes>`），满足条件时触发 `BGSAVE`。
        
    - 在 AOF 重写完成后，完成新旧文件的替换等收尾工作。
        

**五、主从复制维护**

- 如果服务器是 ==**主服务器**==，则 ==**对从服务器进行定期同步**==：
    
    - 发送心跳包（`PING` / `REPLCONF`）维持连接。
        
    - 向等待中的从节点发送积压缓冲区中的命令。
        
    - 检查复制超时情况，处理断开的从节点连接。
        

**六、集群模式维护**

- 如果处于 ==**集群模式**==，对集群进行 ==**定期同步和连接测试**==：
    
    - 定期发送 `PING` 检测节点连通性。
        
    - 通过 Gossip 协议交换节点信息。
        
    - 检测节点是否下线（PFAIL → FAIL 转换）。
        
    - 处理槽迁移等集群状态变更。
        

---

### 6. `serverCron` 的执行频率与调整

- ==默认执行间隔为 `100ms`==，由配置项 `hz` 控制（`hz 10` 表示每秒执行 10 次）。
    
- Redis 7.0 之后引入了 `dynamic-hz`，服务器会根据客户端连接数自动调整执行频率（空闲时降低、繁忙时提高）。
    
- `serverCron` 内部会控制每次执行的时间上限，防止单次执行过长影响事件循环的响应能力。






**面试话术**

> `serverCron` 是 Redis 中唯一的周期性时间事件，默认每 100ms 执行一次。它的核心职责可以概括为三类：**数据维护**（过期键清理）、**资源管理**（客户端连接回收、统计信息更新）、**功能触发**（自动触发 BGSAVE、主从心跳、集群检测）。所有这些任务都有严格的执行时间上限，确保不会阻塞 Redis 的单线程事件循环。
