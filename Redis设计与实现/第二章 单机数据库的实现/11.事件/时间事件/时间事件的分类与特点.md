**时间事件**

**1. 时间事件的分类**

Redis 的时间事件分为两类：==**定时事件**== 和 ==**周期性事件**==。

- **定时事件**：在指定的时间点执行一次，执行完毕后就会被删除。
    
- **周期性事件**：每隔一段时间执行一次，执行完毕后会更新下一次执行时间，继续存在。
    

**2. 时间事件的组成结构**

一个时间事件由以下三个部分组成：

| 属性               | 说明                                         |
| ---------------- | ------------------------------------------ |
| ==**id**==       | 全局唯一 ID，用于标识该时间事件。ID 从小到大递增，新事件的 ID 大于旧事件。 |
| ==**when**==     | 毫秒精度的 UNIX 时间戳，记录了该事件下一次应该被执行的时间。          |
| ==**timeProc**== | 时间事件处理器（函数指针），当事件到达时被调用。                   |

**3. 定时事件与周期性事件的区分**

时间事件处理器的返回值决定了事件的类型：

- ==如果处理器返回 `ae.h/AE_NOMORE`==，则该事件为 ==**定时事件**==。它会在执行一次之后被直接删除，不再参与后续调度。
    
- ==如果处理器返回其他整数值（如 100）==，则该事件为 ==**周期性事件**==。服务器会根据返回值更新事件的 `when` 属性（`当前时间 + 返回值毫秒`），让这个事件在一段时间后再次被触发。
    

**4. 时间事件的存储结构**

==所有时间事件都存放在一个**无序链表**中==。当时间事件执行器运行时，它会遍历整个链表，查找所有 `when` 属性小于等于当前时间的已到达事件，并调用相应的事件处理器。

**5. 无序链表对性能的影响（修正）**

==时间事件链表虽然是按 ID 排序的（新事件始终在链表头部）==，但 ID 递增顺序并不等于事件到达时间的顺序。新添加的事件可能比链表中已有事件更早到达，因此链表**不按 `when` 属性排序**，查找已到达事件时必须遍历整个链表，时间复杂度为 O(N)。

**但是，这并不影响性能**，原因在于：

- ==**时间事件数量极少**==：在目前版本的 Redis 中，正常模式下服务器只使用 `serverCron` 这一个时间事件。即使开启 Sentinel 模式，时间事件数量也仅为少数几个。
    
- ==**链表几乎不会退化**==：因为事件数量极少，遍历开销可以忽略不计。所谓的"链表退化"通常指数百万级别的节点，而 Redis 的时间事件链表通常只有 1-2 个节点，根本不存在性能问题。
    
- ==**`serverCron` 本身就是周期性事件**==：它每次执行后返回一个非 `AE_NOMORE` 的值（如 100 毫秒），以此不断更新自己的 `when` 属性，实现周期性运行。
