**普通客户端的关闭机制**

### 一、客户端被关闭的原因

一个普通客户端可以因为多种原因被服务器关闭：

|关闭原因|触发条件|
|---|---|
|==**网络连接断开**==|客户端进程退出或被杀死，TCP 连接随之关闭|
|==**协议错误**==|客户端发送了不符合 Redis 协议（RESP）的命令请求|
|==**CLIENT KILL 命令**==|该客户端成为 `CLIENT KILL` 命令的目标|
|==**空转超时**==|客户端的空转时间超过了 `timeout` 配置的值（有例外，见下文）|
|==**输入缓冲区超限**==|命令请求的大小超过了输入缓冲区的限制大小（默认 1GB）|
|==**输出缓冲区超限**==|要发送给客户端的数据大小超过了输出缓冲区的限制|

### 二、空转超时的例外情况

如果用户为服务器设置了 `timeout` 配置选项，当客户端的空转时间（`当前时间 - lastinteraction`）超过 `timeout` 的值时，客户端会被关闭。

但以下客户端 ==**即使空转时间超时也不会被服务器关闭**==：

|例外客户端|标志|
|---|---|
|==**主服务器**==|打开了 `REDIS_MASTER` 标志|
|==**从服务器**==|打开了 `REDIS_SLAVE` 标志|
|==**正在被 BLPOP 等命令阻塞**==|打开了 `REDIS_BLOCKED` 标志|
|==**正在执行 SUBSCRIBE / PSUBSCRIBE 等订阅命令**==|处于 Pub/Sub 订阅状态|

**设计原因**：主从连接中断会导致复制中断，阻塞命令中断会导致客户端丢失等待的数据，订阅中断会导致消息丢失。这些场景下，==**数据正确性优先于资源回收**==。

### 三、输出缓冲区的限制机制

虽然可变大小缓冲区理论上可以保存任意长的命令回复，但为了避免客户端的回复过大导致服务器内存耗尽，服务器会时刻检查客户端输出缓冲区的大小，并在超出范围时执行相应的限制操作。

#### 1. 两种限制模式

|限制模式|触发条件|服务器行为|
|---|---|---|
|==**硬性限制（hard limit）**==|输出缓冲区大小**立即**超过硬性限制值|==**立即关闭客户端**==|
|==**软性限制（soft limit）**==|输出缓冲区大小超过软性限制值，但未超过硬性限制值|记录 `obuf_soft_limit_reached_time`，持续监控|

#### 2. 软性限制的执行逻辑

- 当输出缓冲区大小超过软性限制时，服务器会使用 `obuf_soft_limit_reached_time` 属性记录客户端**第一次**到达软性限制的起始时间。
    
- 之后服务器会持续监视这个客户端：
    
    - ==**如果持续超出软性限制，且超出时长达到了配置的关闭时间**==，服务器会关闭该客户端。
        
    - ==**如果在关闭时间到达之前，输出缓冲区大小降回到软性限制以下**==，则不会关闭客户端，且 `obuf_soft_limit_reached_time` 属性会被清空（重置）。
        

**设计原因**：软性限制允许客户端"短暂突发"地接收大量数据（如偶发的 `LRANGE` 返回大列表），但防止长期占用过多内存。这是一种更灵活的限流策略。

#### 3. 分类配置

通过 `client-output-buffer-limit` 选项，可以为不同类别的客户端分别设置不同的软性限制和硬性限制：

|客户端类别|配置项|说明|
|---|---|---|
|==**普通客户端**==|`normal`|常规的命令请求客户端|
|==**从服务器客户端**==|`slave`|主从复制中的从节点连接|
|==**发布/订阅客户端**==|`pubsub`|执行 `SUBSCRIBE` 等订阅命令的客户端|

**配置示例**：
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit slave 256mb 64mb 60
client-output-buffer-limit `pubsub` 32mb 8mb 60

- `normal 0 0 0`：普通客户端不做限制（三个值分别表示硬限制、软限制、软限制秒数，0 表示不限制）。
    
- `slave 256mb 64mb 60`：从节点硬限制 256MB，软限制 64MB，持续超过软限制 60 秒后断开。
    
- `pubsub 32mb 8mb 60`：发布/订阅客户端硬限制 32MB，软限制 8MB，持续超过软限制 60 秒后断开。
    

**面试追问**：为什么从节点和发布/订阅客户端的限制通常比普通客户端更严格？

> 从节点需要接收主节点的全量 RDB 数据和增量命令，数据量通常较大，所以限制相对宽松但仍需设上限。发布/订阅客户端如果消费速度跟不上消息生产速度，输出缓冲区会快速膨胀，所以需要较严格的限制来保护服务器内存。
