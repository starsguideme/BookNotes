**1. 解析流程**

在服务器将客户端发送的命令请求保存到 `querybuf` 属性之后，服务器会对输入缓冲区中的内容进行解析。解析完成后，会将拆分出的命令及其参数分别保存到客户端的 ==`argv` 属性== 和 ==`argc` 属性== 中。

**2. argv 属性**

`argv` 是一个 ==**字符串对象数组**==，数组中的每一项都是一个 SDS 字符串对象（`redisObject`，编码为 `REDIS_ENCODING_RAW`）。

- ==`argv[0]`== 始终是要执行的**命令名**（如 `"SET"`、`"GET"`、`"LPUSH"` 等）。
    
- 从 `argv[1]` 开始，依次是该命令的**参数**。
    
==`argv` 是一个数组，不是栈==。之所以 `argv[0]` 固定为命令名，是因为 Redis 协议规定命令请求的第一个元素就是命令本身，这是协议层面的设计。

**3. `argc` 属性**

`argc` 负责记录 `argv` 数组的长度，即命令及其参数的**总数量**。

**示例**：当客户端发送 `SET name "zhangsan"` 时：

| 属性        | 值            | 说明                 |
| --------- | ------------ | ------------------ |
| `argc`    | `3`          | 共 3 个元素：命令名 + 两个参数 |
| `argv[0]` | `"SET"`      | 要执行的命令             |
| `argv[1]` | `"name"`     | 参数1：键名             |
| `argv[2]` | `"zhangsan"` | 参数2：键值             |
|           |              |                    |

**面试要点**

**Q：argv 中的字符串对象和 querybuf 的 SDS 是什么关系？**

> `querybuf` 中存储的是原始字节流（客户端发来的完整命令文本），服务器解析时会根据 Redis 协议（RESP）的格式，把字节流拆分成多个独立的 SDS 字符串，再封装成 `redisObject` 存入 `argv` 数组。`querybuf` 是"原材料"，`argv` 是"成品零件"。

**Q：为什么 argc 需要单独记录，不能直接获取数组长度？**

> C 语言的原生数组不会自动记录长度，如果不单独维护 `argc`，每次都需要遍历数组直到遇到 `NULL` 才能知道长度，效率太低。直接用一个整型属性记录长度，访问速度 O(1)。
