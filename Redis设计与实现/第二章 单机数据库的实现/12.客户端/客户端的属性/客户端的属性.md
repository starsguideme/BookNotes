## Redis 客户端的属性分类

Redis 客户端的所有状态信息都保存在 `redisClient` 结构体中。这些属性按照功能可以分为两大类：==**通用属性**== 和 ==**与特定功能相关的属性**==。

---

### 一、通用属性

这些属性是**每个客户端都需要的**，无论它正在执行什么命令，属于客户端的基础设施：

| 属性                                 | 说明              |
| ---------------------------------- | --------------- |
| ==**fd（套接字描述符）**==                 | 标识客户端与服务器的网络连接  |
| **name（客户端[[名字]]）**                | 用于调试和管理的友好名称    |
| **flags（[[标志值]]）**                 | 记录客户端的角色和当前状态   |
| ==**querybuf（[[输入缓冲区]]）**==        | 暂存从客户端读取到的命令请求  |
| ==**buf/bufpos（[[命令回复与输出缓冲区]]）**== | 暂存要发送给客户端的回复数据  |
| **`argv/argc`**（[[命令参数与命令]])       | 当前被解析出的命令及参数    |
| **ctime（创建时间）**                    | 客户端连接创建的时间      |
| **lastinteraction（最后交互时间）**        | 用于检测超时，超时后可能被关闭 |
| **authenticated（[[身份验证]]）**        | 标记客户端是否已通过密码验证  |

---

### 二、与特定功能相关的属性

这些属性**只在客户端执行特定操作时才用到**，不需要为所有客户端提前分配复杂结构，只有在真正需要时才创建：

| 功能场景             | 对应属性                                             | 作用                                 |
| ---------------- | ------------------------------------------------ | ---------------------------------- |
| ==**数据库操作**==    | `db`（数据库指针）  <br>`dictid`（数据库号码）                 | 记录客户端当前正在使用的数据库，由 `SELECT` 命令切换    |
| ==**事务操作**==     | `mstate`（事务状态）                                   | 存储 `MULTI`/`EXEC` 之间的命令队列          |
| ==**WATCH 命令**== | `watched_keys`（被监视的键列表）                          | 实现事务的乐观锁（CAS），在执行 `EXEC` 前检查键是否被修改 |
| ==**列表阻塞命令**==   | `bpop_keys` / `bpoll_keys`                       | 记录 `BLPOP`/`BRPOP` 等阻塞命令等待的键和超时时间  |
| ==**主从复制**==     | `replstate`（复制状态）  <br>`repl_putback_buf`（积压缓冲区） | 主从同步时使用，控制复制流程和存储待传播命令             |
| ==**发布/订阅**==    | `pubsub_channels`（频道）  <br>`pubsub_patterns`（模式） | 记录该客户端订阅了哪些频道和模式                   |

---

### 三、套接字描述符（fd）与客户端类型

==**fd 属性是区分客户端类型的核心依据**==，它的值决定了客户端的本质：

| fd 值              | 客户端类型              | 说明                                                  |
| ----------------- | ------------------ | --------------------------------------------------- |
| ==**大于 -1 的整数**== | **[[普通客户端]]**      | 真正的网络连接，通过 TCP socket 与服务器通信，是常规的客户端                |
| ==**-1**==        | **[[伪客户端]]**       | 不是真正的网络连接，没有对应的 socket，用于内部操作                       |
| 伪客户端又分为两种         | ==**AOF 载入伪客户端**== | 从 AOF 文件还原数据时使用，载入完毕即销毁                             |
|                   | ==**Lua 脚本伪客户端**== | 执行 Lua 脚本中包含的 Redis 命令时使用，整个服务器生命周期中只有一个，直到服务器关闭才销毁 |

---

### 面试要点

**Q：为什么要把属性分为通用和特定功能两类？**

> 这样设计是为了**节省内存**。每个客户端都需要通信、读命令、返回结果，这些通用属性是必须有的。但很多客户端一辈子都不会执行一次事务或阻塞命令，如果给每个客户端都分配这些结构体，内存浪费会非常严重。所以 Redis 只在需要时才为特定功能分配属性，这和数据库里按需连接是一个道理。

**Q：伪客户端和普通客户端的根本区别是什么？**

> ==**有没有网络连接。**== 普通客户端有真正的 TCP socket，通过 fd 读写数据；伪客户端没有网络连接，它直接在内存中模拟命令的发送和执行。AOF 恢复时用伪客户端，是因为命令来源是 AOF 文件而不是网络请求；Lua 脚本用伪客户端，是因为脚本中的命令本就运行在服务器内部，不需要经过网络层。
