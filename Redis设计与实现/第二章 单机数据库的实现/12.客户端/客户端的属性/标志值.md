### 1. 核心特征

客户端的 `flags` 属性用于 ==**记录客户端的角色以及当前所处的状态**==。

`flags` 的值可以是单个标志，也可以是多个标志通过 ==**二进制位或运算符 `|` 组合而成**==。每个标志都是 `redis.h` 中定义的一个宏常量，对应一个二进制位。这种设计使得一个客户端可以同时拥有多种角色和状态，且判断效率极高（`flags & FLAG_NAME` 即可判断）。

### 2. 标志的分类

`flags` 的属性可以分为两大类：==**角色标志**== 和 ==**状态标志**==。

#### 一、角色标志

记录客户端在整个 Redis 系统中的身份：

| 标志常量                   | 含义                                              |
| ---------------------- | ----------------------------------------------- |
| ==`REDIS_MASTER`==     | 该客户端代表一个**主服务器**（当前实例是它的从节点）                    |
| ==`REDIS_SLAVE`==      | 该客户端代表一个**从服务器**（当前实例是它的主节点）                    |
| `REDIS_PRE_PSYNC`      | 从服务器版本低于 Redis 2.8，不支持 `PSYNC` 命令，只能使用旧版 `SYNC` |
| ==`REDIS_LUA_CLIENT`== | 该客户端是执行 Lua 脚本的**[[伪客户端]]**                     |

**面试要点**：==判断一个客户端是普通客户端还是主/从节点，直接看 `flags` 里有没有 `REDIS_MASTER` 或 `REDIS_SLAVE` 标志即可。== 主从复制的很多逻辑（如命令传播时排除从节点发来的命令）都依赖这个标志位来判断。

#### 二、状态标志

记录客户端当前所处的功能状态：

| 标志常量                          | 含义                                                |
| ----------------------------- | ------------------------------------------------- |
| **==`REDIS_MONITOR`==**       | **客户端正在执行 `MONITOR` 命令，即作为“监视器”接收所有命令的实时日志**      |
| **`REDIS_DIRTY_CAS`**         | **客户端在执行 `WATCH` 后，被监视的键已被其他客户端修改，事务的 CAS 检查将失败** |
| **`REDIS_BLOCKED`**           | **客户端正在被列表阻塞命令（如 `BLPOP`）阻塞等待**                   |
| **`REDIS_UNIX_SOCKET`**       | **客户端通过 Unix 域套接字连接（而非 TCP socket），通常本地通信时使用**    |
| **`REDIS_UNBLOCKED`**         | **客户端已从阻塞状态中脱离**                                  |
| **`REDIS_MULTI`**             | **客户端正在执行事务（已执行 `MULTI`，但尚未执行 `EXEC`）**           |
| **`REDIS_CLOSE_ASAP`**        | **标记客户端应尽快关闭，底层原因可能是输出缓冲区溢出等**                    |
| **`REDIS_CLOSE_AFTER_REPLY`** | **待回复发送完毕后关闭客户端，常用于错误处理**                         |
| **`REDIS_READING_CHANNEL`**   | **表示该客户端是作为集群节点间的消息通道读取端的临时客户端**                  |
| **`REDIS_FORCE_AOF`**         | **强制将当前命令写入 AOF（即使 AOF 持久化是关闭的），用于保证某些关键命令的安全性**  |
| **`REDIS_FORCE_REPL`**        | **强制将当前命令传播给从节点，同样用于关键命令的可靠性保障**                  |
### 三、特殊的命令：PUBSUB 与 SCRIPT LOAD

#### 1. 常规规则

通常情况下，Redis 只会将**对数据库进行了修改**的命令写入 AOF 文件，并复制到各个从服务器。如果一个命令没有对数据库进行任何修改，则会被认为是只读命令，不会保存到 AOF 文件中（这与 AOF 的保存机制有关——[[AOF文件的写入与同步]]），更不会被复制到从服务器里。

#### 2. 例外：有副作用的命令

以上规则适用于绝大多数 Redis 命令，但 ==**PUBSUB 和 SCRIPT LOAD 是例外**==。它们虽然没有直接修改数据库中的键值对，但它们的执行会产生“副作用”，因此必须被持久化和传播。

|命令|副作用|使用的强制标志|标志作用|
|---|---|---|---|
|==**PUBSUB**==|向频道的所有订阅者发送消息，所有接收到消息的客户端状态都会因为这个命令而改变|==`REDIS_FORCE_AOF`==|强制将该命令写入 AOF 文件，使将来重放 AOF 时能产生相同的副作用|
|==**SCRIPT LOAD**==|修改了服务器的 Lua 脚本缓存，改变了服务器状态|==`REDIS_FORCE_AOF`== 和 ==`REDIS_FORCE_REPL`==|前者强制写入 AOF；后者强制传播给所有从服务器，保证主从的脚本缓存一致|

#### 3. 两个强制标志的区别

|标志|作用|
|---|---|
|==`REDIS_FORCE_AOF`==|强制将当前命令写入 AOF 文件，即使 AOF 持久化是关闭的，保证关键命令的副作用可以随 AOF 恢复|
|==`REDIS_FORCE_REPL`==|强制将当前命令传播给所有从节点，保证主从状态一致性|

**面试话术**：判断命令是否要写入 AOF 或传播给从节点，核心是看命令 ==**有没有副作用**==，而不是看它有没有修改数据库里的键。PUBSUB 修改了客户端状态，SCRIPT LOAD 修改了服务器脚本缓存，这些“非键空间”的状态变更同样需要持久化和主从同步。

### 四、flags 的标志示例

根据你补充的例子，以下是一些常见的标志组合：

- **客户端是一个主服务器**：    

    flags = REDIS_MASTER
    
- **客户端正在被列表阻塞命令阻塞**：
    
    flags = REDIS_BLOCKED
    
- **一个从节点客户端正在执行事务，且被阻塞**（多个标志组合）：
    
    
    flags = REDIS_SLAVE | REDIS_MULTI | REDIS_BLOCKED
    
- **一个执行 Lua 脚本的伪客户端，需要强制写 AOF**：
    
    
    flags = REDIS_LUA_CLIENT | REDIS_FORCE_AOF




**为什么 flags 用位运算而不是几个 boolean 字段？**

> 节省内存，一个 `int` 就能表示 32 种状态，而且 **位运算判断状态（`flags & REDIS_BLOCKED`）只需要一条 CPU 指令**，效率比多个 `if` 判断高得多。这种设计在 C 语言的系统编程中非常常见。
