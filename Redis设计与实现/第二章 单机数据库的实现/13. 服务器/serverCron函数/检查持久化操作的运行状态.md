### 一、子进程 ID 记录

服务器状态使用两个属性记录持久化子进程的 ID：

|属性|对应的持久化操作|含义|
|---|---|---|
|==**`rdb_child_pid`**==|BGSAVE|记录执行 RDB 生成的子进程 ID|
|==**`aof_child_pid`**==|BGREWRITEAOF|记录执行 AOF 重写的子进程 ID|

- 如果当前没有执行对应的持久化操作，则属性值设置为 ==**-1**==。
    
- 只要其中一个属性的值不为 -1，就表示服务器正在执行持久化任务。
    

### 二、子进程运行中的检查

每次 `serverCron` 函数执行时，程序都会检查 `rdb_child_pid` 和 `aof_child_pid` 两个属性的值。只要其中有一个不为 -1，程序就会执行一次 ==**`wait3`**== 函数，检查子进程是否有信号发来：

|情况|信号状态|程序行为|
|---|---|---|
|==**有信号到达**==|子进程已结束|**BGSAVE**：用新的 RDB 文件替换旧的 RDB 文件（原子替换，防止操作冗余）  <br>**BGREWRITEAOF**：用重写后的 AOF 文件替换现有的 AOF 文件|
|==**没有信号到达**==|子进程仍在运行|持久化任务未完成，程序不做任何操作|

**补充细节**：`wait3` 是 Linux 系统中用于等待子进程状态变化的系统调用。如果子进程已结束，`wait3` 会返回子进程的 PID 和退出状态，同时清理僵尸进程。Redis 使用的是非阻塞模式调用 `wait3`（传入 `WNOHANG` 参数），因此即使子进程未结束，也不会阻塞主线程。

### 三、无持久化任务时的三个检查

另一方面，如果 `rdb_child_pid` 和 `aof_child_pid` 两个属性都为 -1，表示服务器当前没有在执行任何持久化任务。在这种情况下，程序会依次进行以下三个检查：

|检查项|触发条件|操作|
|---|---|---|
|==**检查 1：BGREWRITEAOF 是否被延迟**==|`aof_rewrite_scheduled == 1`|开始一次新的 BGREWRITEAOF 操作，并将延迟标志清零|
|==**检查 2：自动保存条件是否满足**==|RDB 自动保存条件已触发（如 `save 900 1`）且当前无持久化操作|开始一次新的 BGSAVE 操作|
|==**检查 3：AOF 重写条件是否满足**==|AOF 文件大小超过了重写阈值且当前无其他持久化操作|开始一次新的 BGREWRITEAOF 操作|

### 四、完整状态判断流程图
**serverCron 每次执行**
         **↓**
**检查 `rdb_child_pid` 和 `aof_child_pid`**
         **↓**
    **┌── 至少有一个不为 -1（持久化任务进行中）**
    **│       ↓**
    **│   调用 wait3 检查子进程状态**
    **│       ↓**
    **│   ├── 有信号到达（子进程已结束）**
    **│   │       ↓**
    **│   │   ├── 是 BGSAVE 完成 → 替换 RDB 文件**
    **│   │   └── 是 BGREWRITEAOF 完成 → 替换 AOF 文件**
    **│   │**
    **│   └── 无信号到达（子进程仍在运行）**
    **│           ↓**
    **│       不做任何操作，等待下次 `serverCron`**
    **│**
    **└── 两个都为 -1（无持久化任务进行中）**
            **↓**
        **依次进行三个检查：**
            **↓**
        **① `aof_rewrite_scheduled` == 1？**
           **→ 是 → 开始 BGREWRITEAOF，重置标志**
            **↓**
        **② RDB 自动保存条件满足？**
           **→ 是 → 开始 BGSAVE**
            **↓**
        **③ AOF 重写条件满足？**
           **→ 是 → 开始 BGREWRITEAOF**
            **↓**
        **三个检查完毕，继续 `serverCron` 后续流程**

### 面试要点

**Q：为什么用 `wait3` 而不是 `waitpid`？**

> `wait3` 是 `waitpid` 的变体，区别在于 `wait3` 可以获取子进程的资源使用统计信息（如 CPU 时间、内存使用等）。Redis 利用这些信息来记录持久化操作的耗时和资源开销，便于运维分析。同时，`wait3` 配合 `WNOHANG` 参数实现非阻塞检查，不会阻塞事件循环。

**Q：为什么要等子进程结束才替换文件，而不是在子进程中直接替换？**

> 子进程拥有独立的内存空间，不能直接修改父进程的状态（包括文件描述符表）。文件替换操作需要父进程执行 `rename()` 系统调用，这个操作必须在父进程中完成。因此，子进程只负责生成新文件，完成后通过信号通知父进程，由父进程在 `serverCron` 中统一完成替换和清理工作。

**Q：三个检查的顺序可以调整吗？**

> 这个顺序遵循"**先处理排队任务，再检查新触发条件**"的原则：
> 
> - BGREWRITEAOF 延迟任务（检查 1）优先级最高，因为这是之前被推迟的操作，应该优先执行。
>     
> - 再检查 RDB 自动保存条件（检查 2），因为 RDB 是周期性快照，时效性不如 AOF 重写紧迫。
>     
> - 最后检查 AOF 重写条件（检查 3），因为如果前面已经触发了 BGSAVE，AOF 重写会推迟到下一次 serverCron 再检查。
