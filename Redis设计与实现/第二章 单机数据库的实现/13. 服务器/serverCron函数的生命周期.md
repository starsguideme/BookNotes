==**`serverCron`**== 是 Redis 服务器中最重要的周期性事件，默认以 ==**每 100ms 一次**== 的频率执行。它负责执行服务器运行期间的各项定期维护任务，是维持服务器良好运转的核心，也是一种后台的执行任务。
注：周期性事件的意思是 每隔一段时间都会进行的操作，这在[[时间事件的分类与特点]]中阐述了
---

### 二、serverCron 的核心职责

#### 1. 更新服务器时间缓存

为了减少系统调用的执行次数，Redis 在服务器状态中维护了两个时间缓存属性：

| 属性                 | 精度  | 更新频率     | 适用场景               |
| ------------------ | --- | -------- | ------------------ |
| ==**`unixtime`**== | 秒级  | 100ms 一次 | 日志打印、持久化触发判断等低精度场景 |
| ==**`mstime`**==   | 毫秒级 | 100ms 一次 | 服务器上线时间计算等         |

对于需要 ==**高精度时间**== 的功能（如为键设置过期时间、添加慢查询日志），服务器仍然会执行系统调用来获取最准确的当前时间。

**设计原则**：==**在性能足够的前提下用缓存的近似值，当业务语义要求精确性时才执行系统调用。**==

详见：[[更新服务器的时间缓存]]

---

#### 2. 更新 LRU 时钟

服务器状态中的 ==**`lruclock`**== 属性保存了服务器的 LRU 时钟，每 ==**10 秒**== 更新一次。

- 每个 Redis 对象都有一个 `lru` 属性，记录该对象最后一次被访问的时间。
    
- 计算空转时间：==**空转时间 = lruclock - 对象的 lru 属性**==。
    
- 由于 `lruclock` 每 10 秒才更新一次，所以计算出的 LRU 空转时间只是一个模糊估算值。
    
- LRU 时钟用于 ==**内存淘汰策略**== 和 `OBJECT IDLETIME` 命令。
    

详见：[[更新LRU时钟]]

---

#### 3. 更新服务器每秒执行命令次数

`serverCron` 中的 `trackOperationsPerSecond` 函数以每 100ms 一次的频率进行抽样计算：

计算方式：
  命令增量 = 当前执行命令总数 - 上次抽样时的命令总数
  时间差 = 当前时间 - 上次抽样时间
  每秒命令数 = (命令增量 / 时间差毫秒) × 1000

- 这个估算值被存入 ==**`ops_sec_samples` 环形数组**==（最多保存 16 个采样值）。
    
- 通过 `INFO stats` 命令的 `instantaneous_ops_per_sec` 域可以查看，它反映的是 ==**最近约 1.6 秒内的平均命令处理速率**==。
    
- 因为是抽样估算而非精确计数，所以**理论上并不精确**。
    

详见：[[更新服务器每秒执行命令次数]]

---

#### 4. 更新服务器内存峰值记录

服务器状态中的 ==**`stat_peak_memory`**== 属性记录了服务器启动以来的内存峰值。

- 每次 `serverCron` 执行时，程序会对比当前已用内存与 `stat_peak_memory` 的值，如果当前值更大就更新该属性。
    
- 可通过 `INFO memory` 命令查看，有两种格式：
    
    - ==**`used_memory_peak`**==：原始字节数。
        
    - ==**`used_memory_peak_human`**==：人类可读格式。
        
- 这个值对于评估服务器内存需求和判断是否需要扩容非常重要。
    

详见：[[更新服务器内存峰值记录]]

---

#### 5. 处理 SIGTERM 信号

服务器启动时会为 `SIGTERM` 信号关联处理器 ==**`sigtermHandler`**== 函数。

- **关键设计**：信号处理器**不直接关闭服务器**，而是仅仅设置 ==**`shutdown_asap = 1`**== 标志位。
    
- **原因**：信号处理器在中断上下文中执行，如果直接执行关闭逻辑可能导致数据不一致或死锁。设置标志位后立即返回，将实际的关闭操作交给主线程在安全的时间点执行。
    
- 每次 `serverCron` 运行时检查 `shutdown_asap`，如果值为 1 则执行优雅关闭流程（停止接收请求、刷盘 AOF/RDB、关闭客户端、释放资源）。
    

详见：[[处理SIGTERM信号]]

---

#### 6. 管理客户端资源

`serverCron` 每次执行都会调用 ==**`clientsCron`**== 函数，对一定数量的客户端分批进行检查：

- ==**释放超时客户端**==：如果客户端与服务器之间的连接已超时（空转时间超过 `timeout` 配置值），则释放该客户端。但主服务器、从服务器、被阻塞的客户端和订阅客户端**不会被释放**。
    
- ==**收缩输入缓冲区**==：如果客户端输入缓冲区过大且长时间未被充分使用，程序会释放当前的输入缓冲区并重新创建一个默认大小的缓冲区，防止内存浪费。
    

详见：[[客户端资源管理]]

---

#### 7. 管理数据库资源

`serverCron` 每次执行都会调用 ==**`databaseCron`**== 函数，对服务器中的一部分数据库进行检查：

- ==**删除过期键**==：执行定期删除策略，随机抽取键检查并删除已过期的键。
    
- ==**收缩字典**==：当哈希表（字典）中删除了很多元素变得过于稀疏时，进行收缩操作，将内存空间还给操作系统。
    

详见：[[数据库的键空间及其操作]]

---

#### 8. 管理持久化子进程

服务器状态使用两个属性记录持久化子进程的 ID：

|属性|对应的持久化操作|
|---|---|
|==**`rdb_child_pid`**==|记录执行 BGSAVE 的子进程 ID|
|==**`aof_child_pid`**==|记录执行 BGREWRITEAOF 的子进程 ID|

- 如果没有执行对应的持久化操作，则属性值为 ==**-1**==。
    

**子进程运行中的检查**：只要 `rdb_child_pid` 或 `aof_child_pid` 有一个不为 -1，程序会调用 ==**`wait3`**== 函数检查子进程状态：

- ==**有信号到达**==：表示子进程已完成，RDB 文件或 AOF 文件已生成完毕，服务器执行文件替换等后续操作。
    
- ==**无信号到达**==：表示持久化任务未完成，不做任何操作。
    

**无持久化任务时的三个检查**：如果 `rdb_child_pid` 和 `aof_child_pid` 均为 -1，程序依次检查：

1. ==**是否有 BGREWRITEAOF 被延迟**==（`aof_rewrite_scheduled == 1`）→ 开始 BGREWRITEAOF
    
2. ==**RDB 自动保存条件是否满足**== → 开始 BGSAVE
    
3. ==**AOF 重写条件是否满足**== → 开始 BGREWRITEAOF
    

**BGSAVE 与 BGREWRITEAOF 的互斥机制**：

- 在 BGSAVE 执行期间，如果收到 BGREWRITEAOF 命令，该命令会被 ==**延迟**== 到 BGSAVE 执行完毕（设置 `aof_rewrite_scheduled = 1`）。
    
- 在 BGREWRITEAOF 执行期间，如果收到 BGSAVE 命令，该命令会被 ==**直接拒绝**==（因为 BGSAVE 可由 `save` 配置自动触发）。
    
- **设计原因**：避免两个子进程同时运行导致的 ==**磁盘 I/O 竞争**== 和 ==**内存翻倍风险**==（写时复制机制下，两个子进程同时存在会导致内存可能翻倍）。
    

详见：[[执行被延迟的AOF重写命令]]

---

#### 9. AOF 缓冲区的定期写入

如果服务器开启了 AOF 持久化功能且 AOF 缓冲区（`aof_buf`）中还有待写入的数据，`serverCron` 会调用相应程序将缓冲区内容写入到 AOF 文件中。

**与事件循环的 AOF 写入形成双重保障**：

- ==**主路径**==：事件循环每次迭代结束前，`flushAppendOnlyFile` 写入。
    
- ==**补充路径**==：`serverCron` 每 100ms 检查一次，防止服务器空闲时数据在缓冲区停留过久。
    

详见：[[AOF文件的写入与同步]]、[[将AOF缓冲区中的内容重写到AOF文件]]

### 三、命令执行流程（所有章节的串联核心）

除了 `serverCron` 的各项周期性职责外，第14章还展示了 ==**一条命令从发送到回复的完整执行流程**==，它把所有前序章节串联了起来：
客户端发送命令
    ↓
**①`readQueryFromClient` 读取（第12章 事件）**
    **↓**
**② 解析 `querybuf` → `argv/argc`（第13章 客户端）**
    **↓**
**③ 命令表查找 → `cmd 指针`（第13章 客户端）**
    **↓**
**④ 预备操作：身份验证、参数校验、内存检查等（第14章 服务器）**
    **↓**
**⑤ 调用 `cmd`->proc(client) 执行（第14章 服务器）**
    **↓**
**⑥ 后续工作：慢查询日志、统计更新、AOF 写入、主从传播（第14章 服务器）**
    **↓**
**⑦ 命令回复 → 输出缓冲区 → sendReplyToClient（第12章 事件 + 第13章 客户端）**

详见：[[命令请求的执行过程]]

### 四、面试要点总结

| **考点**                              | **回答要点**                                           |
| ----------------------------------- | -------------------------------------------------- |
| **`serverCron` 的执行频率**              | **默认 100ms 一次**                                    |
| **`serverCron` 的核心职责**              | **时间缓存、LRU 时钟、内存峰值、信号处理、客户端管理、数据库管理、持久化触发、AOF 写入** |
| **为什么 LRU 时钟 10 秒更新一次**             | **LRU 淘汰是近似算法，不需要精确时间，10 秒更新足以满足需求且开销最低**          |
| **BGSAVE 和 BGREWRITEAOF 为什么不能同时执行** | **磁盘 I/O 竞争 + 内存翻倍风险**                             |
| **信号处理器为什么不直接关闭服务器**                | **信号处理器在中断上下文中执行，直接关闭可能导致数据不一致或死锁**                |
| **一条命令的完整执行流程**                     | **读取 → 解析 → 查找 → 预备操作 → 执行 → 后续工作 → 返回结果**         |
