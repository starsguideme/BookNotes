**命令执行器（2）：执行预备操作**

在真正执行命令之前，服务器已经收集齐了执行命令所需的全部信息：

|信息|存储位置|说明|
|---|---|---|
|命令实现函数|客户端的 ==**cmd**== 属性|指向 `redisCommand` 结构体|
|命令参数|客户端的 ==**argv**== 属性|字符串对象数组|
|参数个数|客户端的 ==**argc**== 属性|`argv` 数组的长度|

但在真正调用 `cmd->proc(client)` 之前，还需要执行一系列预备操作，确保命令能够正确、安全地执行。这些操作按照"开销从小到大"排列，共十个检查点：

---

**一、检查 cmd 指针是否为 NULL**

服务器检查客户端状态的 `cmd` 指针是否指向 `NULL`。如果为 `NULL`，说明用户输入的命令名字在命令表中找不到对应的命令实现。服务器不再执行后续步骤，直接向客户端返回错误信息：`"ERR unknown command '...'"`。

**二、检查参数个数是否正确**

服务器根据 `redisCommand` 结构中的 ==**`arity`**== 属性，检查命令请求所给定的参数个数是否正确。

|arity 值|含义|检查逻辑|
|---|---|---|
|正数（如 `2`）|参数个数固定|`argc == arity` 才合法|
|负数（如 `-3`）|参数数量可变，绝对值是最小参数个数|`argc >= \|arity\|` 才合法|

如果参数个数不正确，服务器直接向客户端返回错误信息。

**三、检查身份验证**

服务器检查客户端的 ==**`authenticated`**== 属性。如果 `authenticated == 0`（未通过身份验证），该客户端 ==**只能执行 `AUTH` 命令**==，其余所有命令都会被拒绝。

**四、检查内存占用（maxmemory）**

如果服务器打开了 `maxmemory` 功能，在执行命令之前先检查服务器的内存占用情况。如果内存超出限制，服务器会尝试进行内存回收。

- 回收成功 → 继续执行。
    
- 回收失败 → 返回 `"OOM"` 错误信息。
    

只有 `sflags` 中包含 ==`m`== 标志的命令才会触发此检查。

**五、检查 BGSAVE 错误状态**

如果服务器上一次执行 `BGSAVE` 命令时出错，并且满足以下三个条件，服务器将拒绝执行当前命令：

1. `stop-writes-on-bgsave-error` 配置为 `yes`（默认开启）。
    
2. 上一次 `BGSAVE` 执行失败。
    
3. 当前命令是 ==**写命令**==（`sflags` 中包含 `w` 标志）。
    

**六、检查发布/订阅状态**

如果客户端当前正在使用 `SUBSCRIBE` 命令订阅频道，或正在使用 `PSUBSCRIBE` 命令订阅模式，那么服务器 ==**只会执行以下四个命令**==：

|允许执行的命令|说明|
|---|---|
|`SUBSCRIBE`|订阅频道|
|`PSUBSCRIBE`|订阅模式|
|`UNSUBSCRIBE`|退订频道|
|`PUNSUBSCRIBE`|退订模式|

除这四个命令外，其他所有命令都会被服务器拒绝。

**七、检查数据载入状态**

如果服务器正在进行数据载入（如从 RDB 或 AOF 文件恢复数据），只有带有 ==**`l` 标识**==（loading）的命令才会被服务器执行，例如 `INFO`、`SHUTDOWN`、`PUBLISH` 等。其他命令都会被拒绝。

**八、检查 Lua 脚本阻塞状态**

如果服务器因为执行 Lua 脚本超时而进入阻塞状态，那么服务器 ==**只会执行以下两个命令**==：

|允许执行的命令|说明|
|---|---|
|==**`SHUTDOWN NOSAVE`**==|不进行持久化直接关闭服务器|
|==**`SCRIPT KILL`**==|杀死当前正在运行的 Lua 脚本|

其他命令都会被服务器拒绝，直到脚本执行完毕或被杀死。

**九、检查事务状态**

如果客户端正在执行事务（即已执行 `MULTI` 命令），那么服务器 ==**只会执行以下四个命令**==：

|允许立即执行的命令|说明|
|---|---|
|`EXEC`|执行事务队列中的所有命令|
|`DISCARD`|取消事务，清空事务队列|
|`MULTI`|开启事务|
|`WATCH`|监视键，用于事务的 CAS 检查|

除这四个命令外，所有其他命令都会被放入 ==**事务队列（`mstate`）**== 中，等待 `EXEC` 时一并执行。

**十、通知监视器**

如果服务器打开了监视器功能（有客户端执行了 `MONITOR` 命令），那么服务器会将当前正要执行的命令及其参数信息发送给所有监视器客户端。==**这一步不管命令最终是否执行成功都会做**==，确保监视器能收到所有命令请求的实时日志。

---

### 预备操作完整流程图

**客户端状态准备完毕（cmd / argv / argc）**
         **↓**
**① cmd == NULL？ → 是 → 返回 "unknown command"**
         **↓ 否**
**② argc 不满足 arity 要求？ → 是 → 返回 "wrong number of arguments"**
         **↓ 否**
**③ authenticated == 0 且命令不是 AUTH？ → 是 → 返回 "NOAUTH"**
         **↓ 否**
**④ maxmemory 开启且内存不足且无法回收？ → 是 → 返回 "OOM"**
         **↓ 否**
**⑤ BGSAVE 出错 + stop-writes + 当前是写命令？ → 是 → 返回 "MISCONF"**
         **↓ 否**
**⑥ 客户端处于 Pub/Sub 状态，命令不在四个允许命令中？ → 是 → 拒绝执行**
         **↓ 否**
**⑦ 服务器正在载入数据，命令没有 `l` 标识？ → 是 → 拒绝执行**
         **↓ 否**
**⑧ Lua 脚本超时阻塞，命令不是 SHUTDOWN NOSAVE / SCRIPT KILL？ → 是 → 拒绝执行**
         **↓ 否**
**⑨ 客户端处于事务状态，命令不是 EXEC/DISCARD/MULTI/WATCH？ → 是 → 放入事务队列**
         **↓ 否**
**⑩ 通知监视器（如有）**
         **↓**
**进入命令执行阶段 → 调用 cmd->proc(client)**
