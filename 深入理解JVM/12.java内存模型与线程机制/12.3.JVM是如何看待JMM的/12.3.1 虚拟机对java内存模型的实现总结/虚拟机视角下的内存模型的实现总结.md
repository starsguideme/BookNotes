

### 一、`JMM` 的核心：三大性质与一个规则

虚拟机视角下的 Java 内存模型是一个可被执行的规范，其中[[java内存模型下的三大核心性质]]和一个核心规则确保了并发的实现。

**三大核心性质**：

| 性质 | 说明 |
|------|------|
| ==**原子性**== | 单次操作的完整性与正确性，要么全部执行，要么全部不执行 |
| ==**可见性**== | 一个线程修改了共享变量的值，其他线程能够立即得知这个修改 |
| ==**有序性**== | 程序按照代码的先后顺序执行，通过内存屏障和锁来限制重排序 |

这三点确保了在并发情况下的程序可以被正确执行，而这三点也均是基于 **happens-before** 这一核心规则来实现的。

**happens-before 规则** 是 `JMM` 的核心规则，支撑先行发生原则实现的共有八条规则（程序次序规则、管程锁定规则、volatile 变量规则、线程启动规则、线程终止规则、线程中断规则、对象终结规则、传递性）。这些规则确保了先行发生原则的执行。

### 二、`JMM` 与 `JVM` 的关系：规范与实现

`JMM` 是一个规范，而不是一个可以直接执行的规则。在具体实现的过程中，仍然依靠虚拟机来执行。虚拟机本身有着自己的内存操作——[[内存间的交互操作]]（lock、unlock、read、load、use、assign、store、write 共八种原子操作）。

这些交互操作可以与 `JMM` 中的 happens-before 规则相结合，使得` JVM` 在遵循 `JMM` 规范的基础上，能够通过具体的底层机制（内存屏障、锁语义、Monitor 等）将规范落地执行。详见[[虚拟机视角下的先行发生原则]]。

```text
JMM（规范层）
    ↓ 定义规则
happens-before 规则（核心规则层）
    ↓ 依赖实现
JVM 的内存交互操作 + 内存屏障（实现层）
    ↓ 提供给开发者
volatile / synchronized / Lock（应用层）
```

### 三、volatile：连接规范与实现的桥梁

happens-before 规则本身是无法被直接调用的，于是就有了 volatile 这一个关键字。volatile 的本质是一个轻量级的同步机制，它通过结合先行发生原则与[[内存屏障]]的方式来让线程之间可以正确完成并发操作。

虽然 volatile 可以完成这些功能，但其也有自己的一些只属于它自己的某些规则，大致如下：

| volatile 的特殊规则 | 说明 |
|-------------------|------|
| ==**Load 与 use 必须连用**== | 保证工作内存中的变量值始终是最新的，读取的都是主内存中的最新值 |
| ==**assign 与 store 必须连用**== | 保证每次修改都能立即同步回主内存，让其他线程可见 |
| ==**write 后必须触发后续的 Load**== | 形成完整的数据通路，保证可见性——先 assign → store → write，然后其他线程 Load → use |

详见[[volatile字段的特殊规则]]。

### 四、volatile 解决了什么问题？

随着 volatile 的出现，也一并解决了 Java 内存模型中主内存与工作内存相互之间交涉的问题。如果没有 volatile 的实现，则线程之间是不可见的——线程 A 对共享变量的修改存在于自己的工作内存中，线程 B 无法看到这个修改。

一旦不可见就会带来以下问题：

| 问题 | 说明 |
|------|------|
| ==**数据不一致**== | 线程 B 读到的是旧值，基于旧值进行后续操作，导致数据错误 |
| ==**效率低下**== | 为了保证数据一致，可能需要频繁地使用锁，增加了线程阻塞和上下文切换的开销 |
| ==**缓存一致性问题**== | 多个线程的工作内存（对应不同 CPU 核心的缓存）持有同一个变量的不同副本，无法自动同步 |

详见[[主内存与工作内存下的不同]]
volatile 通过内存屏障和 happens-before 规则，强制将修改后的值刷新到主内存，并使其他线程的缓存副本失效，从而解决了上述问题。但 volatile 不能替代锁——它只保证可见性和单次读写的原子性，不保证复合操作的原子性。
