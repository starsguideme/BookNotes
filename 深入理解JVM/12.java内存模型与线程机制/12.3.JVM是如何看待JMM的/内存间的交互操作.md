### 一、8 种原子操作

JMM 定义了 8 种原子操作，用于描述主内存与工作内存之间的具体交互协议：

|操作|作用域|说明|
|---|---|---|
|==**lock**==|主内存|把一个变量标识为一条线程独占的状态|
|==**unlock**==|主内存|把一个处于锁定状态的变量释放出来，释放后的变量才可以被其他线程锁定|
|==**read**==|主内存|把主内存中的变量值读取到工作内存中，以方便后续的 load 操作|
|==**load**==|工作内存|把 read 操作从主内存中得到的变量值放入工作内存的变量副本中|
|==**use**==|工作内存|把工作内存中一个变量的值传递给执行引擎，每当虚拟机需要使用这个变量时都会执行此操作|
|==**assign**==|工作内存|把执行引擎中的一个变量值赋给工作内存中的变量，每当虚拟机需要给变量赋值时都会执行此操作|
|==**store**==|工作内存|把工作内存中的变量值传输到主内存中，以方便后续的 write 操作|
|==**write**==|主内存|把 store 操作从工作内存中得到的变量值放入主内存的变量中|

### 二、操作之间的顺序要求

内存之间的操作顺序也起到了很关键的作用：

- 如果要把主内存中的变量值拷贝到工作内存中，就必须**先执行 read 操作，后执行 load 操作**。
    
- 如果要把变量从工作内存中同步回主内存中，就必须**先执行 store 操作，后执行 write 操作**。
    

这些操作只需要保证按照顺序执行，但可以在这些操作中间夹杂其他的操作。这是因为 JMM 中具有数据的**传递性原则**——先执行的程序对后执行的程序是一定具有可见性的。

### 三、8 条基本规则

除了以上的内存交互操作之外，JMM 还规定了以下 8 条规则：

**规则 1**：不允许 read 和 load、store 和 write 操作之一单独存在。即不允许一个内存变量从主内存读取到工作内存时，只执行 read 而不执行 load，或者只执行 store 而不执行 write。

**规则 2**：不允许一个线程丢弃它最近的 assign 操作。即工作内存中的变量被修改之后，必须将修改结果同步回主内存，以保证数据的一致性。

**规则 3**：不允许一个线程无缘故地把数据从工作内存中同步到主内存中。**（这条规则的真正含义是：只有在变量被 assign 修改之后，才需要同步回主内存。如果变量没有被修改，就不需要无意义地刷回主内存。这是一种性能优化——避免不必要的写回操作，减少内存带宽消耗。）**

**规则 4**：一个新的变量只能在主内存中创建，不允许工作内存中使用未执行初始化的变量。这是因为在未执行初始化操作之前，工作内存中的该变量是根本没有具体地址的，需要被 JVM 分配空间之后才可以被使用，否则可能导致内存泄漏或访问异常。由此得到，在执行 use 和 store 操作之前，必须先执行 assign 和 load 操作。

**规则 5**：一个变量在同一个时刻只允许一条线程对其加上锁（互斥锁）。但锁操作可以被同一个线程反复执行多次（即**可重入锁**）。**（lock 操作的意义是标记变量被某线程独占。同一线程可以多次 lock，每 lock 一次计数器加 1，每次 unlock 计数器减 1，只有计数器归零时锁才真正释放。这就是 `synchronized` 可重入性的底层依据。）**

**规则 6**：如果一个变量事先没有被 lock 锁定，那么就不能对它执行 unlock 操作。而且 unlock 操作只能对线程内部使用，无法跨线程使用——只有持有锁的线程才能释放锁。

**规则 7**：对一个变量在执行 unlock 之前，必须先把工作内存中的变量同步到主内存中。**（这正是 JMM 保证可见性的核心规则——释放锁时，必须将工作内存中的所有修改刷新到主内存，让后续获取锁的线程能读到最新值。如果在 unlock 之前没有同步数据，一旦释放锁的同时线程没有机会执行剩下的代码且线程中有写操作，就会带来数据不一致的问题。）**

**规则 8**：由于这些操作实在是过于繁琐，同时还要保证数据的可靠性，JMM 便使用了一个更高层次的规则——**happens-before 规则**。这一规则在《Java并发编程的艺术》中已经被详细描述。由于 happens-before 规则中线程内部之间具有数据的传递性、数据的依赖性等原则，确保了在单线程下的有序性（哪怕是被重排序了）。

### 四、8 种操作与 happens-before 的关系

JMM 定义了 8 种原子操作和 8 条规则来描述内存交互的底层细节，但这些规则非常繁琐。happens-before 规则是 JMM 提供的**更高层次的抽象**——程序员只需要理解 happens-before 规则（如 volatile 写 happens-before volatile 读，释放锁 happens-before 获取锁），就能写出正确的并发代码，而不需要关注底层的 read/load/store/write 等具体操作。
