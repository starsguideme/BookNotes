
**线程调度的开销与协程的演进**

### 一、线程调度的开销来源

线程调度的浪费来源于用户态与内核态的状态转换开销，而这种转换的开销来源于**响应中断、保护和恢复线程执行的成本**。整个切换过程如下：

```text
线程 A → 系统中断 → 保存线程 A 的上下文 → 恢复线程 B 的上下文 → 线程 B
```

**上下文在不同视角下的含义**：

| 视角 | 上下文的内容 |
|------|------------|
| ==**开发视角**== | 方法调用过程中的各种局部变量与资源 |
| ==**线程视角**== | 方法的调用栈中存储的各类信息，即栈区与 TLAB 中的各种对象 |
| ==**操作系统与硬件视角**== | 存储在内存、缓存和寄存器中的一个个具体数值 |

由于物理硬件的各种 I/O 设备与寄存器在操作系统中都会被模拟成可被共享的资源，因此如果在线程执行的过程中发生中断，就需要把线程 A 的上下文数据保存下来，再恢复线程 B 的上下文数据，并加以维护。这种任务必定是一种**重量级的操作**。以上是内核线程会带来的核心问题。

### 二、用户线程的演进：从早期到协程

如果使用的是用户线程呢？早期的用户线程同样不能降低开销。由于用户线程完全是由开发者自己调度，会带来**栈的互相纠缠**问题，也不支持多线程操作。

随着用户线程的发展，最终演化成[[线程调度的分类#二、协同式调度]]，因此其也有个别名叫做**协程（`Coroutine`）**。

协程根据实现方式可以分为两类：

| 类型 | 别名 | 特点 |
|------|------|------|
| ==**有栈协程**== | Stackful Coroutine | 每个协程拥有自己独立的调用栈，可以在任意嵌套函数中挂起和恢复，实现较重量 |
| ==**无栈协程**== | Stackless Coroutine | 不依赖独立栈，通过状态机或 CPS（Continuation-Passing Style）变换实现，是一种很轻量级的协程 |

### 三、协程的优势与局限

| 维度 | 说明 |
|------|------|
| ==**优势**== | 轻量级，创建和切换开销极小，不需要用户态与内核态之间的切换，能支持海量并发 |
| ==**局限**== | 实现很复杂，需要开发者自己管理调度逻辑，且操作系统内核无法感知协程的存在 |
| ==**一般实现方式**== | 协程一般都是用协同式的线程来实现的，虽然也有其他协程方式，但协同式调度是主流 |

具体到了虚拟机上的实现，又有许多规则与麻烦需要处理——比如 JVM 的 HotSpot 默认使用内核线程的 1:1 模型，而 Java 的虚拟线程（Project Loom）则是在 JVM 层面实现了协程的支持。

### 四、适用范围

| 场景 | 推荐方案 | 说明 |
|------|---------|------|
| ==**高并发 I/O 密集型**== | 协程（用户线程） | 如 Web 服务器、API 网关等海量短连接场景，协程能大幅降低线程切换开销 |
| ==**CPU 密集型任务**== | 内核线程 | 需要长时间占用 CPU 的计算任务，内核线程能充分利用多核优势 |
| ==**需要隔离性的任务**== | 内核线程 | 某个线程可能崩溃但不能影响其他线程的场景 |
| ==**Java 后端开发**== | 虚拟线程（Project Loom） | Java 19+ 引入的虚拟线程，本质上是在 JVM 层面实现的协程，兼顾开发效率与性能 |

### 五、面试要点

| **问题**              | 回答                                            |
| ------------------- | --------------------------------------------- |
| **线程调度的开销来源**       | ==**用户态与内核态的切换**==，包括保存和恢复上下文的成本              |
| **上下文在不同视角下的含义**    | 开发视角看局部变量，线程视角看栈区和 TLAB，OS 视角看内存/缓存/寄存器中的数值   |
| **协程和有栈协程/无栈协程的关系** | 协程是用户态线程的演化，有栈协程有独立调用栈，无栈协程通过状态机实现            |
| **协程的优势和局限**        | 优势是轻量级、高并发；局限是实现复杂，需要开发者自己管理调度                |
| **Java 是否支持协程**     | Java 19+ 引入虚拟线程（Project Loom），本质是在 JVM 层面实现协程 |
