
### 一、互斥与同步的关系

互斥同步是一种常见也是最主要的正确并发保障手段。其中[[临界区]]、[[互斥量]]和[[信号量]]都是常见的互斥实现方式。因此：

```text
互斥是实现同步的方式，同步是互斥的结果
```

### 二、`synchronized` 的实现机制

在 Java 中，互斥同步是靠 `synchronized` 关键字与 `Lock` 等块结构的同步语法来实现的。`synchronized` 经过编译之后，会在同步块前后形成 **`monitorenter`** 和 **`monitorexit`** 这两个字节码指令。这两个字节码指令都需要一个 `reference` 类型的参数来指明锁定与解锁的对象，根据是否指定的方式来判断对象引用是什么，来决定是对对象实例还是 `Class` 对象执行上锁。

根据规范的要求，在执行 `monitorenter` 指令时，首先要去尝试获取对象的锁。如果这个对象没有被上锁或是线程已经拥有对象的锁，就会把锁的计数器 **+1**。而在执行 `monitorexit` 指令时，计数器值会 **-1**。一旦计数器的值为 0，就代表锁被完全释放了。但此时如果释放失败，则说明线程被阻塞了，进入线程的 BLOCKED 状态，需要被其他线程解锁后通知该线程继续执行。

### 三、`synchronized` 的两个重要特性

| 特性 | 说明 |
|------|------|
| ==**可重入性**== | `synchronized` 修饰的同步块对同一条线程来说是可被多次执行的，这代表着同一线程反复进入同步块中不会产生由死锁导致的阻塞状态 |
| ==**无条件阻塞**== | 被 `synchronized` 修饰的同步块在持有锁的线程执行完毕并释放锁之前，会无条件地阻塞在后面其他线程的进入，这意味着**无法强制释放锁，也无法强制中断等待和设置超时退出** |

### 四、`synchronized` 的重量级本质

持有锁（使用 `synchronized`）是一个**重量级**的操作。由于 Java 的线程是映射到操作系统的原生内核线程之上的，如果要阻塞或唤醒一条线程，需要操作系统来帮忙，这就不可避免地需要从**用户态切换到内核态**。

这会带来以下的开销：

| 开销类型 | 说明 |
|---------|------|
| ==**处理器时间**== | 系统调用的执行本身需要消耗 CPU 时间 |
| ==**上下文切换时间**== | 线程切换时保存和恢复上下文状态的开销 |
| ==**寻址操作**== | 线程状态数据在内存中的读写开销 |

Java 为了避免由于使用这些操作导致大规模的资源浪费，就会使用**自旋等待**的方式来降低切换核心的情况。自旋等待就是在用户态反复尝试获取锁，而不是立即进入内核态阻塞，从而减少上下文切换的频率。

### 五、`ReentrantLock`：非块结构的互斥同步

从 JDK 5 之后，由于使用 `synchronized` 过于繁琐的情况，开发团队就在 JUC 包下的锁接口下引入了一种新的以**非块结构**存在的互斥同步手段——`Lock` 接口。在这个手段中有一个很重要的实现方式，也是常用的实现方式，其为**重入锁（`ReentrantLock`）**。

`ReentrantLock` 与 `synchronized` 的对比：

**相同点**：都是以互斥的方式来实现同步的结果，用法也大致类似。

**不同点**：`ReentrantLock` 比 `synchronized` 多了三个高级功能：

| 高级功能 | 说明 |
|---------|------|
| ==**等待可中断**== | 在处理需要长时间执行任务过程中需要临时中断的场景，可通过 `lockInterruptibly()` 实现 |
| ==**公平锁**== | 以线程请求锁的时间顺序来安排将锁优先给谁。可通过构造函数指定，但会对吞吐量产生巨大影响 |
| ==**锁绑定多个条件**== | 在只有一把锁的情况下同时使用多个条件对象（`Condition`），实现更精细的线程调度 |

### 六、`synchronized` 与 `ReentrantLock` 的使用场景

| 场景 | 推荐方案 | 说明 |
|------|---------|------|
| ==**线程较少、代码简单**== | `synchronized` | 清晰简单，更加熟悉，锁可以被自动释放，锁拥有者对 JVM 来说是可知的 |
| ==**线程较多、需要高级功能**== | `ReentrantLock` | 需要等待可中断、公平锁、绑定多个条件等高级特性 |
| ==**性能差异**== | 无需纠结 | 随着 JDK 的更新，两者的性能差异已经不是主要考虑因素 |

### 七、适用范围

| 适用场景 | 说明 |
|---------|------|
| ==**简单同步需求**== | 使用 `synchronized`，代码简洁，自动释放锁，不易出错 |
| ==**需要可中断的锁获取**== | 使用 `ReentrantLock.lockInterruptibly()`，适合长时间任务需要取消的场景 |
| ==**需要公平锁**== | 使用 `ReentrantLock(true)`，适合对线程执行顺序有严格要求的场景 |
| ==**需要多个条件变量**== | 使用 `ReentrantLock` + `Condition`，实现更精细的线程等待/通知机制 |
| ==**需要超时获取锁**== | 使用 `ReentrantLock.tryLock(timeout)`，避免无限期阻塞 |

### 八、面试要点

| **问题**                      | 回答                                           |
| ----------------------- | -------------------------------------------- |
| **互斥和同步的关系**                | ==**互斥是实现同步的方式，同步是互斥的结果**==                  |
| **`synchronized` 的可重入性**    | 同一线程反复进入同步块**不会产生死锁**                        |
| **`synchronized` 的无条件阻塞**   | ==**无法强制释放锁，也无法强制中断等待和设置超时退出**==             |
| **`ReentrantLock` 的三个高级功能** | ==**等待可中断、公平锁、锁绑定多个条件**==                    |
| **两者使用场景的区别**               | 简单场景用 `synchronized`，需要高级功能用 `ReentrantLock` |
