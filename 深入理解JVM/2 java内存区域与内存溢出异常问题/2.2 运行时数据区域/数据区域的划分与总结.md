### 一、整体架构

`JVM` 在执行 Java 程序的过程中会将其所管理的内存划分为几个不同的数据区域，这些区域都有各自的用途以及创建和销毁时间。

有的区域随着 `JVM` 进程的启动一直存在，如**堆**中的全局变量和类的对象实例。有些则依赖用户线程的启动和结束而建立和销毁，如**虚拟机栈**中的局部变量表（通常所说的"栈"就是指这里）和**程序计数器**。

整个运行时数据区由**执行引擎**负责与共享区域交互，而栈和程序计数器则由**本地库接口**与具体的本地方法实现关联。

### 二、各区域的具体划分

| 区域                | 是否线程共享         | 生命周期                    |
| ----------------- | -------------- | ----------------------- |
| ==**[[堆区]]**==    | ==**是**==，线程共享 | JVM 启动时创建，所有线程共享        |
| ==**[[方法区]]**==   | ==**是**==，线程共享 | JVM 启动时创建，存储类信息、常量、静态变量 |
| ==**[[虚拟机栈]]**==  | **否**，线程私有     | 与线程同生命周期，每个方法执行时创建栈帧    |
| ==**[[程序计数器]]**== | **否**，线程私有     | 每个线程独立拥有一份，记录当前执行位置     |
| ==**[[本地方法栈]]**== | **否**，线程私有     | 与虚拟机栈类似，为本地方法服务         |
|                   |                |                         |

### 三、方法区和堆为什么是线程共享的？

**不是因为内部自动使用了 volatile 关键字。**

方法区和堆是线程共享的，因为它们存储的是**所有线程都需要访问的公共数据**——类的元信息、静态变量、对象实例。如果每个线程都复制一份，内存浪费极大。

至于多线程共享带来的可见性和有序性问题，是由 **JMM 的同步机制**（`volatile`、`synchronized`、happens-before 规则）来保证的，而不是内存区域本身具备同步能力。方法区和堆"只是存储空间"，本身不负责线程安全。加不加锁、用不用 volatile，是程序员在访问这些共享数据时自己决定的。

### 四、线程私有的区域为什么独立？

虚拟机栈、程序计数器、本地方法栈之所以线程私有，是因为它们记录的是**每个线程自己的执行状态**——当前执行到哪一行、调用了哪些方法。这些信息各线程独立，不需要共享，也不能共享。这些私有区域通过**内存屏障的隔离**，确保线程之间互不干扰。

### 五、程序计数器详解

程序计数器是一块较小的内存空间，可以看作当前线程所执行的 Class 字节码的**行号指示器**。它负责控制程序的执行流程，支持分支、循环、跳转、异常处理和线程恢复等功能。

==**线程切换后能继续正确执行，靠的不是自动加锁，而是程序计数器的值。**== 每个线程都有自己独立的程序计数器，记录当前线程执行到哪一行字节码。线程被挂起时，这个值被保存下来；线程恢复时，JVM 根据这个值继续从上次断点执行。

**为什么执行 native 方法时计数器为空？** 程序计数器记录的是 JVM 字节码指令的地址。native 方法是 C/C++ 写的，在 JVM 外部执行，不存在 JVM 字节码，也没有对应的字节码地址可以记录，所以置为空。

### 六、虚拟机栈详解

与程序计数器一样，Java 的虚拟机栈也是**线程私有**的，它的生命周期与线程相同。虚拟机栈描述的是正在执行的 Java 方法的内存模型——==**`JMM` 的工作内存，在 `JVM` 中最重要的承载体就是虚拟机栈**==。

每个方法被执行的时候，JVM 会同步地创建一个**栈帧**，用于存储局部变量表、操作数栈、动态链接、方法出口等信息。每一个方法被调用到执行完毕的过程，就对应着一个栈帧在虚拟机栈中从入栈到出栈的过程。

**为什么用栈帧而不是独立空间？** 因为方法的调用天然具有"先调用后返回"的 LIFO 特性。用栈来管理最自然——入栈对应方法调用，出栈对应方法返回。栈帧在栈上的分配和释放几乎是零成本的——入栈时移动一下栈顶指针，出栈时再移回去，不需要 GC 参与。

**局部变量槽（Slot）** 是局部变量表的最小存储单元，每个 Slot 占 32 位，能存放 `boolean`、`byte`、`char`、`short`、`int`、`float`、`reference` 和 `returnAddress` 共 8 种类型。`long` 和 `double` 是 64 位的，占用两个 Slot。局部变量槽的大小在编译期就确定好了——方法中有多少个局部变量、每个变量的类型是什么，编译后是一目了然的。

虚拟机栈可能抛出两种异常：

|异常|触发条件|
|---|---|
|==**StackOverflowError**==|线程请求的栈深度大于 JVM 允许的最大深度（如无限递归）|
|==**OutOfMemoryError**==|JVM 的虚拟机栈在自动扩容时，无法向内存申请到足够的所需空间|

### 七、本地方法栈

本地方法栈与虚拟机栈所发挥的作用非常类似，其核心区别在于：

|栈类型|服务对象|
|---|---|
|==**虚拟机栈**==|为 JVM 执行 **Java 方法**（字节码）服务|
|==**本地方法栈**==|为 JVM 使用到的 **native 方法**服务|

其他特点——线程私有、生命周期与线程相同、可能抛出 `StackOverflowError` 和 `OutOfMemoryError`——均与虚拟机栈一样。当 Java 程序调用 `Thread.start()` 等 native 方法时，底层就是通过本地方法栈来执行对应的 C/C++ 代码。

### 八、堆区详解

堆是虚拟机所管理的内存中最大的一块。Java 堆是被**所有线程共享**的一块内存区域，在虚拟机启动时创建。此内存区域的唯一目的是**存放对象实例**——Java 世界里几乎所有的对象和数组都存储在堆区。

由于 Java 的堆是垃圾收集器管理的内存区域，因此也被称为**`GC` 堆**。从回收内存的角度看，现代` GC` 大部分基于**分代收集理论**设计，将堆分为新生代和老年代，以不同的策略回收不同生命周期的对象。

从分配内存的角度看，所有线程共享的 Java 堆中可以划分出多个**线程私有的分配缓冲区（`TLAB`，Thread Local Allocation Buffer）**。`TLAB` 的设计是为了提升对象分配的效率——线程在自己的私有缓冲区中分配对象，无需加锁，只有缓冲区用完了才需要向共享堆区申请新的空间。

此外，随着逃逸分析和栈上分配等优化技术的发展，对象并不一定都分配在堆上——某些生命周期短且不会逃逸出方法的对象，可能直接在虚拟机栈上分配，方法结束自动销毁，无需 GC 介入。

目前在主流的 JVM 版本中，堆区是可以根据需求来实现扩展的（通过 `-Xms` 和 `-Xmx` 参数设置初始值和最大值）。但扩展取决于两个条件——堆中是否还有空闲空间，以及堆区是否还能继续扩展。如果堆区中没有任何可回收的实例对象，且堆区无法再次扩展时，JVM 会抛出 `OutOfMemoryError` 异常。

### 九、方法区详解

[[方法区]]与堆区一样，是各个线程共享的内存区域。它用于存储被 JVM 加载的类型信息、常量、静态变量、即时编译器编译的代码缓存等数据。

**为什么方法区又叫"非堆"？** 这两个概念是从不同维度说的。说它是"堆的逻辑部分"，是因为从内存管理上看，它和堆一样是线程共享的，都归 GC 管。把它叫做"非堆"，是为了让程序员知道：**它和堆不一样，别指望它能像堆一样频繁分配和回收对象。** 你平常 `new` 出来的对象全在堆里，方法区放的是类的结构信息，这些东西很少变动。"非堆"的称谓是为了提醒开发者：这两个区域虽然都是共享的，但用途和管理方式完全不同，需要分开配置内存参数。

**永久代 vs 元空间**：永久代是早期 `HotSpot` 对方法区的具体实现，在` JVM` 内部有固定上限，易 `OOM`。元空间是 `JDK` 8 之后取而代之的方案，存储位置从 `JVM` 内部移到了**堆外直接内存**，默认只受系统可用内存限制。原来配置永久代的参数 `-XX:PermSize` 和 `-XX:MaxPermSize` 直接作废，改成了 `-XX:MetaspaceSize` 和 `-XX:MaxMetaspaceSize`。

方法区的` GC` 回收条件极其苛刻——必须同时满足该类的所有实例已被回收、加载该类的 `ClassLoader` 已被回收、该类的 Class 对象没有任何地方被引用，三个条件缺一不可。因此方法区的回收成功率远低于堆区。

### 十、运行时常量池

Class 文件中的常量池存放的是编译期生成的各种字面量与符号引用。类加载完成后，这个常量池被搬进方法区，变成**运行时常量池**。

运行时常量池具有**动态性**——不仅包含编译期确定的常量，运行时也可以通过 `String.intern()` 等方法将新的常量放入池中。这意味着，并非所有常量都必须在编译期就确定，程序在运行时也可以向常量池中添加新的内容。

由于运行时常量池是方法区的一部分，它的内存也受方法区大小的限制。当常量池中的常量过多，无法再申请到新的内存时，会抛出 `OutOfMemoryError`。

### 十一、直接内存

直接内存并非是 `JVM` 运行时数据区域的一部分，也不是 JVM 规范中定义的内存区域。它是在 `JDK 1.4` 之后加入的 `NIO` 类中引入的一种基于通道与缓冲区的 I/O 方式。

直接内存的核心优势是**避免了 Java 堆和 Native 堆之间的数据来回复制**。在传统 I/O 中，数据需要从操作系统内核缓冲区先拷贝到 Java 堆中的缓冲区，然后才能被 Java 程序处理——这涉及两次拷贝，以及用户态与内核态的频繁切换。而 `NIO` 使用直接内存后，数据可以直接从内核缓冲区写入堆外内存，Java 程序通过存储在堆中的 `DirectByteBuffer` 对象来操作这块内存，省去了中间的拷贝环节。

由于直接内存存在于 Java 堆之外，它不受 `JVM `堆大小的限制（不归 `-Xmx` 管）。但它仍然是内存，一定会受到本机总内存大小和操作系统自身内存需求的限制。如果直接内存加上 JVM 堆内存的总和超出了物理内存的限制，就会出现 `OutOfMemoryError` 异常。
