**运行时常量池溢出与元空间参数**

### 一、运行时常量池与方法区的关系

由于运行时常量池是方法区的一部分，所以这两个区域的溢出异常其实可以看成同一个对象的溢出异常。在 JDK 8 之后，方法区中的永久代已经被元空间彻底代替，其中一个原因就是内存溢出的问题。

### 二、`String.intern()` 的作用与版本差异

在 JVM 中有个 `String.intern()` 方法，这个方法的作用是判断常量池中是否存在这个 String 类的字符串，如果有则返回这个对象的引用，如果没有会将这个 String 类对象添加至常量池中，然后返回这个 String 类对象的引用。

此操作在不同 JDK 版本中的行为有明显差异：

| JDK 版本 | 方法区实现 | `intern()` 行为 |
|---------|----------|----------------|
| ==**JDK 6 及之前**== | 永久代 | 首次出现的字符串会被**复制一份**放入永久代中的常量池，并返回池中的引用。即使堆中的原对象被 GC 回收，池中的副本依然存在 |
| ==**JDK 7**== | 永久代（但常量池已迁移） | 常量池被移到了堆中，`intern()` 不再复制对象，而是直接在常量池中**记录堆中对象的引用**。如果堆中对象被 GC 回收，常量池中对应的引用也会失效 |
| ==**JDK 8 及之后**== | 元空间 | 常量池依然在堆中，`intern()` 行为与 JDK 7 一致。元空间只存类元数据，不存字符串常量 |

### 三、为什么 JDK 6 及之前容易 OOM？

在 JDK 6 及之前的版本中，`String.intern()` 会把字符串**复制一份**放入永久代中的常量池。永久代的大小是固定的（由 `-XX:PermSize` 和 `-XX:MaxPermSize` 控制），如果程序中大量调用 `intern()` 往常量池中添加字符串，永久代很快就会被撑满，抛出 `OutOfMemoryError: PermGen space`。

这就是为什么 JDK 7 要把常量池从永久代移到堆中——堆的空间通常比永久代大得多，而且可以动态扩展，大大降低了常量池溢出的风险。到了 JDK 8，永久代被彻底移除，元空间存储在直接内存中，只受系统可用内存的限制，常量池的 OOM 问题基本得到解决。

### 四、示例代码

```java
import java.util.HashSet;
import java.util.Set;

public class InternOOM {
    public static void main(String[] args) {
        Set<String> set = new HashSet<>();
        short i = 0;
        while (true) {
            set.add(String.valueOf(i++).intern());
        }
    }
}
```

这段代码在不同 JDK 版本中会抛出不同的异常：

| JDK 版本    | 异常信息                                | 原因                                |
| --------- | ----------------------------------- | --------------------------------- |
| JDK 6 及之前 | `OutOfMemoryError: PermGen space`   | `intern()` 把字符串复制到永久代，永久代空间固定，被撑满 |
| JDK 7     | `OutOfMemoryError: Java heap space` | 常量池在堆中，`HashSet` 和常量池都在堆里，堆先满     |
| JDK 8 及之后 | `OutOfMemoryError: Java heap space` | 同 JDK 7，元空间不存字符串常量，只有类元数据在元空间     |

### 五、元空间的核心参数

| 参数                                  | 作用                                                  | 默认值                       |
| ----------------------------------- | --------------------------------------------------- | ------------------------- |
| **==`-XX:MaxMetaspaceSize`==**      | 设置元空间的最大值                                           | 默认 `-1`（不限制），只受本地内存空间大小限制 |
| **==`-XX:MetaspaceSize`==**         | 指定元空间的初始大小，以字节为单位。达到该值就会触发 GC 进行类型的卸载，同时收集器会对该值进行调整 | 默认约 21MB（因平台而异）           |
| **==`-XX:MinMetaspaceFreeRatio`==** | GC 之后，控制元空间**最小**剩余容量的百分比。如果剩余空间低于此值，会适当增加元空间大小     | 默认 40                     |
| **==`-XX:MaxMetaspaceFreeRatio`==** | GC 之后，控制元空间**最大**剩余容量的百分比。如果剩余空间高于此值，会适当减少元空间大小     | 默认 70                     |

**参数调整逻辑**：

-   如果 `GC` 释放了大量空间，收集器会适当地**减少**分配给元空间的大小，避免内存浪费。
-   如果 `GC` 只释放了少量空间，收集器会在不超过 `-XX:MaxMetaspaceSize` 的前提下，适当地**增加**分配给元空间的大小，以减少因元空间不足导致的频繁 GC。

`-XX:MinMetaspaceFreeRatio` 和 `-XX:MaxMetaspaceFreeRatio` 正是用来控制这种调整行为的——前者防止元空间太小导致频繁 GC，后者防止元空间太大造成内存浪费。

### 六、面试要点

| 问题 | 回答 |
|------|------|
| `String.intern()` 在不同 JDK 版本中的行为差异 | JDK 6 复制到永久代；JDK 7+ 在堆中记录引用 |
| 为什么 JDK 7 要把常量池移到堆中 | ==**避免永久代 OOM**==，堆空间更大且可动态扩展 |
| JDK 8 元空间取代永久代的原因之一 | ==**永久代大小固定，容易 OOM**==；元空间在直接内存，受系统内存限制 |
| 元空间有哪些核心参数 | `-XX:MetaspaceSize`（初始大小）、`-XX:MaxMetaspaceSize`（最大值）、`-XX:MinMetaspaceFreeRatio`（最小剩余比例）、`-XX:MaxMetaspaceFreeRatio`（最大剩余比例） |
| 元空间参数调整的逻辑 | GC 后剩余空间少则扩容，剩余空间多则缩容，由 Min/Max FreeRatio 控制 |
