
### 一、方法区GC回收的两部分

方法区GC回收主要是两部分：**废弃的常量**和**不再使用的类型**。

### 二、废弃常量的回收

回收废弃常量与堆区中即将被回收的对象是非常类似的。判断一个常量是否已经不再被调用是简单的——就是内存中没有任何其他地方引用了这个常量，就说明其已经不再被调用，可以在下次GC时被回收。

### 三、不再使用的类型的回收条件

但要判断的是**不再被使用的类**就需要满足以下三种条件：

| 条件 | 说明 |
|------|------|
| ==**该类所有的实例都已经被回收**== | Java堆中不存在该类及其所有派生子类的任何实例 |
| ==**加载该类的类加载器已经被回收**== | 这个条件除非是经过精心设计的可替换类加载器的场景，否则较难达成 |
| ==**该类对应的Class对象没有任何地方被引用**== | 无法通过任何方式（包括反射）去访问该类的方法 |

以上是在JVM中被允许回收的类所需满足的基本条件。但**满足不一定是肯定回收**——这还需要对JVM进行额外设置（如 `-Xnoclassgc` 参数控制是否对类进行回收）。

### 四、频繁自定义类加载器场景

一般情况下，在频繁自定义类加载器的场景中（如JSP动态加载、OSGi模块化框架等），通常都需要让JVM具有基本的**自动的类卸载能力**，否则会给GC在回收方法区时产生巨大的内存压力。

### 五、面试要点

| 问题            | 回答                                  |
| ------------- | ----------------------------------- |
| **方法区GC回收哪两部分**   | ==**废弃的常量**和**不再使用的类型**==           |
| **判断类不再使用的三个条件**  | ==**所有实例已回收、类加载器已回收、Class对象无处引用**== |
| **满足三个条件一定会被回收吗** | ==**不一定**==，还需要JVM参数支持              |
| **什么场景需要自动类卸载能力** | 频繁使用**自定义类加载器**的场景，如JSP、OSGi        |
