
### 一、两次标记过程

即使之前在[[可达性分析算法与GC根节点]]中判定到了存在不可到达的对象节点，但其也不是一定会被 GC 回收的，因为他们还没被认定是垃圾。要想让对象被宣告为真死亡时，至少要被**标记为两次**。

### 二、第一次标记与筛选

如果对象没有可达性分析，无法通过与 GC 根节点引用链相连接到达的对象节点，其会被标记为**第一次**，并在这之后会进行下一步的**筛选**。筛选的条件是该对象是否有必要执行 `finalize()` 方法：

| 条件 | 处理方式 |
|------|---------|
| ==**对象没有覆盖 `finalize()` 方法**== | JVM 会将该对象设置为无需被再次使用，即该对象会被下次 GC 时**直接回收** |
| ==**`finalize()` 方法已经被 JVM 调用过**== | 同上，直接回收 |
| ==**对象覆盖了 `finalize()` 方法且未被调用过**== | 该对象被判定为**有必要执行 `finalize()` 方法** |

### 三、F-Queue 队列与 Finalizer 线程

如果该对象被判定为有必要执行 `finalize()` 方法时，该对象会被放置在一个 **`F-Queue` 的队列**中，并在这之后创建一条由 JVM 自动建立并监管、优先度较低的 **`Finalizer` 线程**去执行相应的方法。

这里的"执行"一般是适用于在 JVM 一开始创建线程时使用，但生命周期并非是完全贯彻的。如果遇到 `finalize()` 方法执行较慢时，会导致系统宕机（因为 `Finalizer` 线程是单线程，一个对象的 `finalize()` 执行过慢会阻塞队列中其他对象的处理）。

### 四、第二次标记与自救

此时至于对象是否通过 `finalize()` 方法来标记此对象依旧在某个类中调用时，对象需要将其通过**引用链与 GC 根节点建立连接**。一旦成功地建立连接，说明对象依旧存在于 JVM 的生命周期中，该对象会被移出"即将回收"的集合，完成**自救**。

如果对象在 `finalize()` 方法中没有与 GC Roots 建立连接，则会被第二次标记，随后被 GC 回收。

### 五、完整流程图

```text
对象的死亡判定流程：

① 可达性分析 → 不可达对象
    ↓
② 第一次标记
    ↓
③ 筛选：对象是否覆盖 finalize() 且未被 JVM 调用过？
    ↓
    ├── 否 → 直接回收（下次 GC 时）
    │
    └── 是 → 将对象放入 F-Queue 队列
              ↓
        ④ Finalizer 线程执行 finalize() 方法
              ↓
        ⑤ 对象在 finalize() 中是否与 GC Roots 建立连接？
              ↓
              ├── 是 → 自救成功，对象移出"即将回收"集合
              │
              └── 否 → 第二次标记，随后被 GC 回收
```

### 六、面试要点

| **问题**                       | 回答                                         |
| ------------------------ | ------------------------------------------ |
| **对象被回收前需要经历几次标记**           | ==**两次**==                                 |
| **第一次标记后如何筛选**               | 判断对象是否覆盖了 `finalize()` 方法且未被 JVM 调用过       |
| **F-Queue 队列的作用**            | 存放等待执行 `finalize()` 方法的对象                  |
| **Finalizer 线程的特点**          | ==**优先级较低**==，由 JVM 自动建立并监管，单线程执行          |
| **对象如何自救**                   | 在 `finalize()` 方法中通过**引用链与 GC Roots 建立连接** |
| **`finalize()` 方法执行过慢会导致什么** | 会阻塞 F-Queue 中其他对象的处理，可能导致**系统宕机**          |
