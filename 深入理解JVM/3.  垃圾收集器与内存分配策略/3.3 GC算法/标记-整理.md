
### 一、核心定位

由于[[标记-复制]]算法的特性——在对象存活率较高时既要进行较多的复制操作，其效率会降低，且需要双倍的空间——因此其不能用于老年代。

标记-整理算法的标记方法与[[标记-清除]]类似，但清除方法却完全不同。它不是直接对可回收对象进行清理，而是让所有存活的对象都向同一个内存空间中进行移动，同时清理掉边界以外的内存。

### 二、移动对象的代价

在移动对象的过程中，更新所有引用对象是一种巨大的任务。因为这种类型的操作不仅需要**全部暂停正在工作的用户线程**（STW），还得考虑各种开销，这就涉及到了**内核操作**，因此其一定是**内核态任务**。

| 代价 | 说明 |
|------|------|
| ==**必须STW**== | 移动对象过程中需要暂停所有用户线程，保证数据一致性 |
| ==**需要内核态操作**== | 涉及系统调用，需要从用户态切换到内核态 |
| ==**需要更新所有引用**== | 所有指向被移动对象的引用都需要更新为新地址 |

### 三、不移动对象的代价

在进行此操作的时候如果不考虑移动和整理存活对象时，会导致大量的存活对象分布在内存中的各个角落。这时候就需要系统级的**内存分配器和内存访问器**来解决，这让本就很吃紧的用户态切换到内核态的访问资源变得更加雪上加霜。如果此时碰巧给这个操作增加了额外的负担——如对象定位、对象移动、切割并分配对象空间等——必然会直接影响到系统给予应用软件的吞吐量，导致**软件卡顿**。

| 代价              | 说明                        |
| --------------- | ------------------------- |
| ==**内存分配复杂化**== | 碎片化导致无法使用简单的指针碰撞，必须使用空闲列表 |
| ==**频繁系统调用**==  | 碎片化导致更频繁的内核态/用户态切换        |
| ==**影响吞吐量**==   | 额外负担（对象定位、切割分配等）导致软件卡顿    |

### 四、移动与不移动的权衡

基于以上两点，无论是否移动对象都有其相应的缺点：

| 选择 | 分配空间 | GC回收 | 吞吐量 | 适用场景 |
|------|---------|--------|--------|---------|
| ==**不移动对象**== | 变得更复杂（空闲列表） | GC更快 | 较低 | 需要**低延迟**的场景（如CMS） |
| ==**移动对象**== | 简单（指针碰撞） | 回收更复杂 | ==**更高**== | 需要**高吞吐量**的场景（如Parallel Old） |

从GC的所需时间来看，虽然不移动时GC更快，但对于整个程序的吞吐来说，移动对象反而更高。因此这种算法一般用于处理**吞吐量**，而标记-清除则用于处理需要**较高延迟**的地方。

### 五、面试要点

| **问题**                 | 回答                                       |
| ------------------ | ---------------------------------------- |
| **标记-整理算法的核心原理**       | 将所有存活对象向一端移动，然后**清理掉边界以外的内存**            |
| **为什么移动对象必须STW**       | 需要保证数据一致性，防止用户线程在移动过程中修改引用               |
| **不移动对象的代价**           | 内存碎片化，分配空间变复杂，影响**吞吐量**                  |
| **标记-整理算法适用于哪个区域**     | ==**老年代**==（如Parallel Old、Serial Old收集器） |
| **标记-整理和标记-清除的适用场景区别** | 标记-整理用于追求**高吞吐量**的场景；标记-清除用于追求**低延迟**的场景 |
