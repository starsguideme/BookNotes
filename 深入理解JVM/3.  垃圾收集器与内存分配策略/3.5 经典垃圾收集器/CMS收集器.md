
### 一、核心定位

CMS 是一种以获取**最短回收停顿时间**为目标的收集器，一般是用于互联网网站或基于浏览的 B/S 系统的服务器上，因此 CMS 收集器具有**高响应**的效果。

### 二、CMS 的四个步骤

根据 CMS 的名称可以得出其也是一种基于[[标记-清除]]算法实现的，大致步骤可以分为四个：

| 步骤                                | 说明                                                         | 是否需要 STW       |
| --------------------------------- | ---------------------------------------------------------- | -------------- |
| ==**1. 开始标记（Initial Mark）**==     | 仅仅只是标记一下 GC 根节点能**直接关联到**的对象，因此其速度很快                       | ==**需要**==（短暂） |
| ==**2. 并发标记（Concurrent Mark）**==  | 从 GC 根节点像遍历有向图一样，遍历时需要大量的时间但**不需要停顿用户线程**，还可以与 GC 线程一起并发执行 | **不需要**        |
| ==**3. 重新标记（Remark）**==           | 修正并发标记期间因用户线程继续运行而导致的标记变动的记录                               | ==**需要**==（短暂） |
| ==**4. 并发清除（Concurrent Sweep）**== | 并发清除未标记的对象                                                 | **不需要**        |

从开始标记到并发清除，这一系列的操作均是**并发型**的，甚至其 GC 过程可以与用户线程一起执行。

### 三、CMS 的优点

CMS 在并发处理垃圾对象的时候具有很强的作用，其最大的优势就是**低延迟**——用户线程在 GC 期间不需要长时间停顿，适合对响应速度有高要求的场景。

### 四、CMS 的三个核心缺点

| 缺点                        | 说明                                                                                                                                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ==**对处理器资源敏感**==          | CMS 收集器的默认回收线程数是 `(处理器核心数 + 3) / 4`。如果处理器核心数是 4 个及以上，并发回收的线程占用随处理器核心数的增加而降低；如果不足 4 个，CMS 的处理速度会由于算力不足导致性能大幅度下降。因此诞生了 **i-CMS**（增量式 CMS），与 CMS 一样的工作方式，虽然会增加收集时间但可以减少对线程的影响，但实践证明处理时间反而增加了，因此被废弃                     |
| ==**无法处理浮动垃圾，可能产生并发失败**== | 由于 CMS 并发标记与清除的阶段用户线程依旧在运行，程序在运行自然就还会有新的垃圾对象产生，但这一部分对象是出现于标记过程结束以后，所以 CMS 无法处理它们（即**浮动垃圾**）。也由于这个特性导致在 GC 时依旧需要给用户线程预留一部分空间，如果不遵守这个规则设置了过高的回收阈值，会导致并发失败后 JVM 会暂停所有用户线程，并使用 **Serial Old 收集器**来重新进行老年代的收集，因此花的时间反而更长 |
| ==**基于标记-清除导致内存碎片**==     | 基于标记-清除的特性导致其在 GC 时会产生大量的**不连续的微小空间碎片**。碎片太多，当一个大对象要晋升老年代时找不到连续空间，触发 Promotion Failed → JVM 被迫用 Serial Old 做一次 Full GC 来整理碎片                                                                                        |

### 五、面试要点

| 问题             | 回答                                              |
| -------------- | ----------------------------------------------- |
| CMS 收集器的目标     | ==**最短回收停顿时间**==，追求低延迟                          |
| CMS 的四个步骤      | ==**初始标记 → 并发标记 → 重新标记 → 并发清除**==               |
| CMS 基于哪种算法     | ==**标记-清除**==                                   |
| CMS 的三个核心缺点    | ==**对处理器资源敏感、无法处理浮动垃圾、产生内存碎片**==                |
| 什么是浮动垃圾        | 并发标记和清除期间，用户线程继续运行产生的**新垃圾对象**，CMS 无法在本次 GC 中处理 |
| CMS 出现并发失败时会怎样 | 会使用 **Serial Old 收集器**进行 Full GC，STW 时间反而更长     |
