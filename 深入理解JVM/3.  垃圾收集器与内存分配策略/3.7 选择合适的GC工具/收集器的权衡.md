
### 一、三个核心考量维度

| 维度             | 说明                                                             |
| -------------- | -------------------------------------------------------------- |
| ==**吞吐量**==    | 吞吐量 = 用户代码运行时间 / (用户代码运行时间 + GC 时间)，吞吐量越高表示 CPU 用于处理业务的时间越多    |
| ==**硬件问题**==   | 考虑服务器核心数、内存大小、操作系统的架构（如 64 位）以及 JVM 是否支持该收集器                   |
| ==**JDK 版本**== | 不同的收集器有版本要求，如 `Shenandoah` 需要 JDK 12+，`ZGC` 需要 JDK 15+ 才正式生产可用 |

### 二、各收集器的对比

| 收集器 | 目标 | 算法 | 适用场景 |
|--------|------|------|---------|
| ==**Serial**== | 简单高效 | 标记-复制（新生代） | 单核 CPU，客户端模式 |
| ==**ParNew**== | 多线程新生代回收 | 标记-复制（新生代） | 多核 CPU，与 CMS 配合 |
| ==**Parallel Scavenge**== | 高吞吐量 | 标记-复制（新生代） | 后台计算型任务，对停顿不敏感 |
| ==**Serial Old**== | 老年代单线程回收 | 标记-整理（老年代） | 单核 CPU，客户端模式 |
| ==**Parallel Old**== | 高吞吐量老年代回收 | 标记-整理（老年代） | 与 Parallel Scavenge 配合 |
| ==**CMS**== | 最短停顿时间 | 标记-清除（老年代） | 互联网网站，B/S 系统 |
| ==**G1**== | 可预测的停顿时间模型 | 整体标记-整理，局部标记-复制 | 服务端应用，JDK 9 默认收集器 |
| ==**Shenandoah**== | 极低延迟 | 并发复制 | 需要极低停顿的大堆应用 |
| ==**ZGC**== | 超大堆低延迟 | 并发整理 | 超大堆（TB 级），要求极低延迟 |
| ==**Epsilon**== | 无操作 | 只分配内存，不回收 | 性能测试、短生命周期应用 |

### 三、不同场景的推荐

| 场景                       | 推荐收集器                                | 原因              |
| ------------------------ | ------------------------------------ | --------------- |
| ==**CPU 密集型后台计算**==      | `Parallel Scavenge` + `Parallel Old` | 追求高吞吐量，对停顿不敏感   |
| ==**Web 服务器 / API 网关**== | `G1`                                 | 低延迟与高吞吐量的平衡     |
| ==**需要极低延迟的金融系统**==      | `Shenandoah` 或 `ZGC`                 | 停顿时间极短（10ms 级别） |
| ==**单核或小内存环境**==         | `Serial` + `Serial Old`              | 简单高效，没有线程切换开销   |
| ==**超大堆（TB 级）**==        | `ZGC`                                | 停顿时间不随堆大小增长而增加  |

| **什么场景用 G1**                | ==**Web 服务器**==，低延迟与高吞吐量的平衡       |
| **什么场景用 ZGC**               | ==**超大堆（TB 级）**==，要求极低延迟          |
| **什么场景用 Serial**            | ==**单核 CPU 或客户端模式**==，简单高效        |
