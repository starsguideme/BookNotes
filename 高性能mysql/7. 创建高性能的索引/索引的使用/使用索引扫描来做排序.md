
### 一、两种生成有序结果的方式

在 MySQL 中有两种方式可以生成有序的结果：通过**排序操作**或按照**索引顺序扫描**。如果在 `Explain` 的输出中，`type` 列的值是 `index`，则说明 MySQL 使用了索引扫描来做排序。

### 二、索引扫描的代价

通过扫描索引，可以快速查找到紧挨着的记录。但如果索引不能覆盖查询所需的全部列，那么就可能需要**回表**，使用全表扫描来获取未被索引覆盖的列。这本质上的行为都是**随机 I/O**。因此按索引顺序读取所需的时间通常情况下是要比全表扫描要久的，尤其是在高 I/O 下。

### 三、单表与多表查询的索引排序规则

**单表查询**：当索引的顺序和排序的顺序是完全一致的时候，并且所有列的排序方向都一样时，MySQL 才可以使用索引来对结果进行排序。

**多表查询**：则只有当 `ORDER BY` 子句引用的字段**全部在第一个表中**时，才可以使用索引排序。且排序子句和查询子句的限制也应是一样的，都需要满足**最左前缀要求**，否则 MySQL 会使用排序操作而不是索引排序。

### 四、前导列为常量时的例外

凡事皆有例外。如果前导列是**常量**的时候，排序子句中的列也可以**不满足索引的最左前缀**。比如在使用了条件筛选或 `JOIN` 关键字中的子句将这些列指定为了常量，就可以填充索引字段中的间隙。

因此，在正常的排序命令中哪怕没有满足索引的最左前缀要求，也可以用于查询排序，这是因为索引的第一列已经被指定成了常量。

### 五、满足最左前缀的两种方式

| 方式 | 说明 |
|------|------|
| ==**ORDER BY 下第一列为常量 + 第二列**== | 第一列是常量，第二列成为新的最左前缀 |
| ==**ORDER BY 下前两列都是最左前缀**== | 前两列都满足最左前缀要求 |

### 六、不能使用索引排序的两种情况

| 情况 | 说明 |
|------|------|
| ==**排序方式不统一**== | 有的列是升序（ASC），有的列是降序（DESC），排序方向不一致 |
| ==**引入了不在索引列中的列**== | `ORDER BY` 中包含了索引范围之外的列 |

### 七、索引排序的性能对比

| 排序方式 | 适用场景 | 优势 | 劣势 |
|---------|---------|------|------|
| ==**索引排序**== | 排序条件满足索引顺序，且列排序方向一致 | 数据**已经有序**，无需额外排序操作，性能极高 | 受限于索引定义，排序方向必须统一 |
| ==**文件排序（filesort）**== | 无法利用索引排序时 | 灵活性高，支持任意排序 | 需要**额外内存或磁盘**进行排序，性能较低 |

MySQL 的 `filesort` 有两种模式：如果排序数据量较小，在**内存**（`sort_buffer`）中完成排序；如果排序数据量过大，则使用**磁盘临时文件**进行排序，性能会急剧下降。

### 八、`Explain` 中的 `Extra` 字段解读

| `Extra` 显示 | 说明 |
|-------------|------|
| ==**`Using index`**== | 使用了**覆盖索引**，不需要回表，性能最优 |
| ==**`Using index; Using filesort`**== | 虽然使用了索引，但**排序无法利用索引**，需要额外排序 |
| ==**`Using filesort`**== | 无法使用索引排序，需要**文件排序**，性能较差 |
| ==**`Using temporary`**== | 使用了**临时表**，性能较差，需要优化 |
