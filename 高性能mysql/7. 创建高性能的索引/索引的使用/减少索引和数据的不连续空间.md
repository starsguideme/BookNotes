
### 一、碎片化的影响

因为 MySQL 常使用的索引是 B 树，在使用 B 树的过程中可能会产生大量的**碎片**，这会显著地降低查询效率。碎片化的索引可能会以很差或无序的方式存储在磁盘上。

根据设计，B 树索引需要**随机磁盘访问**才能定位到叶子页，因此随机访问几乎无可避免，且对物理空间上的**顺序和紧密型**要求是**越高则性能越好**，反之，则可能会遇到性能瓶颈。

### 二、三种碎片类型

在查询的过程中，表的数据存储可能会发生碎片化。然而数据存储的碎片化却比索引的要复杂得多，大致可以分为三类：

| 碎片类型           | 说明                  | 影响                                      |
| -------------- | ------------------- | --------------------------------------- |
| ==**行碎片**==    | 数据行被存储在多个地方的多个片段中   | 即使只从索引中访问一行记录，性能也会大幅度下降，因为可能会触发**全表扫描** |
| ==**行间碎片**==   | 逻辑上页或行连续，在硬盘上却不是连续的 | 行间碎片对**全表扫描**和[[聚簇索引]]扫描之类的操作有很大影响      |
| ==**剩余空间碎片**== | 数据页中有大量的空余空间        | 会导致服务器读取大量**不必要的空间资源**，从而造成浪费           |

### 三、碎片化的解决方案

以上的三种碎片的解决方法是通过 **`OPTIMIZE TABLE`** 或**导出后再导入**的方式来整理数据。这适用于多级索引。

但如果索引不支持 `OPTIMIZE TABLE` 这个功能，可以通过一个**空的 `ALTER TABLE`** 来重建表，并将该表的存储引擎改成当前引擎即可。

**语法**：

```sql
ALTER TABLE 表名 ENGINE 引擎名;
```

| 方案                       | 说明                                   |
| ------------------------ | ------------------------------------ |
| ==**`OPTIMIZE TABLE`**== | 整理表碎片，减少不连续空间，适用于大多数引擎               |
| ==**导出后再导入**==           | 通过导出数据并重新导入，间接重建表和索引                 |
| ==**空的 `ALTER TABLE`**== | 通过 `ALTER TABLE 表名 ENGINE 引擎名` 重建表结构 |

### 四、面试要点

| 问题                       | 回答                                          |
| ------------------------ | ------------------------------------------- |
| **数据存储碎片化分哪三类**              | ==**行碎片、行间碎片、剩余空间碎片**==                     |
| **行碎片的危害**                   | 可能导致**全表扫描**，性能大幅度下降                        |
| **行间碎片的危害**                  | 对**全表扫描**和聚簇索引扫描有很大影响                       |
| **剩余空间碎片的危害**                | 读取大量**不必要的空间资源**，造成浪费                       |
| **如何解决碎片化**                  | 使用 `OPTIMIZE TABLE`、导出再导入、或空的 `ALTER TABLE` |
| **`OPTIMIZE TABLE` 不适用时怎么办** | 使用 ==**`ALTER TABLE 表名 ENGINE 引擎名`**== 重建表  |
