
### 一、为什么需要索引统计信息？

如果存储引擎提供的**扫描行数信息不够准确**，亦或者**执行计划本身太复杂**以至于无法正确地匹配各个阶段的行数，那么优化器会使用**索引统计信息**来估算扫描行数。一般情况下，都是使用 **`ANALYZE TABLE`** 来重新生成统计信息，以此来解决这个问题。

### 二、ANALYZE TABLE 的作用

当使用了 `ANALYZE TABLE` 之后，会产生大量的索引信息。其中需要重点关注的是**索引列的基数（Cardinality）**。

| 概念 | 说明 |
|------|------|
| ==**基数（Cardinality）**== | 显示了存储引擎**估算**索引列有多少个**不同的取值**。基数越大，说明索引的区分度越高，优化器越倾向于使用该索引 |

### 三、InnoDB 统计信息的抽样计算

在 MySQL 默认情况下，通常使用的是 **InnoDB** 引擎。该引擎有个特点，其会通过**抽样**的方式来计算统计信息：

1.  首先会**随机读取少量的索引页面**。
2.  然后以此为**样本**来计算索引的统计信息。

这种方式可以避免全表扫描的开销，但统计结果是一个**近似值**，不是精确值。

### 四、InnoDB 首次使用时的全表更新问题

在 InnoDB 下，首次使用 InnoDB 引擎时会尝试**更新全表**。而更新全表时，轻则浪费大量资源，重则会直接让服务器宕机。

因此可以尝试关闭 **`innodb_on_metadata`** 来避免此操作。通过关闭该参数，可以防止在首次访问元数据时触发全表统计信息更新。

### 五、面试要点

| 问题                     | 回答                              |
| ---------------------- | ------------------------------- |
| **优化器如何估算扫描行数**            | 使用 ==**索引统计信息**==               |
| **如何重新生成索引统计信息**           | 使用 ==**`ANALYZE TABLE`**==      |
| **什么是基数（Cardinality）**     | 索引列**不同取值的数量**，基数越大，索引区分度越高     |
| **InnoDB 如何计算统计信息**        | 通过 ==**抽样**==，随机读取少量索引页面作为样本    |
| **如何避免首次使用 InnoDB 时的全表更新** | 关闭 ==**`innodb_on_metadata`**== |
