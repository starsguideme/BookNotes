**1. 根据合理的需求创建多列索引**

**2. 索引合并策略**  
MySQL 引入了一种叫**索引合并（Index Merge）** 的优化策略，可以在一定程度上使用表中的多个单列索引来定位需要的行。  
在这种情况下，查询能够同时对多个单列索引进行扫描，并将扫描结果进行合并。该算法有三种形式：

- **交集合并（Intersection）**：用于多个 `AND` 条件
    
- **并集合并（Union）**：用于多个 `OR` 条件
    
- **组合合并**：前两者的混合形式
    

**3. 索引合并不是万能的 —— 往往是索引设计糟糕的信号**

**3.1 交集合并（AND 条件）**  
当优化器对多个索引做交集操作时，**通常意味着需要一个包含所有相关列的多列索引**，而不是多个独立的单列索引。

**3.2 并集合并（OR 条件）**  
当优化器对多个索引做并集合并时，往往需要在算法的缓存、排序和合并操作上耗费大量 CPU 和内存资源，特别是当某些索引的选择性不高时，需要合并扫描并返回大量数据。

**4. 索引合并 ≠ 性能优化**  
虽然索引合并可以避免全表扫描，但它通常意味着：

- 索引设计不够合理
    
- 或者查询条件写得不够理想
    
- 在某些版本或场景下，索引合并甚至可能比全表扫描更慢（如对大量数据进行并集合并）
    

> ✅ 更优方案：
> 
> - 对于 `AND` → 优先使用**多列索引**
>     
> - 对于 `OR` → 尽量避免让多个不同列的 `OR` 条件触发并集合并，必要时可改为 `UNION` 或重构索引
 **5. 如何判断索引合并是好是坏？**

- 使用 `EXPLAIN`，重点关注：
    
    - `Extra` 列是否出现 `Using intersect(...)` 或 `Using union(...)`
        
    - `type` 是否仍为 `index_merge` 而不是 `ref`
        
- 如果发现频繁触发**并集合并**且查询很慢，应优先考虑：
    
    - 是否可以用 `IN` 替代部分 `OR`
        
    - 是否可以用 `UNION` 手动拆分并控制结果集
        
    - 是否可以设计覆盖更多条件的多列索引，避免索引合并触发
6. 如果使用EXPLAIN命令时看到有索引合并，应该检查查询语句的写法和结构，这时可以通过optimizer_switch来关闭索引合并功能，还可以使用IGNORE INDEX语法让优化器忽略某些索引，从而避免触发包含索引合并的执行计划
