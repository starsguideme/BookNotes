
### 一、联接查询的本质

在 MySQL 中，**联接**一词指的是几乎所有查询，因此理解什么是联接查询是很有必要的。

该查询方式可以简单理解为 MySQL 对任何联接都会**嵌套循环使用**，即取出单条数据，然后寻找匹配的行，依次下去最后找到所有匹配的数据。所以，**索引确实重要**——联接查询的性能高度依赖索引能否快速定位匹配行。

### 二、执行计划

和其他数据库不同，MySQL 不会生成字节码来执行查询。MySQL 会生成一颗**指令树**，然后通过查询执行引擎完成指令树并返回结果，并确保返回的数据包含了重构查询的全部信息。

在大部分情况下，联接查询是一棵**平衡树**，但 MySQL 却是一棵**左侧深度优先的树**。这意味着 MySQL 的联接执行是从最左边的表开始，逐层深入查找匹配行。

### 三、联接查询优化器

联接查询优化器决定了**多表查询的顺序**。在多联接下，会有多种不同的联接顺序来获得一样的效果。一般情况下其会选择**成本最低**的，但也如[[查询优化器]]一样，有时成本未必最低，且最低时也未必是好事。

根据查询优化器的结果来看，通常情况下 MySQL 会根据实际需求进行优化查询。但由于其特性，导致如果出现查询大量的表时会有 **N 的阶乘**种联接顺序，这会浪费大量空间与时间。

**解决方案**：通过**消除选择**来减少搜索空间，比如说**左连接**和**相关子查询**。之所以这么做是因为，在 MySQL 中一个表的结果依赖于另一个表的检索数据，因此这些联接顺序是固定的，不能被优化器自由调整。

### 四、排序优化

如果出现不能依靠索引来生成排序结果时，MySQL 就需要自行操作。如果数据量小在**内存**执行，如果数据量大就需要使用**磁盘**。不过 MySQL 将这些操作统称为**文件排序（filesort）**，哪怕在内存中并不需要磁盘文件时亦如此。

当被排序的数据小于**排序缓冲区（sort buffer）**时，MySQL 就会使用内存来进行**快速排序**。可如果内存不够，则 MySQL 会将数据**分块**，然后对每个独立的块使用快排进行排序，并将得到的数放入到磁盘上。当所有的数据都已经完成，会将这些数据进行**合并**，最后返回给客户端。

### 五、两种文件排序方法

**1. 两次传输排序（旧版本）**

| 步骤 | 说明 |
|------|------|
| ==**第一次传输**== | 读取**行指针**和需要排序的字段后对其排序 |
| ==**第二次传输**== | 在排序结果中读取所需的数据行 |

**缺点**：需要两次传输操作，且第二次读取的数据已经被第一次读取时被排序，因此第二次读取会产生**大量磁盘 I/O**，排序成本较高。

**2. 单次传输排序（新版本）**

| 步骤 | 说明 |
|------|------|
| ==**读取所需所有列**== | 先读取查询所需要的所有列 |
| ==**根据给定列排序**== | 按指定字段进行排序 |
| ==**直接返回结果**== | 不再需要第二次读取 |

**优点**：因为已经不需要进行两次操作，所以对于具有**密集型 I/O** 来说，此操作的效率高了很多。也因为只需要一次读取，所以其**不会产生任何的随机 I/O**。

**缺点**：会使用**更多的内存**，以此让文件排序必须执行更多的排序合并。

### 六、文件排序的临时空间问题

在 MySQL 中，如果要进行文件排序，其使用的临时空间会很大。原因在于每次排序都会对排序记录分配一个**足够长的定长空间**来存放，这个定长空间必须够长才能容纳其中最长的字符串，哪怕会浪费空间也依然需要定长空间。

因此在联接查询时都需要排序，MySQL 会按照两种情况来处理这种的文件排序：

| 情况 | 处理方式 |
|------|---------|
| ==**`ORDER BY` 子句中的所有列都来自联接的第一个表**== | MySQL 会在**第一个表**进行文件排序 |
| ==**`ORDER BY` 子句中的列来自多个表**== | MySQL 需要在**临时表**中进行排序 |
