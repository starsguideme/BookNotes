
### 一、优化器的核心作用

由[[语法解析器与预处理器]]中提到的**解析树**被合理生成了，并且由**优化器**将其转换成**查询执行计划**。一条查询可以有很多种执行方式，但返回的结果相同。优化器的作用是找到其中**最好的执行计划**。

MySQL 使用了**基于成本的优化器**，它将尝试预测一个查询使用某种计划的成本，并选择其中**成本最小**的一个。

### 二、基于成本的优化器

最初成本的最小单位是**随机读取一个数据页**的成本，但最后引入了一些计算因子来估算某些操作的代价。这些因子根据每张表结构不同而不同，这些因子也会在某些程度上让优化器产生误判。

### 三、优化器的局限性

| 问题 | 说明 |
|------|------|
| ==**统计信息不准确**== | MySQL 服务器依赖**存储引擎**提供的统计信息来评估成本，但并不是所有引擎的信息都是准确的 |
| ==**成本指标不等于实际成本**== | 即使统计数据正确，查询的实际成本也依然可能超过或低于 MySQL 估算的近似值 |
| ==**MySQL 的最优不是实际最优**== | 成本模型的估算结果可能不是真实场景下的最优解 |
| ==**MySQL 从不考虑并发查询**== | 优化器只评估当前查询的成本，不考虑并发运行时的资源竞争 |
| ==**MySQL 并不总是依靠成本进行优化**== | 某些情况下会基于规则进行优化，而不是成本 |
| ==**MySQL 不考虑不受其控制的操作成本**== | 如用户自定义函数（UDF）的调用成本 |
| ==**无法估算所有执行计划**== | 执行计划太多时，优化器不可能全部估算，可能错过最优执行计划 |

### 四、静态优化与动态优化

MySQL 的查询优化器使用了很多种方法来生成最优的执行计划。优化策略简单的可以分为两种：

| 优化类型         | 说明                                                                           | 本质        |
| ------------ | ---------------------------------------------------------------------------- | --------- |
| ==**静态优化**== | 可以直接对**解析树**进行优化，不依赖于任何特别的值，且在第一次完成后就一直生效。即使使用**参数不同且重复**的执行也不会对结果产生**任何影响** | **编译时优化** |
| ==**动态优化**== | 和查询的上下文有关，也可能和其他因素有关，其每次生成的结果会因为种种因素而产生不同的效果                                 | **运行时优化** |

在执行**绑定变量和存储过程**的时候，动态优化和静态优化分别都有独立的重要作用。因此不能搞混淆——MySQL 对静态优化只需执行**一次**，但对动态优化却要根据实际情况来使用。

### 五、优化器的具体优化策略

| 优化策略 | 说明 |
|---------|------|
| ==**重新定义联结表的顺序**== | 数据表的联接并不总是按照在查询中指定的顺序执行，决定联接顺序是优化器一个重要功能 |
| ==**将外联接转化成内联接**== | 并不是所有的 `OUTER JOIN` 语句都以外联接的方式进行，在特定情况下外联接有可能会变成内联接 |
| ==**使用代数等价变换规则**== | MySQL 可以使用一些代数等价变换规则来简化并规范表达式，这可以减少一部分比较，还可以移除一些恒成立和恒不成立的判断 |
| ==**优化 `COUNT`、`MIN` 和 `MAX`**== | 通常可以帮助 MySQL 优化这类表达式。例如，要找到某一列的最小值，只需要查询对应 B 树索引**最左端的记录**，MySQL 可以直接获取索引的第一行记录。在优化器生成执行计划时就可以利用这一点，在 B 树索引中优化器会把这个表达式作为一个**常数**看待 |
| ==**预估并转化为常数表达式**== | 当 MySQL 检测到一个表达式可以转换为常数时，就会一直把该表达式作为常数进行优化处理。第一步是从某表中找到需要的行，如果该表中存在**主键索引**，优化器会知道这是需要的数据，因此优化器在生成执行计划的时候，会通过索引信息知道将返回多少行数据，并将返回数据的类型变成 **`const`**。另一种则是看到常数条件的情况——通过等式将常数值从一个表传到另一个表中，此时可以通过 `WHERE`、`USING` 或 `ON` 语句来限制某列取值为常数 |
| ==**覆盖索引扫描**== | 当索引列中包含查询中需要的列时，MySQL 就可以通过**索引返回需要的数据**，不需要回表 |
| ==**子查询优化**== | MySQL 在某些情况下会将子查询转换成一种效率更高的形式，从而减少多个查询对数据的访问 |
| ==**提前终止查询**== | 当发现已经满足查询需求时，MySQL 会立刻终止查询，比如说使用 `LIMIT` 的时候 |
| ==**等值传播**== | 如果两列的值可以通过**等式联接**，那么 MySQL 能够把其中一列的 `WHERE` 条件传递到另一列上 |
| ==**列表 IN 的比较**== | 在 MySQL 中，`IN` 列表中的数据会**优先进行排序**，然后通过**二分查找**的方式来确定列表中的值是否满足条件 |

以上是优化器的一部分，除此之外其还有大量的其他优化。虽然在实际中，可以默认采用优化器的功能，但如果遇到特殊情况，也依旧需要对其微调，比如说在某些字段加上索引等。

### 六、面试要点

| 问题                 | 回答                                          |
| ------------------ | ------------------------------------------- |
| **MySQL 优化器的作用**       | 将解析树转换成**执行计划**，选择**成本最小**的方案               |
| **MySQL 使用哪种优化器**      | ==**基于成本的优化器**==                            |
| **静态优化和动态优化的区别**       | 静态优化是**编译时优化**，只执行一次；动态优化是**运行时优化**，根据上下文变化 |
| **`MIN` 和 `MAX` 如何优化** | 通过 B 树索引直接获取**最左/最右端的记录**，当作常数处理            |
| **`IN` 列表如何优化**        | 先**排序**，再通过**二分查找**判断                       |
| **`LIMIT` 如何优化**       | 触发**提前终止查询**，发现满足需求后立刻停止                    |
