
### 一、核心思想

可以对每个表进行一次**单表查询**，然后将结果在**应用程序中进行联接**。

### 二、分解联接的优势

| 优势                  | 说明                                                     |
| ------------------- | ------------------------------------------------------ |
| ==**让缓存的效率更高**==    | 单表查询结果更容易被缓存复用，因为单表数据的变更频率远低于多表联接结果                    |
| ==**减少锁竞争**==       | 将查询分解后，执行单个查询可以减少锁的竞争，每个查询锁的范围更小                       |
| ==**更容易对数据库进行拆分**== | 在应用层做联接，可以更容易对数据库进行拆分，更容易做到高性能和可扩展                     |
| ==**查询本身的效率提升**==   | 使用 `IN` 代替联接查询，可以让 MySQL 按照 ID 顺序进行查询，这也比随机 I/O 更高效    |
| ==**减少冗余记录的访问**==   | 在应用层做联接查询，意味着关于某条记录应用只需查询一次；而在数据库中做联接查询，则可能会重复地访问一部分数据 |

### 三、应用层联接的额外优势

在应用层做联接，还可以减少**网络和内存开销**。在有些场景下，执行联接操作更有效，比如说**缓存和重用之前查询结果中的数据**。

### 四、适用场景

| 适用场景 | 说明 |
|---------|------|
| ==**数据量大、多表关联**== | 单表查询 + 应用层联接，避免复杂的多表 JOIN |
| ==**需要缓存复用**== | 单表结果更容易缓存，复用性更强 |
| ==**数据库垂直分库后**== | 跨库无法进行 JOIN，只能在应用层做联接 |

| 不适用场景 | 说明 |
|-----------|------|
| ==**数据量小、单次简单查询**== | 数据在同一台服务器时，数据库内 JOIN 可能比应用层联接更快 |
| ==**对实时一致性要求高的场景**== | 应用层联接需要多次查询，数据可能不一致 |
